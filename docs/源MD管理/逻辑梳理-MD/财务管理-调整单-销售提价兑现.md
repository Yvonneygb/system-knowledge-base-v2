# 财务管理-调整单-销售提价兑现

> 后端代码位于 `ae-business` 微服务，核心类：`EpmSalesPriceRebateServiceImpl`、`EpmSalesPriceRebateController`。前端为低代码页面(hlod)，无独立前端源码。

## 业务流程

### 业务流程图

```text
销售提价兑现列表页(hlod低代码页面)
        │
        ├── 新建兑现单 ──→ 弹窗填写：事业部/经销商/限定日期范围/入账日期
        │                    │
        │                    └── POST /v1/{orgId}/epm-sales-price-rebate/generate-rebate-summary
        │                         └── 调用 operationCashBiz 方法
        │                              ├── signRebateDetails()：更新已签收返利明细的签收标识
        │                              ├── generateCashDetails()：按事业部+法人客户+经销商+交易主体获取兑现明细
        │                              ├── 保存兑现单头(CASH_SUMMARY)
        │                              ├── 保存兑现明细(CASH_DETAILS)
        │                              └── 更新返利明细的兑现标识(REBATE_DETAILS.REDEMPTION_FLAG=Y)
        │
        ├── 推送ERP ──→ POST /v1/{orgId}/epm-sales-price-rebate/request-composer?cashId={id}
        │                └── 调用 pushErp 方法
        │                     ├── 校验兑现单是否存在
        │                     ├── 校验兑现单是否已推送成功
        │                     ├── 查询未推送/推送失败的兑现明细
        │                     ├── 组装推送数据(CashPoolDataDTO)
        │                     │    └── 来源数据ID、交易公司编码、经销商编码、法人账户ID、金额、入账日期
        │                     ├── 调用 ebsSdkService.synAdjustCashPoolToEbs 推送至ERP资金池
        │                     └── 根据ERP返回结果更新推送状态
        │
        └── 查看/编辑兑现单 ──→ 查看兑现单头(CASH_SUMMARY)和兑现明细(CASH_DETAILS)
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| 发票真实性核销 | 数据依赖 | 返利明细数据来源于真实性核销返利 | 核销已审批通过且已签收 |
| 折扣政策 | 数据依赖 | 销售提价来源于折扣政策配置 | 折扣政策已审批 |
| ERP资金池 | 服务依赖 | 兑现汇总单推送至ERP资金池 | ERP系统可用 |
| 法人账户配置 | 配置依赖 | 推送ERP时需要法人账户ID | EPM_LEGAL_ENTITY_ACCOUNT已配置 |

### 下游影响

- 影响1：ERP资金池
  - 兑现汇总单推送至ERP资金池，增加资金池余额

- 影响2：返利明细状态
  - 生成兑现单后，返利明细的REDEMPTION_FLAG更新为Y，防止重复兑现

- 影响3：兑现记录
  - 生成兑现记录写入CASH_SUMMARY表和CASH_DETAILS表，供后续查询和对账

## 重点逻辑

### 重点逻辑1：生成兑现汇总单 {数据汇总}

- **业务意义**：将分散的返利明细按事业部维度汇总为兑现汇总单，便于统一兑现和推送

- **具体逻辑描述**

  - 第1点：先调用signRebateDetails()更新已签收返利明细的签收标识，将已签收的返利明细SIGN_FLAG更新为Y

  - 第2点：调用generateCashDetails()按事业部+法人客户+经销商+交易主体获取兑现明细

  - 第3点：按事业部(entId)分组，每个事业部生成一个兑现单头(CASH_SUMMARY)

  - 第4点：保存兑现明细(CASH_DETAILS)，关联兑现单头ID

  - 第5点：更新返利明细的兑现标识(REDEMPTION_FLAG=Y)和关联的兑现明细ID

### 重点逻辑2：ERP资金池推送 {数据推送}

- **业务意义**：兑现结果推送至ERP资金池，确保财务系统数据同步

- **具体逻辑描述**

  - 第1点：校验兑现单是否存在(cashSummaryRepository.selectById)，不存在则抛出"兑现单异常，请稍后重试"

  - 第2点：校验兑现单是否已推送成功(getPushStatus==SUCCESS)，已推送则抛出"当前兑现不允许推送,请重新核实"

  - 第3点：查询未推送或推送失败的兑现明细(cashSummaryRepository.findListUnprocessedByCashId)

  - 第4点：组装推送数据(CashPoolDataDTO)，包含来源数据ID、交易公司编码、经销商编码、法人账户ID、金额、入账日期

  - 第5点：调用ebsSdkService.synAdjustCashPoolToEbs推送至ERP资金池

  - 第6点：根据ERP返回结果更新推送状态，只有所有行都成功才标记兑现单头为SUCCESS

### 重点逻辑3：签收标识更新 {签收校验}

- **业务意义**：确保只有已签收的返利明细才能参与兑现，防止未签收数据被误兑现

- **具体逻辑描述**

  - 第1点：查询所有SIGN_FLAG=N且REDEMPTION_FLAG=N的返利明细

  - 第2点：批量查询这些返利明细对应的发货行是否已签收(lnkObOrderReceivableRepository.signedStatu)

  - 第3点：对已签收的返利明细更新SIGN_FLAG为Y

#### 按钮1：新建兑现单（列表页）

- **触发条件**：点击"新建"按钮
- **执行逻辑**：
  - 第1点：弹窗显示创建表单，包含事业部、经销商、限定日期开始、限定日期结束、入账日期
  - 第2点：用户填写参数后点击确认
  - 第3点：调用POST /v1/{orgId}/epm-sales-price-rebate/generate-rebate-summary接口
  - 第4点：后端operationCashBiz方法先调用signRebateDetails()更新已签收返利明细的签收标识
  - 第5点：调用generateCashDetails()按事业部+法人客户+经销商+交易主体获取兑现明细
  - 第6点：按事业部分组，每个事业部生成一个兑现单头(CASH_SUMMARY)
  - 第7点：保存兑现明细(CASH_DETAILS)，关联兑现单头ID
  - 第8点：更新返利明细的兑现标识(REDEMPTION_FLAG=Y)
- **接口调用**：POST `/v1/{organizationId}/epm-sales-price-rebate/generate-rebate-summary`
- **排查SQL**：

```sql
-- 查询兑现单列表（按创建时间倒序）
SELECT
  cs.ID              AS 兑现单ID,
  cs.ENT_ID          AS 事业部ID,
  cs.CUSTOMER_ID     AS 经销商ID,
  cs.AMOUNT          AS 兑现金额,
  TO_CHAR(cs.GL_DATE, 'YYYY-MM-DD') AS 入账日期,
  TO_CHAR(cs.START_TIME, 'YYYY-MM-DD') AS 兑现开始时间,
  TO_CHAR(cs.END_TIME, 'YYYY-MM-DD') AS 兑现结束时间,
  cs.PUSH_STATUS     AS 推送状态,
  TO_CHAR(cs.PUSH_TIME, 'YYYY-MM-DD HH24:MI:SS') AS 推送时间,
  cs.REMARKS         AS 备注
FROM CASH_SUMMARY cs
ORDER BY cs.CREATED DESC;

-- 查询兑现明细
SELECT
  cd.ID              AS 兑现明细ID,
  cd.CASH_SUMMARY_ID AS 兑现单ID,
  cd.BILL_ID         AS 法人ID,
  cd.CUSTOMER_ID     AS 经销商ID,
  cd.TRADING_COMPANY_ID AS 交易公司ID,
  cd.REBATE_AMT      AS 返点金额,
  cd.PUSH_STATUS     AS 推送状态,
  TO_CHAR(cd.PUSH_TIME, 'YYYY-MM-DD HH24:MI:SS') AS 推送时间,
  cd.CURRENCY        AS 币种
FROM CASH_DETAILS cd
WHERE cd.CASH_SUMMARY_ID = #{cashSummaryId}
ORDER BY cd.ID;

-- 查询返利明细的签收和兑现状态
SELECT
  rd.ID              AS 返利明细ID,
  rd.BILL_ID         AS 法人ID,
  rd.ENT_ID          AS 事业部ID,
  rd.TRADING_COMPANY_ID AS 交易公司ID,
  rd.CUSTOMER_ID     AS 经销商ID,
  rd.ACTION_OPT      AS 操作类型,
  rd.OPT_QTY         AS 操作数量,
  rd.REBATE_QTY      AS 返点数量,
  rd.REBATE_AMT      AS 返点金额,
  rd.REBATE_SUMMARY_ID AS 返点记录控制ID,
  rd.CASH_DETAILS_ID AS 兑现明细ID,
  rd.REDEMPTION_FLAG AS 是否已兑现,
  rd.SIGN_FLAG       AS 是否已签收,
  rd.CURRENCY        AS 币种,
  TO_CHAR(rd.CREATED, 'YYYY-MM-DD') AS 创建时间,
  TO_CHAR(rd.LAST_UPD, 'YYYY-MM-DD') AS 最后更新时间,
  rd.LAST_UPD_BY     AS 最后更新人
FROM REBATE_DETAILS rd
WHERE rd.SIGN_FLAG = 'N'
  AND rd.REDEMPTION_FLAG = 'N'
ORDER BY rd.CREATED DESC;
```

#### 按钮2：推送ERP（列表页）

- **触发条件**：选中一条兑现单且推送状态≠SUCCESS
- **执行逻辑**：
  - 第1点：校验cashId不为0，否则抛出"兑现单参数不能为空"
  - 第2点：查询兑现单头(cashSummaryRepository.selectById)，不存在则抛出"兑现单异常，请稍后重试"
  - 第3点：校验兑现单推送状态，已推送成功则抛出"当前兑现不允许推送,请重新核实"
  - 第4点：查询未推送或推送失败的兑现明细(findListUnprocessedByCashId)，无明细则抛出"当前兑现单没有符合推送的明细"
  - 第5点：组装推送数据(CashPoolDataDTO)，遍历兑现明细，查询法人账户ID(epmLegalEntityAccountRepository.getLegalEntityAccount)
  - 第6点：调用ebsSdkService.synAdjustCashPoolToEbs推送至ERP资金池
  - 第7点：解析ERP返回结果(X_DATA_TBL)，逐行判断PROCESS_STATUS是否为S(成功)
  - 第8点：更新兑现明细和兑现单头的推送状态
- **接口调用**：POST `/v1/{organizationId}/epm-sales-price-rebate/request-composer?cashId={cashId}`
- **排查SQL**：

```sql
-- 查询未推送或推送失败的兑现单
SELECT
  cs.ID              AS 兑现单ID,
  cs.ENT_ID          AS 事业部ID,
  cs.AMOUNT          AS 兑现金额,
  cs.PUSH_STATUS     AS 推送状态,
  TO_CHAR(cs.PUSH_TIME, 'YYYY-MM-DD HH24:MI:SS') AS 推送时间
FROM CASH_SUMMARY cs
WHERE cs.PUSH_STATUS IS NULL
   OR cs.PUSH_STATUS = 'PENDING'
   OR cs.PUSH_STATUS = 'FAIL'
ORDER BY cs.CREATED DESC;

-- 查询未推送的兑现明细
SELECT
  cd.ID              AS 兑现明细ID,
  cd.CASH_SUMMARY_ID AS 兑现单ID,
  cd.CUSTOMER_ID     AS 经销商ID,
  cd.TRADING_COMPANY_ID AS 交易公司ID,
  cd.REBATE_AMT      AS 返点金额,
  cd.PUSH_STATUS     AS 推送状态
FROM CASH_DETAILS cd
WHERE cd.PUSH_STATUS IS NULL
   OR cd.PUSH_STATUS != 'SUCCESS'
ORDER BY cd.ID;

-- 查询法人账户配置
SELECT
  lea.LEGAL_ENTITY_ACCOUNT_ID AS 法人账户ID,
  lea.TRADING_COMPANY_ID      AS 交易公司ID,
  lea.CUSTOMER_ID             AS 经销商ID,
  lea.ACCOUNT_ID              AS 账户ID
FROM EPM_LEGAL_ENTITY_ACCOUNT lea
WHERE lea.TRADING_COMPANY_ID = #{tradingCompanyId}
  AND lea.CUSTOMER_ID = #{customerId};
```

### 保存校验

- 校验1：限定日期开始和结束不能为空 —— 确保查询返利明细的时间范围有效

  - 详细逻辑

    - 第1点：generateCashDetails方法校验dto.getStartTime().isEmpty() || dto.getEndTime().isEmpty()

    - 第2点：为空时抛出CommonException("开始时间或结束时间不能为空")

  - 系统体现：toast提醒"开始时间或结束时间不能为空"

  - 排查SQL：

    ```sql
    SELECT ID, START_TIME, END_TIME, GL_DATE
    FROM CASH_SUMMARY
    WHERE START_TIME IS NULL OR END_TIME IS NULL;
    ```

- 校验2：入账日期不能为空 —— 确保兑现单有有效的入账日期

  - 详细逻辑

    - 第1点：generateCashDetails方法校验dto.getGlDate().isEmpty()

    - 第2点：为空时抛出CommonException("入账日期不能为空")

  - 系统体现：toast提醒"入账日期不能为空"

  - 排查SQL：

    ```sql
    SELECT ID, GL_DATE
    FROM CASH_SUMMARY
    WHERE GL_DATE IS NULL;
    ```

### 状态机

#### 状态机流转图

```text
新建兑现单 ──生成──→ PENDING(未推送) ──推送ERP──→ SUCCESS(推送成功)
                                        │
                                        └──→ FAIL(推送失败) ──重新推送──→ SUCCESS
```

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|------------|

#### 报错1：兑现单参数不能为空

- **触发条件**：用户点击"推送ERP"按钮，传入的cashId为0
- **逻辑分析**：pushErp方法在EpmSalesPriceRebateServiceImpl.java:66处校验cashId==0时抛出CommonException("兑现单参数不能为空")。该校验为前置参数校验，防止空指针和无效查询。需在列表页选中有效的兑现汇总单记录后再点击推送
- **排查SQL**：

```sql
SELECT ID, AMOUNT, PUSH_STATUS, GL_DATE
FROM CASH_SUMMARY
WHERE ID = #{cashId};
```

#### 报错2：兑现单异常，请稍后重试

- **触发条件**：用户选中兑现单点击"推送ERP"，但cashSummaryRepository.selectById(cashId)返回null
- **逻辑分析**：pushErp方法在EpmSalesPriceRebateServiceImpl.java:70处校验兑现单头不存在时抛出CommonException("兑现单异常，请稍后重试")。根因有三类：(1)兑现单已被其他用户删除；(2)兑现单ID被篡改；(3)并发操作导致数据不一致。需刷新列表确认兑现单是否存在
- **排查SQL**：

```sql
SELECT ID, AMOUNT, PUSH_STATUS, GL_DATE
FROM CASH_SUMMARY
WHERE ID = #{cashId};
```

#### 报错3：当前兑现不允许推送,请重新核实

- **触发条件**：用户选中已推送成功的兑现单再次点击"推送ERP"
- **逻辑分析**：pushErp方法在EpmSalesPriceRebateServiceImpl.java:73处校验cashH.getPushStatus()等于SUCCESS时抛出CommonException("当前兑现不允许推送,请重新核实")。该校验防止重复推送导致ERP资金池数据重复。需核实兑现单推送状态，仅PENDING或FAIL状态的兑现单可推送
- **排查SQL**：

```sql
SELECT ID, AMOUNT, PUSH_STATUS, PUSH_TIME
FROM CASH_SUMMARY
WHERE ID = #{cashId} AND PUSH_STATUS = 'SUCCESS';
```

#### 报错4：当前兑现单没有符合推送的明细

- **触发条件**：用户选中兑现单点击"推送ERP"，兑现明细均已推送或无有效明细
- **逻辑分析**：pushErp方法在EpmSalesPriceRebateServiceImpl.java:80处校验cashDetailsV为空时抛出CommonException("当前兑现单没有符合推送的明细")。根因有二：(1)兑现明细均已推送成功或推送失败，无PENDING状态明细；(2)兑现明细对应的交易公司、经销商在EPM_LEGAL_ENTITY_ACCOUNT中未配置账户ID，导致所有明细被过滤。需核查明细推送状态及法人账户配置
- **排查SQL**：

```sql
-- 查询兑现明细的推送状态
SELECT
  cd.ID              AS 兑现明细ID,
  cd.CASH_SUMMARY_ID AS 兑现单ID,
  cd.REBATE_AMT      AS 返点金额,
  cd.PUSH_STATUS     AS 推送状态,
  cd.TRADING_COMPANY_ID AS 交易公司ID,
  cd.CUSTOMER_ID     AS 经销商ID
FROM CASH_DETAILS cd
WHERE cd.CASH_SUMMARY_ID = #{cashId}
  AND cd.PUSH_STATUS != 'SUCCESS';

-- 核查法人账户配置
SELECT
  lea.LEGAL_ENTITY_ACCOUNT_ID AS 法人账户ID,
  lea.TRADING_COMPANY_ID      AS 交易公司ID,
  lea.CUSTOMER_ID             AS 经销商ID,
  lea.ACCOUNT_ID              AS 账户ID
FROM EPM_LEGAL_ENTITY_ACCOUNT lea
WHERE lea.TRADING_COMPANY_ID = #{tradingCompanyId}
  AND lea.CUSTOMER_ID = #{customerId};
```

#### 报错5：ERP返回数据异常，没有结果明细

- **触发条件**：推送ERP后，ERP接口返回的X_DATA_TBL_ITEM为空或null
- **逻辑分析**：pushErp方法在EpmSalesPriceRebateServiceImpl.java:168处校验tblItemArr为空时抛出CommonException("ERP返回数据异常，没有结果明细")。该异常表示ERP接口synAdjustCashPoolToEbs调用成功但返回结果格式异常，缺少X_DATA_TBL_ITEM节点。根因有二：(1)ERP接口版本不匹配，返回格式变更；(2)ERP侧处理异常但未按约定格式返回错误。需联系ERP运维核查接口日志
- **排查SQL**：

```sql
SELECT ID, AMOUNT, PUSH_STATUS, PUSH_TIME
FROM CASH_SUMMARY
WHERE ID = #{cashId};
```

#### 报错6：没有可处理的明细

- **触发条件**：用户点击"生成兑现汇总单"按钮，operationCashBiz方法查询无符合生成条件的返利明细
- **逻辑分析**：operationCashBiz方法在EpmSalesPriceRebateServiceImpl.java:227处校验cashDetailsV为空时抛出CommonException("没有可处理的明细")。该方法先调用signRebateDetails更新已签收返点明细，再通过generateCashDetails按事业部+法人客户+经销商+交易主体获取兑现明细。无明细根因有三类：(1)上游发票真实性核销未审批通过，返利明细未生成；(2)返利明细已全部生成过兑现(REDEMPTION_FLAG=Y)；(3)查询条件(事业部/经销商/时间范围)不匹配。需核查返利明细的签收和兑现标志
- **排查SQL**：

```sql
-- 查询未兑现且已签收的返利明细
SELECT
  rd.ID              AS 返利明细ID,
  rd.ENT_ID          AS 事业部ID,
  rd.CUSTOMER_ID     AS 经销商ID,
  rd.REBATE_AMT      AS 返点金额,
  rd.REDEMPTION_FLAG AS 是否已兑现,
  rd.SIGN_FLAG       AS 是否已签收
FROM REBATE_DETAILS rd
WHERE rd.SIGN_FLAG = 'Y'
  AND rd.REDEMPTION_FLAG = 'N'
  AND rd.ENT_ID = #{entId}
  AND (rd.CUSTOMER_ID = #{customerId} OR #{customerId} IS NULL);
```

### 常见问题

- 问题1：兑现单生成后金额为0
  - 原因：返利明细的REBATE_AMT为0或null，排查SQL：SELECT rd.ID, rd.REBATE_AMT, rd.REDEMPTION_FLAG FROM REBATE_DETAILS rd WHERE rd.REBATE_AMT IS NULL OR rd.REBATE_AMT = 0;
  - 解决思路：检查上游发票真实性核销是否正确生成了返利金额

- 问题2：推送ERP失败
  - 原因：ERP系统不可用或推送数据异常(兑现金额为0/负数、经销商编码在ERP中不存在、项目编码不匹配)，排查SQL：SELECT cd.ID, cd.REBATE_AMT, cd.PUSH_STATUS, cd.TRADING_COMPANY_ID, cd.CUSTOMER_ID FROM CASH_DETAILS cd WHERE cd.PUSH_STATUS = 'FAIL';
  - 解决思路：检查CASH_DETAILS.PUSH_STATUS为FAIL的记录，核实法人账户配置和经销商数据

- 问题3：兑现明细对应的法人账户ID为空
  - 原因：EPM_LEGAL_ENTITY_ACCOUNT表中未配置该交易公司和经销商对应的账户ID，排查SQL：SELECT lea.* FROM EPM_LEGAL_ENTITY_ACCOUNT lea WHERE lea.TRADING_COMPANY_ID = #{tradingCompanyId} AND lea.CUSTOMER_ID = #{customerId};
  - 解决思路：在法人账户配置页面补充配置
