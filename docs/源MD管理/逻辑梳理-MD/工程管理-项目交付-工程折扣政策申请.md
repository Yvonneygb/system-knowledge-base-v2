### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| CRM产品信息 | 数据依赖 | 通过CRM接口获取产品信息（getCrmItem），用于产品明细行选择 | CRM接口可用 |
| 产品价格表 | 数据依赖 | 通过get-prices接口获取产品实时价格，自动填充标准单价 | 产品在价格表中存在 |
| 经销商主档 | 数据依赖 | 政策关联适用经销商（customerStr/customerObj） | 经销商在系统中有效 |
| 编码规则配置 | 配置依赖 | 工程使用编码规则AE.EPM_DISCOUNT_POLICY_GC自动生成政策编码 | 编码规则已配置且生效 |
| 工作流引擎 | 配置依赖 | 启动OA审批流程，多级审批 | 工作流已部署且可用 |
| OA审批系统 | 配置依赖 | OA多级审核，审批通过后回调更新政策状态 | OA流程配置完成 |
| CRM系统 | 数据依赖 | 专项折扣审批通过后同步CRM创建政策 | suitableType=special时推送 |

### 下游影响

- 影响1：政策生效后可用于折扣单创建
  - 审批通过后valid=2，工程折扣单创建时可引用该政策的折扣率

- 影响2：驱动工程要货订单定价
  - 政策生效后，要货订单根据政策自动计算折扣率/特价

- 影响3：可发起折扣政策失效
  - 政策生效后可通过"工程折扣政策失效"功能将部分产品项失效

- 影响4：专项折扣同步CRM
  - 专项政策审批通过后调用CRM接口创建政策，CRM返回crmid/crmcode

## 重点逻辑

### 重点逻辑1：工程/家装/样品三菜单共用后端代码

- **业务意义**：三个菜单共用同一套后端Controller和ServiceImpl，通过参数区分业务类型，减少重复代码

- **具体逻辑描述**

  - 第1点：工程isMakt=0, suitableType=normal；家装isMakt=0, suitableType=normal(通过事业部区分)；样品isMakt=2, suitableType=special

  - 第2点：编码规则根据suitableType和isMakt选择——工程用AE.EPM_DISCOUNT_POLICY_GC、家装用AE.EPM_DISCOUNT_POLICY_JZ、样品用AE.EPM_DISCOUNT_POLICY

  - 第3点：审批通过后，通用折扣(suitableType=normal)直接生效(valid=2)，专项折扣(suitableType=special)需同步CRM再生效

### 重点逻辑2：政策类型控制适用范围字段动态显隐

- **业务意义**：根据政策类型动态控制适用范围字段的必填和可编辑状态，确保不同类型政策配置正确的适用范围

- **具体逻辑描述**

  - 第1点：政策类型=1(客户)时，适用客户必填且可编辑，适用区域/省份/客户分类清空且禁用

  - 第2点：政策类型=2(区域)时，适用区域必填且可编辑，适用省份/客户分类清空且禁用

  - 第3点：政策类型=3(客户分类)时，适用客户分类必填且可编辑，适用区域/省份清空且禁用

  - 第4点：政策类型=4(省份)时，适用省份必填且可编辑，适用区域/客户分类清空且禁用

### 重点逻辑3：保存前多项预校验

- **业务意义**：保存时执行多项业务校验，确保政策数据完整性、合规性和防重复配置

- **具体逻辑描述**

  - 第1点：校验产品行(checkProductLine)——确保至少有一条产品明细行

  - 第2点：校验申请类型(checkApplicationType)——"全产品类型"与"型号"或"产品"类型不能同时存在

  - 第3点：校验优惠方式(checkPreferentialType)——通用折扣时产品优惠方式只能为"折扣"

  - 第4点：校验必填字段(requiredField)——头信息关键字段已填写

  - 第5点：校验产品不重复——同一产品/型号不能在多个有效政策中重复配置

  - 第6点：校验封顶数量——单个经销商封顶数量不能大于政策行封顶总数量

  - 第7点：校验新品——涉及新品型号时不允许通过型号定义折扣政策

### 重点逻辑4：审批通过后生效逻辑

- **业务意义**：工作流审批通过是政策生效的必要条件，不同类型政策生效方式不同

- **具体逻辑描述**

  - 第1点：通用折扣(suitableType=normal)审批通过后直接设valid=2(有效)，无需推送CRM

  - 第2点：专项折扣(suitableType=special)审批通过后调用CRM接口创建折扣政策，CRM返回crmid/crmcode后设valid=2

  - 第3点：审批拒绝/终止时更新hzApproveStatus，不改变valid状态

### 重点逻辑5：产品明细和阶梯政策导入

- **业务意义**：支持通过Excel批量导入产品明细和阶梯政策，提高录入效率

- **具体逻辑描述**

  - 第1点：调用importProduct接口，解析Excel文件

  - 第2点：根据申请类型(产品/型号/全产品)分别处理导入逻辑

  - 第3点：导入时自动匹配产品价格和折扣信息

### 保存校验

- 校验1：产品行不能为空 —— 确保至少有一条产品明细行

  - 详细逻辑

    - 第1点：checkProductLine校验产品行列表不为空且存在非delete状态行

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM
    WHERE DISCOUNT_POLICY_ID = :id
    ```

- 校验2：申请类型不能同时存在"全产品"与"型号"或"产品" —— 确保申请类型不冲突

  - 详细逻辑

    - 第1点：checkApplicationType校验不能同时存在applicationType=3(全产品)与applicationType=1(产品)或2(型号)

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT DISTINCT APPLICATION_TYPE FROM EPM_DISCOUNT_POLICY_ITEM
    WHERE DISCOUNT_POLICY_ID = :id
    ```

- 校验3：通用折扣时产品优惠方式只能为"折扣" —— 确保通用政策优惠方式合规

  - 详细逻辑

    - 第1点：suitableType=normal时，产品行preferentialType必须为1(折扣)

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT ITEM.PREFERENTIAL_TYPE FROM EPM_DISCOUNT_POLICY_ITEM ITEM
    JOIN EPM_DISCOUNT_POLICY P ON ITEM.DISCOUNT_POLICY_ID = P.DISCOUNT_POLICY_ID
    WHERE P.DISCOUNT_POLICY_ID = :id AND P.SUITABLE_TYPE = 'normal'
    ```

- 校验4：同一产品/型号不能在多个有效政策中重复配置 —— 防止重复折扣配置

  - 详细逻辑

    - 第1点：校验有效区间内同一产品编码或型号不在其他有效政策中已存在

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT ITEM.ITEM_CODE, P.DISCOUNT_POLICY_NAME
    FROM EPM_DISCOUNT_POLICY_ITEM ITEM
    JOIN EPM_DISCOUNT_POLICY P ON ITEM.DISCOUNT_POLICY_ID = P.DISCOUNT_POLICY_ID
    WHERE ITEM.ITEM_CODE = :itemCode
      AND P.VALID = 2
      AND P.DISCOUNT_POLICY_ID != :currentPolicyId
    ```

- 校验5：单个经销商封顶数量不大于政策行封顶总数量 —— 确保封顶数量逻辑正确

  - 详细逻辑

    - 第1点：capping=2(校验)时，customerCapsNumber必须不大于totalCapNumber

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql

    FROM EPM_DISCOUNT_POLICY_ITEM
    WHERE DISCOUNT_POLICY_ID = :id AND CAPPING = 2
    ```

- 校验6：新品型号不允许通过型号定义折扣政策 —— 确保新品通过具体产品编码制定政策

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    WHERE ITEM.APPLICATION_TYPE = 2 AND ITEM.NEW_PROD_FLAG = 'Y'
    ```

- 校验7：折扣政策名称最大30个字符 —— 确保名称长度合规

  - 详细逻辑

    - 第1点：校验discountPolicyName长度不超过30

### 状态机

#### 状态机流转图

```text
NEW(新建) ──保存并提交──→ RUN(审批中) ──审批通过──→ APPROVED(已审批) → 通用折扣直接生效/专项折扣同步CRM
  ↑                         │
  │                         ├──审批拒绝──→ REJECTED(已拒绝) ──修改后保存并提交──→ RUN
  │                         ├──审批驳回──→ REBUT(已驳回)
  │                         └──终止──────→ INTERRUPT(已终止)
  │
  └──删除──→ (删除)

NEW ──撤回──→ WITHDRAW(已撤回) ──保存并提交──→ RUN
```

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|------------|
| NEW | 新建 | 编辑、保存、保存并提交、删除 |
| RUN | 审批中 | 无(等待审批结果) |
| APPROVED | 审批通过 | 无(流程结束，政策已生效) |
| REJECTED | 审批拒绝 | 编辑、保存、保存并提交 |
| REBUT | 已驳回 | 编辑、保存、保存并提交 |
| WITHDRAW | 已撤回 | 编辑、保存、保存并提交 |
| INTERRUPT | 已终止 | 无(流程结束) |

#### 报错1：产品行不能为空，请检查！
- **触发条件**：保存折扣政策申请时，discountPolicyItemDTOList为空或所有行均为delete状态
- **逻辑分析**：保存校验中检查产品行列表非空且至少有一行非delete状态。该报错为阻断性报错
- **排查SQL**：
  ```sql
  SELECT edp.DISCOUNT_POLICY_ID, edp.DISCOUNT_POLICY_CODE,
         (SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM edpi
          WHERE edpi.DISCOUNT_POLICY_ID = edp.DISCOUNT_POLICY_ID) AS 产品行数
  FROM EPM_DISCOUNT_POLICY edp
  WHERE edp.DISCOUNT_POLICY_ID = :discountPolicyId
  ```

#### 报错2：申请类型："全产品类型" 与 ("型号"或"产品")类型 不能同时存在，请检查！
- **触发条件**：保存时，同时存在applicationType=3(全产品)与applicationType=1(产品)或2(型号)
- **逻辑分析**：保存校验中按APPLICATION_TYPE分组，若同时存在全产品(3)和具体产品/型号(1/2)则抛出阻断性报错。需调整申请类型使不冲突
- **排查SQL**：
  ```sql
  SELECT edpi.APPLICATION_TYPE, COUNT(*) AS 行数
  FROM EPM_DISCOUNT_POLICY_ITEM edpi
  WHERE edpi.DISCOUNT_POLICY_ID = :discountPolicyId
  GROUP BY edpi.APPLICATION_TYPE
  -- 检查是否存在APPLICATION_TYPE=3与1/2同时存在
  ```

#### 报错3：适用类型为"通用"时，产品优惠方式只能为 "折扣"
- **触发条件**：保存时，通用折扣(suitableType=normal)时产品优惠方式(PREFERENTIAL_TYPE)不为1(折扣)
- **逻辑分析**：保存校验中检查通用折扣政策的优惠方式必须为折扣(1)，其他优惠方式(特价/一口价)仅专项折扣支持。需修改优惠方式为折扣
- **排查SQL**：
  ```sql
  SELECT edpi.DISCOUNT_POLICY_ITEM_ID, edpi.ITEM_CODE, edpi.PREFERENTIAL_TYPE, edp.SUITABLE_TYPE
  FROM EPM_DISCOUNT_POLICY_ITEM edpi
  JOIN EPM_DISCOUNT_POLICY edp ON edpi.DISCOUNT_POLICY_ID = edp.DISCOUNT_POLICY_ID
  WHERE edp.SUITABLE_TYPE = 'normal'
    AND edpi.PREFERENTIAL_TYPE <> 1
  ```

#### 报错4：该产品[{编码}]已在折扣政策[{政策名}]里，若需继续录入，请在原折扣政策失效此产品，否则请删除对应产品行
- **触发条件**：保存时，同一产品编码在有效区间内已在其他有效政策(VALID=2)中存在
- **逻辑分析**：保存校验中按ITEM_CODE查询EPM_DISCOUNT_POLICY_ITEM关联EPM_DISCOUNT_POLICY筛选VALID=2且非当前政策，若存在则抛出阻断性报错。需在原政策失效该产品或删除当前行
- **排查SQL**：
  ```sql
  SELECT edpi.ITEM_CODE, edpi.ITEM_NAME, edp.DISCOUNT_POLICY_ID, edp.DISCOUNT_POLICY_CODE,
         edp.DISCOUNT_POLICY_NAME, edp.VALID, edp.EFFECTIVE_DATE_START, edp.EFFECTIVE_DATE_END
  FROM EPM_DISCOUNT_POLICY_ITEM edpi
  JOIN EPM_DISCOUNT_POLICY edp ON edpi.DISCOUNT_POLICY_ID = edp.DISCOUNT_POLICY_ID
  WHERE edpi.ITEM_CODE = :itemCode
    AND edp.VALID = 2
    AND edp.DISCOUNT_POLICY_ID <> :currentPolicyId
  ```

#### 报错5：该型号[{型号}]已在折扣政策[{政策名}]里，若需继续录入，请在原折扣政策失效此产品，否则请删除对应产品行
- **触发条件**：保存时，同一型号在有效区间内已在其他有效政策(VALID=2)中存在
- **逻辑分析**：保存校验中按MODEL查询EPM_DISCOUNT_POLICY_ITEM关联EPM_DISCOUNT_POLICY筛选VALID=2且非当前政策，若存在则抛出阻断性报错。需在原政策失效该型号或删除当前行
- **排查SQL**：
  ```sql
  SELECT edpi.MODEL, edpi.ITEM_NAME, edp.DISCOUNT_POLICY_ID, edp.DISCOUNT_POLICY_CODE,

    AND edp.DISCOUNT_POLICY_ID <> :currentPolicyId
  ```

#### 报错6：产品编码:{编码} 单个经销商封顶数量只能为空
- **触发条件**：保存时，全产品类型(APPLICATION_TYPE=3)的明细行配置了单个经销商封顶数量(CUSTOMER_CAPS_NUMBER)
- **逻辑分析**：保存校验中检查全产品类型不应有封顶数量，因全产品类型不针对具体经销商。需清空封顶数量
- **排查SQL**：
  ```sql
  SELECT edpi.DISCOUNT_POLICY_ITEM_ID, edpi.ITEM_CODE, edpi.APPLICATION_TYPE, edpi.CUSTOMER_CAPS_NUMBER
  FROM EPM_DISCOUNT_POLICY_ITEM edpi
  WHERE edpi.DISCOUNT_POLICY_ID = :discountPolicyId
    AND edpi.APPLICATION_TYPE = 3
    AND edpi.CUSTOMER_CAPS_NUMBER IS NOT NULL
  ```

### 常见问题

- 问题1：工程折扣政策和家装折扣政策的区别？
  - 原因：通过编码规则区分：工程使用AE.EPM_DISCOUNT_POLICY_GC，家装使用AE.EPM_DISCOUNT_POLICY_JZ。两者共用同一套后端API，通过事业部区分
  - 解决思路：检查当前用户事业部配置，确认使用正确的编码规则

- 问题2：产品明细如何添加？
  - 原因：两种方式：1) 通过"选择产品"按钮从CRM产品弹窗选择；2) 通过"导入产品"按钮上传Excel文件批量导入
  - 解决思路：根据数据量选择合适方式，少量用弹窗选择，大量用导入

- 问题3："获取价格"功能的作用？
  - 原因：从产品价格表获取实时标准单价，自动填充到产品明细行，避免手动输入错误价格
  - 解决思路：在录入产品后点击"获取价格"按钮自动填充

- 问题4：政策审批通过后有什么影响？
  - 原因：政策生效后(valid=2)可用于折扣单创建，系统在创建折扣单时会根据政策自动计算折扣率。同一产品/型号不能在多个有效政策中重复配置
  - 解决思路：这是预期行为，如需调整需先失效原政策

- 问题5：如何让政策中的部分产品失效？
  - 原因：通过"工程折扣政策失效"功能，创建失效单选择要失效的产品项，审批通过后这些产品项不再适用于新折扣单
  - 解决思路：在"工程折扣政策失效"菜单中发起失效申请

- 问题6：审批通过后政策仍为未审核状态怎么办？
  - 原因：valid字段未更新为2，可能是CRM同步失败(专项折扣)。排查SQL：`SELECT VALID, CRMID, CRMCODE FROM EPM_DISCOUNT_POLICY WHERE DISCOUNT_POLICY_ID = :id`
  - 解决思路：检查CRM接口状态，确认CRM是否成功创建政策

- 问题7：政策类型切换后适用范围字段未清空？
  - 原因：前端events.update中policyType变更时会自动清空不相关字段，但如果数据已保存需重新编辑
  - 解决思路：重新选择政策类型，系统会自动清空不相关字段
