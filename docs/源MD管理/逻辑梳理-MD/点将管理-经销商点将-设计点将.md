# 点将管理-经销商点将-设计点将

> 后端代码位于 mbo-business 微服务，RESTful API 路径前缀 `mlt/designApply/*`。

## 业务流程

### 业务流程图

```
经销商发起设计点将
        |
        v
设计点将列表(本页面)
        |
        ├──新建──→ 跳转详情页(/detail/null/add) ──→ 填写申请信息
        |                                            ├──保存──→ dealerSave接口 ──→ 草稿
        |                                            └──保存并提交──→ dealerSaveAndSubmit接口 ──→ 已提交
        |
        ├──编辑──→ 跳转详情页 ──→ 修改后保存/保存并提交
        |
        ├──删除──→ 校验草稿/驳回状态 ──→ delete接口
        |
        ├──取消申请──→ 弹窗填写取消原因 ──→ cancelApply接口
        |
        ├──设计点将独特流程：
        |   申请 → 审批 → 开始设计(startDesign) → 上传图纸(upload) → 图纸确认(startDrawingConfirm)
        |        → 下单(startOrder) → 区域确认(areaConfirm) → 完成
        |
        ├──下载设计图纸──→ 弹窗展示设计图/效果图/施工及软装图 ──→ 反馈
        |
        ├──设计改派──→ designReassignment接口
        |
        ├──查看反馈──→ queryFeedback接口
        |
        ├──上传设计图纸──→ upload接口
        |
        ├──效果图补申──→ 跳转详情页(/detail/{id}/supplement) ──→ dealerSaveSupplement/dealerSaveAndSubmitSupplement
        |
        └──行操作──→ 查看详情/查看流程/编辑/删除/效果图补申/下载图纸/终止(termination)
```

### 下游影响

- **设计师点将管理**：申请提交后进入管理审批，数据库共享
- **设计点将详情页**：申请/编辑/效果图补申跳转，openTab新标签页
- **流程摘要组件**：查看流程展示审批历史，ProcessDetail组件
- **服务确认回执**：确认服务安排，数据回写

- **设计图纸存储**：上传图纸存储至文件服务，downloadDrawing接口加载

## 重点逻辑

### 重点逻辑1：经销商发起视角

- **业务意义**：本菜单由经销商主动发起设计点将申请，经销商自主选择门店、设计师与设计信息。
- **具体逻辑描述**：通过`dealer`路径接口（dealerPage、dealerSave、dealerSaveAndSubmit）实现经销商发起，后端自动按当前登录经销商过滤数据并写入DEALER_CODE、DEALER_NAME。

### 重点逻辑2：数据范围隔离

- **业务意义**：经销商仅能查看和操作自己发起的设计点将记录，避免跨经销商数据泄露。
- **具体逻辑描述**：通过`dealer`路径接口自动按当前登录经销商过滤，前端无需传经销商参数。

### 重点逻辑3：applyCode自动生成

- **业务意义**：保证设计点将申请编码全局唯一、可追溯，作为主键贯穿全链路。
- **具体逻辑描述**：提交申请时系统自动生成唯一编码applyCode，写入APPLY_CODE字段。

### 重点逻辑4：设计点将独特流程

- **业务意义**：设计点将区别于其他点将类型，包含完整的设计服务流程：申请→审批→开始设计→上传图纸→图纸确认→下单→完成。
- **具体逻辑描述**：审批通过后由设计师开始设计（startDesign），上传设计图纸（upload），经销商进行图纸确认（startDrawingConfirm），确认后下单（startOrder），区域确认（areaConfirm），最终完成。任一环节可终止（termination）。

### 重点逻辑5：多级审批关联

- **业务意义**：设计点将涉及讲师审批、门店审批等多级审批流程，确保设计服务各方确认。
- **具体逻辑描述**：设计点将涉及designApplyApproval（讲师审批designApplyLecturerApproval）、designApplyTerminalApproval（门店审批）、designApplyCancelApproval（取消审批）等多级审批流程。

### 重点逻辑6：下载图纸与反馈

- **业务意义**：经销商可下载设计师上传的图纸并反馈意见，形成设计沟通闭环。
- **具体逻辑描述**：行操作"下载图纸"，弹窗展示三类图纸：设计图（designTableDS）、效果图（renderingTableDS）、施工及软装图（constructionTableDS）。通过`downloadDrawing`接口加载，每类图纸展示文件名称（可点击预览）和反馈按钮。点击反馈按钮弹窗展示反馈意见（feedbackComments，TextArea，必填）和历史反馈记录（feedbackListDS，通过`queryFeedback`接口加载）。通过：feedbackResult=approved；驳回：feedbackResult=reject。调用`POST feedback`接口，参数包含applyCode、designDrawingId、feedbackResult。

### 重点逻辑7：面积确认/图纸确认

- **业务意义**：面积确认用于确认设计面积以计算费用，图纸确认用于确认设计图纸满足需求。
- **具体逻辑描述**：面积确认校验 approvalState === 'fdd_in_approval'（FDD签署中），调用`useFDD`签合同；图纸确认校验 settlementConfirmState === 'to_be_confirm'（待确认），调用`useFDD`签结算合同。

### 重点逻辑8：效果图补申

- **业务意义**：对已完成的申请进行效果图补充申请，关联原申请。
- **具体逻辑描述**：行操作"效果图补申"，跳转`/detail/{applyCode}/supplement`，使用dealerSaveSupplement/dealerSaveAndSubmitSupplement接口保存，写入RELATION_APPLY_CODE关联原申请，APPLY_TYPE='supplement'。

### 重点逻辑9：设计改派

- **业务意义**：对已生效的设计点将可改派设计师，应对设计师档期变更。
- **具体逻辑描述**：调用`designReassignment`接口，更换设计师并重新走审批流程。

### 重点逻辑10：行操作显隐

- **业务意义**：根据申请状态差异化展示行操作，避免误操作。
- **具体逻辑描述**：编辑再发起：orderLectureState === 'draft' 或 approvalState 为 reject/oa_reject/fdd_reject；效果图补申：始终显示，跳转`/detail/{applyCode}/supplement`；下载图纸：始终显示；终止：根据设计流程状态显示。

### 重点逻辑11：点将设计面积说明

- **业务意义**：明确设计面积计算口径，为费用计算提供依据。
- **具体逻辑描述**：点将设计面积为店面原始结构净空面积，用于计算设计点将费用。

### 自动计算逻辑

| 计算项 | 计算公式 | 触发时机 | 数据来源 |
|--------|---------|---------|---------|
| 费用小计 | settlementAmount = (非增补时) storeArea * lecturerPrice + renderingNumber * 500 + airscapeNumber * 1250 | 效果图数量/鸟瞰图数量/店面面积 onChange | `DesignApplyDetail/index.tsx` 的 `computedSettlementAmount` |
| 门店地址 | storeArea(表单2) = provinceName + '/' + cityName + '/' + areaName | 选择门店弹窗确认 | `handleShowStoreList` 的 onOk |
| 门店详细地址 | storeAddress = storeInfo.addr | 选择门店弹窗确认 | `handleShowStoreList` 的 onOk |
| 门店编码 | storeCode = storeInfo.terminalCode | 选择门店弹窗确认 | `handleShowStoreList` 的 onOk |
| 店面负责人 | shopmanagerName = storeInfo.shopmanagerName | 选择门店弹窗确认 | `handleShowStoreList` 的 onOk |
| 负责人电话 | shopmanagerMob = storeInfo.shopmanagerMob | 选择门店弹窗确认 | `handleShowStoreList` 的 onOk |
| 开票账户 | legalEntityName/legalEntityCode | 选择交易公司弹窗确认 | `handleShowCompanyList` 的 onOk |

### 保存/提交校验

> 数据来源：`detail.tsx` 的 `handleSave` + `stores/detailConfig.tsx` 字段 required 配置。保存与保存并提交共用同一校验逻辑，依次校验 generalFormDS 和 designInfoFormDS。效果图增补模式使用 dealerSaveSupplement/dealerSaveAndSubmitSupplement 接口。

- 校验1：效果图数量必填 —— generalFormDS.renderingNumber，precision=0
- 校验2：鸟瞰图必填 —— generalFormDS.airscapeNumber，precision=0
- 校验3：店面面积必填（非增补模式） —— generalFormDS.storeArea，min=0.0001，step=0.01，precision=2
- 校验4：复尺面积必填（isConfirmArea时） —— generalFormDS.scaleArea
- 校验5：签订人必填（haveSigner时） —— generalFormDS.signer
- 校验6：所属运营中心必填 —— designInfoFormDS.opCenter
- 校验7：交易公司必填 —— designInfoFormDS.tradingCompanyName
- 校验8：开票账户必填 —— designInfoFormDS.legalEntityName（选交易公司自动带出）
- 校验9：门店名称必填 —— designInfoFormDS.storeName
- 校验10：门店地址必填 —— designInfoFormDS.storeArea（选门店自动带出）
- 校验11：店面类型必填 —— designInfoFormDS.storeType，值集MBO.ORD_LECTURER_STORE_TYPE
- 校验12：取消申请时取消原因必填 —— cancelFormDS.cancelReason
- 校验13：图纸反馈时反馈意见必填 —— feedbackFormDS.feedbackComments

### 状态机

流转图：

```
draft(新建) → submitted(已提交) → approved(审批通过) → valid(生效)
   → designing(开始设计) → drawing_uploaded(图纸已上传) → drawing_confirmed(图纸确认)
   → ordered(已下单) → area_confirmed(区域确认) → end(已完成)
rejected(审批驳回) → 可修改重提
valid → cancel_applied(取消申请中) → cancel_approved(已取消)
任一环节 → terminated(已终止)
```

状态列表：

| 当前状态 | 触发动作 | 目标状态 |
|---------|---------|---------|
| draft | 保存并提交 | submitted |
| submitted | 审批通过 | approved |
| submitted | 审批驳回 | rejected |
| rejected | 修改后重新提交 | submitted |
| approved | 生效 | valid |
| valid | 开始设计 | designing |
| designing | 上传图纸 | drawing_uploaded |
| drawing_uploaded | 图纸确认 | drawing_confirmed |
| drawing_confirmed | 下单 | ordered |
| ordered | 区域确认 | area_confirmed |
| area_confirmed | 完成 | end |
| valid | 发起取消申请 | cancel_applied |
| cancel_applied | 取消审批通过 | cancel_approved |
| 任一设计流程状态 | 终止 | terminated |

### 排查SQL

```sql
-- 查询经销商设计点将申请
SELECT
  da.APPLY_CODE    AS 申请编码,
  da.DESIGN_NAME   AS 设计名称,
  da.LECTURER_NAME AS 设计师,
  da.ORDER_LECTURE_STATE AS 点将状态,
  da.DESIGN_STATE  AS 设计状态,
  da.APPROVAL_STATE AS 审核状态,
  da.FEEDBACK_NUMBER AS 反馈次数,
  da.RELATION_APPLY_CODE AS 关联单据
FROM DESIGN_APPLY da
ORDER BY da.CREATE_DATE DESC;

-- 查询图纸反馈记录
SELECT
  dd.APPLY_CODE    AS 申请编码,
  dd.FILE_NAME     AS 文件名称,
  dd.DRAWING_TYPE  AS 图纸类型,
  dd.FEEDBACK_RESULT AS 反馈结果,
  dd.FEEDBACK_COMMENTS AS 反馈意见,
  TO_CHAR(dd.OPERATION_TIME, 'YYYY-MM-DD HH24:MI:SS') AS 反馈时间
FROM DESIGN_DRAWING dd
WHERE dd.FEEDBACK_RESULT IS NOT NULL
ORDER BY dd.OPERATION_TIME DESC;

-- 查询效果图补申申请
SELECT
  da.APPLY_CODE    AS 申请编码,
  da.RELATION_APPLY_CODE AS 关联原申请,
  da.DESIGN_NAME   AS 设计名称,
  da.LECTURER_NAME AS 设计师,
  da.APPROVAL_STATE AS 审核状态
FROM DESIGN_APPLY da
WHERE da.APPLY_TYPE = 'supplement';

-- 查询待图纸确认的申请
SELECT
  da.APPLY_CODE    AS 申请编码,
  da.DESIGN_NAME   AS 设计名称,
  da.SETTLEMENT_CONFIRM_STATE AS 结算确认状态
FROM DESIGN_APPLY da
WHERE da.SETTLEMENT_CONFIRM_STATE = 'to_be_confirm';

-- 查询设计师饱和度
SELECT
  da.LECTURER_NAME AS 设计师,
  COUNT(*)         AS 服务中单据数
FROM DESIGN_APPLY da
WHERE da.ORDER_LECTURE_STATE IN ('valid', 'designing', 'drawing_uploaded')
GROUP BY da.LECTURER_NAME;
```

### 常见问题

**Q1：经销商看不到自己发起的设计点将记录？**
A：检查该经销商是否正确关联当前登录用户，确认DEALER_CODE与当前登录用户关联的经销商一致。

**Q2：设计师点将的审批状态如何查看？**
A：在详情页中可查看完整审批链路，包括讲师审批、门店审批等各环节状态。

**Q3：详情页type参数有什么作用？**
A：`type`参数用于区分详情页的展示模式，不同模式可能展示不同的操作按钮和字段。

**Q4：申请点将弹窗无设计师数据？**
A：检查campApi.lecturerList接口，pageType=design参数是否正确传递。

**Q5：下载图纸弹窗无图纸数据？**
A：检查downloadDrawing接口返回，确认设计图已上传。

**Q6：图纸反馈失败？**
A：检查feedback接口，确认feedbackComments填写。

**Q7：面积确认无法签合同？**
A：检查approvalState是否为fdd_in_approval。

**Q8：效果图补申跳转失败？**
A：检查applyCode是否存在，详情页supplement路由配置。
