# 点将管理-单店培训点将管理-单店点将管理

> 后端代码位于mbo-business微服务（源码未包含在当前源码目录下），以下逻辑基于前端API定义和页面组件代码梳理。

## 业务流程

### 业务流程图

```text
经销商发起点将申请(单店培训)
        |
        v
单店点将管理列表(本页面) ──pageType=manage──→ 查看申请/查看流程
        |
        | pageType=approval
        v
单店点将审批 ──→ 选择一条申请 ──→ 审批通过/驳回
        |                          |
        |                          ├──→ 审批通过：推送OA/法大大/CRM
        |                          └──→ 审批驳回：流程终止
        v
点将执行(单店点将执行页面) ──→ 记录实际点将天数
        |
        v
结束确认 ──→ 经销商确认结束 ──→ 流程归档
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| 经销商单店点将申请 | 数据依赖 | 经销商在"经销商点将-单店点将"页面发起点将申请，生成申请数据 | 经销商已提交单店培训点将申请 |
| HZERO权限服务 | 配置依赖 | 提供页面权限校验、按钮权限校验 | 用户已登录且分配了对应角色 |
| HZERO值集服务 | 配置依赖 | 提供审核状态、点将状态等值集数据 | 值集MBO.APPLY_APPROVAL_STATE等已配置 |
| 讲师档案管理 | 数据依赖 | 提供讲师信息用于点将申请展示 | 讲师档案已创建且状态正常 |
| 工作流引擎 | 配置依赖 | 提供审批流程驱动 | 内置审批trainApplyApproval已配置 |
| 组织主档 | 数据依赖 | 提供组织信息用于权限过滤 | 组织主档已维护 |

### 下游影响

- 影响1：单店点将执行
  - 审批通过后申请进入执行环节，状态流转至执行中

- 影响2：CRM订单系统
  - 审批通过后推送CRM创建订单，回写CRM单号

- 影响3：OA审批系统
  - 审批通过后推送OA流程，记录OA审批结果

- 影响4：法大大电子签约
  - 审批通过后推送法大大生成结算确认书

- 影响5：讲师排期占用
  - 审批通过后占用讲师档期，防止排期冲突

- 影响6：讲师饱和度
  - 审批通过后计入讲师饱和度统计

## 重点逻辑

### 重点逻辑1：审批流程驱动

- **业务意义**：确保讲师资源分配经过审批确认，避免随意占用稀缺讲师资源

- **具体逻辑描述**

  - 第1点：单店培训点将仅涉及1个内置审批流程trainApplyApproval

  - 第2点：单店点将以门店为维度，每条申请关联一个具体门店

  - 第3点：提交时校验讲师在申请时间段内是否已有排期冲突

  - 第4点：审批状态变更自动更新申请主状态

### 重点逻辑2：pageType页面类型切换

- **业务意义**：同一页面复用管理和审批两种视图，通过参数区分功能模式

- **具体逻辑描述**

  - 第1点：manage模式为管理视图，可查看申请详情，不显示审批按钮

  - 第2点：approval模式为审批视图，显示审批按钮，可进行审批通过/驳回操作

  - 第3点：切换时通过onPageTypeChange更新pageType，并重新查询列表数据

  - 第4点：查询接口pageType参数默认为manage

### 重点逻辑3：审批弹窗逻辑

- **业务意义**：规范审批操作流程，确保审批记录完整可追溯

- **具体逻辑描述**

  - 第1点：审批人自动填充当前登录用户真实姓名，不可编辑

  - 第2点：审批时间自动填充当前时间，不可编辑

  - 第3点：签订人仅在pageType=approval时显示，通过signerDS根据法人主体动态查询签订人列表，审批通过时必填

  - 第4点：审批意见必填，TextArea组件

  - 第5点：审批结果为approved（通过）或reject（驳回），通过approvalResult字段传递

  - 第6点：申请类型applyTypeOne=train（培训），applyTypeTwo=apply（申请）

### 选择弹窗

#### 弹窗1：审批弹窗（单选）

| 入参 | | | | 数据范围 |
|------|------|------|------|---------|
| 字段名 | 中文名 | 释义 | 示例 | |
| applyCode | 申请编码 | 待审批的申请编码 | TA20260101001 | 当前列表选中的申请 |
| approvalResult | 审批结果 | 通过或驳回 | approved | approved/reject |
| signerId | 签订人ID | 审批通过时必填 | 10001 | 根据法人主体动态查询的可选签订人 |

> 审批弹窗包含审批意见Form和申请详情展示，审批通过时需选择签订人

> 查询SQL（签订人列表，根据法人主体查询）：

```sql
SELECT
  su.USER_ID   AS 签订人ID,
  su.REAL_NAME AS 签订人姓名,
  su.PHONE     AS 签订人电话
FROM SYS_USER su
WHERE su.ORG_ID = :orgId
  AND su.STATUS = 'active'
ORDER BY su.REAL_NAME;
```

#### 弹窗2：流程摘要弹窗（单选）

| 入参 | | | | 数据范围 |
|------|------|------|------|---------|
| 字段名 | 中文名 | 释义 | 示例 | |
| applyCode | 申请编码 | 待查看流程的申请编码 | TA20260101001 | 当前列表选中的申请 |

> 流程摘要弹窗通过ProcessDetail组件展示流程审批历史，弹窗宽度1000px，仅显示关闭按钮

> 查询SQL（流程审批历史，工作流引擎查询）：

```sql
SELECT
  ph.NODE_NAME     AS 审批节点,
  ph.APPROVER_NAME AS 审批人,
  ph.APPROVE_RESULT AS 审批结果,
  ph.APPROVE_COMMENT AS 审批意见,
  TO_CHAR(ph.APPROVE_TIME, 'YYYY-MM-DD HH24:MI:SS') AS 审批时间
FROM PROCESS_HISTORY ph
WHERE ph.BUSINESS_CODE = :applyCode
ORDER BY ph.APPROVE_TIME;
```

#### 按钮1：查看申请（列表页）

- **触发条件**：选择一条数据，始终显示
- **执行逻辑**：
  - 第1点：通过openTab打开新标签页
  - 第2点：跳转路由为/general/distributorGeneral/distributorGeneralSingleStore/detail/{applyCode}/view
  - 第3点：参数isCrm在pageType=manage时为true，否则为false（控制详情页是否显示CRM相关操作）
- **接口调用**：无，仅前端页面跳转
- **排查SQL**：

```sql
SELECT * FROM TRAIN_APPLY WHERE APPLY_CODE = :applyCode;
```

#### 按钮2：审批（列表页）

- **触发条件**：pageType不等于manage且选择一条数据
- **执行逻辑**：
  - 第1点：打开审批弹窗，填写审批意见、签订人
  - 第2点：校验审批意见必填，审批通过时签订人必填
  - 第3点：调用审批接口提交审批结果
  - 第4点：审批通过后推送OA/法大大/CRM
- **接口调用**：POST /mlt/trainApply/trainApplyApproval
- **排查SQL**：

```sql
SELECT
  ta.APPLY_CODE,
  ta.APPROVAL_STATE,
  ta.ORDER_LECTURE_STATE
FROM TRAIN_APPLY ta
WHERE ta.APPLY_CODE = :applyCode;
```

### 保存校验

无保存功能（管理端只查看+审批，保存由经销商端完成）。

### 提交校验

- 校验1：审批意见必填 —— 确保审批记录有完整的审批意见

  - 详细逻辑

    - 第1点：提交审批前执行applyApprovalFormDS.validate()校验

    - 第2点：审批意见字段为必填，TextArea组件

  - 系统体现：toast提醒"审批意见不能为空"

  - 排查SQL：

    ```sql
    SELECT APPLY_CODE, APPROVAL_COMMENTS
    FROM TRAIN_APPLY
    WHERE APPLY_CODE = :applyCode
      AND (APPROVAL_COMMENTS IS NULL OR APPROVAL_COMMENTS = '');
    ```

- 校验2：审批通过时签订人必填 —— 确保审批通过后有签订人用于后续合同签署

  - 详细逻辑

    - 第1点：当approvalResult为approved时，签订人字段必填

    - 第2点：签订人通过signerDS根据法人主体动态查询

  - 系统体现：toast提醒"签订人不能为空"

  - 排查SQL：

    ```sql
    SELECT APPLY_CODE, SIGNER_ID, SIGNER_NAME
    FROM TRAIN_APPLY
    WHERE APPLY_CODE = :applyCode
      AND APPROVAL_STATE = 'approved'
      AND SIGNER_ID IS NULL;
    ```

### 状态机

#### 状态机流转图

```text
新建(NEW) → 提交(SUBMITTED) → 审批通过(APPROVED) → 生效(EFFECTIVE) → 执行中(EXECUTING) → 已完成(COMPLETED)
                |
                └→ 审批驳回(REJECTED) → 可修改重新提交
```

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|------------|
| NEW | 新建 | 编辑、删除、提交 |
| SUBMITTED | 已提交 | 审批通过、审批驳回、取消 |
| APPROVED | 审批通过 | 推送OA/FDD/CRM |
| REJECTED | 审批驳回 | 修改后重新提交 |
| EFFECTIVE | 已生效 | 转入执行 |
| EXECUTING | 执行中 | 更新进度、结束执行 |
| COMPLETED | 已完成 | 查看 |

- **触发条件**：点击查看申请/审批按钮前未选择列表行或选择多行
- **逻辑分析**：前端校验选中行数量=1，不满足时toast提示
- **排查SQL**：
  ```sql
  SELECT ta.APPLY_CODE AS 申请编码, ta.TRAIN_NAME AS 培训名称,
         ta.APPROVAL_STATE AS 审核状态, ta.ORDER_LECTURE_STATE AS 点将状态
  FROM TRAIN_APPLY ta
  WHERE ta.APPLY_TYPE_ONE = 'train' AND ta.APPLY_TYPE_TWO = 'apply'
  ORDER BY ta.CREATE_DATE DESC;
  ```

#### 报错2：请求失败
- **触发条件**：查询/审批接口调用时
- **逻辑分析**：后端 mbo-business 微服务异常或网络错误，HTTP 状态码非 2xx
- **排查SQL**：
  ```sql
  SELECT ta.APPLY7S 申请编码, ta.ERROR_INFO AS 异常信息
  FROM TRAIN_APPLY ta
  WHERE ta.ERROR_INFO IS NOT NULL;
  ```

#### 报错3：审批意见不能为空
- **触发条件**：提交审批时未填写审批意见
- **逻辑分析**：前端 applyApprovalFormDS.validate() 校验 APPROVAL_COMMENTS 必填，TextArea 组件
- **排查SQL**：

  SELECT ta.APPLY_CODE AS 申请编码, ta.APPROVAL_COMMENTS AS 审批意见
  FROM TRAIN_APPLY ta
  WHERE ta.APPLY_CODE = :applyCode
    AND (ta.APPROVAL_COMMENTS IS NULL OR ta.APPROVAL_COMMENTS = '');
  ```

#### 报错4：签订人不能为空
- **触发条件**：审批通过时未选择签订人
- **逻辑分析**：approvalResult=approved 时 signerId 必填，签订人通过 signerDS 根据法人主体动态查询
- **排查SQL**：

  SELECT ta.APPLY_CODE AS 申请编码, ta.SIGNER_ID AS 签订人ID, ta.SIGNER_NAME AS 签订人姓名
  FROM TRAIN_APPLY ta
  WHERE ta.APPLY_CODE = :applyCode
    AND ta.APPROVAL_STATE = 'approved'
    AND ta.SIGNER_ID IS NULL;
  ```

#### 报错5：数据校验失败
- **触发条件**：审批提交时表单校验未通过
- **逻辑分析**：前端表单校验（审批意见、签订人等必填项）未通过时阻止提交
- **排查SQL**：
  ```sql
  SELECT ta.APPLY_CODE AS 申请编码, ta.APPROVAL_COMMENTS AS 审批意见,
         ta.SIGNER_NAME AS 签订人, ta.APPROVAL_STATE AS 审核状态
  FROM TRAIN_APPLY ta
  WHERE ta.APPROVAL_STATE = 'approving'
    AND (ta.APPROVAL_COMMENTS IS NULL OR ta.APPROVAL_COMMENTS = ''
         OR (ta.SIGNER_ID IS NULL));
  ```

#### 报错6：网络异常/接口超时
- **触发条件**：任意接口调用时，网络中断或接口响应超过 axios timeout 配置
- **逻辑分析**：前端 axios 请求未收到响应或响应超时，触发 catch 回调统一提示"请求失败"。常见根因：网络中断、mbo-business 服务假死、数据库慢查询、工作流引擎响应慢等。需检查网络连通性、后端服务负载、数据库性能
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, TRAIN_NAME AS 培训名称,
         ORDER_LECTURE_STATE AS 点将状态,
         TO_CHAR(LAST_UPDATE_DATE,'YYYY-MM-DD HH24:MI:SS') AS 最后更新时间
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'train' AND APPLY_TYPE_TWO = 'apply'
    AND LAST_UPDATE_DATE >= SYSDATE - 1
  ORDER BY LAST_UPDATE_DATE DESC;
  ```

#### 报错7：权限不足
- **触发条件**：点击查看申请、审批等按钮时，当前用户无对应 permissionList 权限码
- **逻辑分析**：前端 Button 组件通过 permissionList 配置权限码，HZERO 框架校验当前用户角色是否包含该权限码，未包含则按钮不可见或禁用。若强制调用接口，后端也会校验权限返回403。需联系管理员配置对应角色权限
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名, R.ROLE_NAME AS 角色名, P.PERMISSION_CODE AS 权限码
  FROM SYS_USER U
  LEFT JOIN SYS_USER_ROLE UR ON U.USER_ID = UR.USER_ID
  LEFT JOIN SYS_ROLE R ON UR.ROLE_ID = R.ROLE_ID
  LEFT JOIN SYS_ROLE_PERMISSION RP ON R.ROLE_ID = RP.ROLE_ID
  LEFT JOIN SYS_PERMISSION P ON RP.PERMISSION_ID = P.PERMISSION_ID
  WHERE P.PERMISSION_CODE LIKE '%single_store_general_manage%' ORDER BY U.USER_NAME;
  ```

#### 报错8：数据不存在
- **触发条件**：查看申请、审批等操作时，接口返回数据为空或申请编码不存在
- **逻辑分析**：前端通过 applyCode 调用详情接口，后端查询 TRAIN_APPLY 表无对应记录或记录已逻辑删除，返回空数据。常见根因：申请编码错误、申请已被删除、跨租户查询、数据权限隔离等。需检查 APPLY_CODE 有效性及数据权限
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, TRAIN_NAME AS 培训名称,
         ORDER_LECTURE_STATE AS 点将状态, DELETE_FLAG AS 删除标记
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'train' AND APPLY_TYPE_TWO = 'apply'
    AND (DELETE_FLAG = 'Y' OR APPLY_CODE IS NULL);
  ```

#### 报错9：状态不允许操作
- **触发条件**：点击审批按钮时，申请状态不在允许操作的状态范围内
- **逻辑分析**：后端校验申请状态机，如审批要求 APPROVAL_STATE 为 to_be_approval。状态不匹配时后端返回业务异常，前端提示后端返回的 message。需检查申请当前状态及操作流程
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, TRAIN_NAME AS 培训名称,
         ORDER_LECTURE_STATE AS 点将状态, APPROVAL_STATE AS 审核状态,
         ERROR_INFO AS 异常问题
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'train' AND APPLY_TYPE_TWO = 'apply'
    AND APPROVAL_STATE NOT IN ('to_be_approval','approved','reject')
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错10：值集数据不显示
- **触发条件**：查询条件或列表中点将状态、审核状态等下拉选项为空
- **逻辑分析**：前端通过 lookupCode 查询值集 MBO.APPLY_APPROVAL_STATE、MBO.ORDER_LECTURE_STATE 等，值集未配置或未启用则下拉选项为空。需在值集管理页面配置对应值集
- **排查SQL**：
  ```sql
  SELECT LOOKUP_CODE AS 值集编码, LOOKUP_VALUE_CODE AS 值编码,
         LOOKUP_VALUE_NAME AS 值名称, ENABLE_FLAG AS 启用标记
  FROM SYS_LOOKUP_VALUE
  WHERE LOOKUP_CODE IN ('MBO.APPLY_APPROVAL_STATE','MBO.ORDER_LECTURE_STATE','MBO.CANCEL_APPROVAL_STATE')
    AND ENABLE_FLAG = 'N' ORDER BY LOOKUP_CODE;
  ```

#### 报错11：审批人不能为空
- **触发条件**：提交审批时，前端从 getCurrentUser().realName 取审批人姓名为空
- **逻辑分析**：前端审批弹窗 beforeOpen 阶段设置 approvalUserName 为 userInfo.realName，若用户未登录或登录态失效导致 realName 为空，则审批人字段为空。需检查用户登录态、token 是否过期、用户信息接口是否正常
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名, U.REAL_NAME AS 真实姓名,
         U.LOGIN_FLAG AS 登录标记, U.STATUS_CODE AS 状态
  FROM SYS_USER U
  WHERE U.REAL_NAME IS NULL OR U.STATUS_CODE <> 'ACTIVE';
  ```

### 常见问题

- 问题1：审批通过后CRM单号为空
  - 原因：推送CRM失败或CRM系统未返回订单号，排查SQL：SELECT APPLY_CODE, CRM_ORDER_CODE, ERROR_INFO FROM TRAIN_APPLY WHERE APPLY_CODE = :applyCode AND CRM_ORDER_CODE IS NULL;
  - 解决思路：检查ERROR_INFO字段是否有异常信息，尝试重新同步CRM

- 问题2：讲师排期冲突导致提交失败
  - 原因：所点讲师在申请时间段内已有排期，排查SQL：SELECT * FROM MA_LECTURER_SCHEDULE WHERE LECTURER_CODE = :lecturerCode AND ((START_DATE <= :preEndDate AND END_DATE >= :preStartDate))
  - 解决思路：调整培训时间或更换讲师
