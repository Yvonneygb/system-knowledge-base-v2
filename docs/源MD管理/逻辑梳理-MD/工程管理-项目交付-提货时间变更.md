### 流程说明

1. **查询阶段**：用户选择要货订单后，系统查询该订单下所有符合条件的紧急要货行（接口成功、有预占数量、库存有效期未过期、无待审批延期申请）
2. **变更阶段**：用户为每行填写新提货时间后提交，系统逐行处理
3. **推送ERP**：对有效行调用ERP接口（PickupDateChangeIntf）推送提货时间变更，ERP计算新的库存保留有效期并返回
4. **本地更新**：ERP成功后更新紧急要货行提货时间/有效期至、库存保留记录有效期至、写入变更历史记录
5. **即时操作**：无审批节点，执行即生效

## 重点逻辑

### 重点逻辑1：要货行查询过滤条件

- **业务意义**：确保仅对需要变更且可变更的行进行操作，避免对已完成或不可变更行误操作
- **具体逻辑描述**：
  1. 仅查询接口调用成功的行（`INTF_RESULT = 'S'`），排除ERP未成功的行
  2. 仅查询有预占数量的行（`PRE_RESERVED_QTY > 0`），已全部保留成功的行无需变更
  3. 库存保留有效期需大于当天（`Trunc(MAX(VALID_DATE)) > Trunc(sysdate)`），已过期的行不展示
  4. 排除已超期的行（`IS_OVERDUE <> 2`）
  5. 排除有待审批延期申请的行（NOT EXISTS `EPM_URGENT_EXTEND`中`STAT <> 5`的记录）

### 重点逻辑2：预占数量校验

- **业务意义**：只有存在预占数量的行才需要变更提货时间，已全部保留成功的行无需变更
- **具体逻辑描述**：
  1. 提交时检查每行的`preReservedQty`（预占数量），如果≤0则标记为"不处理"
  2. 不处理的行设置`processMessage = "数量已全部保留成功，无需进行提货时间变更，请知悉"`
  3. 不处理的行不调用ERP接口，直接跳过，不影响其他行处理

### 重点逻辑3：推送ERP执行变更

- **业务意义**：提货时间变更需同步到ERP系统，ERP计算新的库存保留有效期并返回
- **具体逻辑描述**：
  1. 组装`PickupDatePushVO`，包含CRM头ID（`orderid`）、CRM行ID（`ext_sa_out_bill_line_id`）、新提货日期、审批日期（`Trunc(sysdate)`）、有效期参数
  2. 有效期参数从系统参数获取：`pickupDateChangeIntf.sysParamValue()`（`VALIDITY_OF_STOCK_RETENTION`）
  3. 调用`PickupDateChangeIntf`推送ERP（EbsAction-PickupDateChangeList）
  4. ERP返回`PickupDateChangeErpVO`，包含`success`标识、`message`、`effectiveDateTo`（新有效期）
  5. ERP成功时更新紧急要货行和库存记录；失败时仅设置错误状态和消息，不阻断其他行

### 重点逻辑4：本地数据联动更新

- **业务意义**：ERP成功后需同步更新本地三处数据，确保CRM与ERP数据一致
- **具体逻辑描述**：
  1. 更新`EPM_URGENT_ORDER_LINE.PICK_UP_DATE`为新提货时间、`VALID_DATE`为ERP返回的有效期至
  2. 查询该行对应的未释放库存保留记录（`RELEASED_TYPE IS NULL`），批量更新`VALID_DATE`为ERP返回的有效期至
  3. 插入`PICKUP_DATE_CHANGE_LIST`变更历史记录，包含原/新提货时间、当时保留/预占/释放数量快照

### 重点逻辑5：延期申请中行的展示

- **业务意义**：展示正在延期申请中的行，提醒用户这些行不可直接变更提货时间
- **具体逻辑描述**：
  1. `urgentExtendChanges`查询有延期申请且状态非完成（`STAT <> 5`）或延期接口失败（`INTF_RESULT = 'E'`且`IS_CANCEL <> 2`）的行
  2. 这些行单独展示，不与可变更行混在一起

#### 按钮1：查询（查询区）

- **触发条件**：已选择要货订单
- **处理逻辑**：
  1. 调用`GET /v1/{organizationId}/pickup-date-change-lists/verify-data?saOutBillHeadId={id}`
  2. 后端执行`EpmUrgentOrderLineServiceImpl.verifyData`方法
  3. 若`saOutBillHeadId`为空，返回空列表
  4. 否则执行两个查询：
     - `orderLineChanges`：查询可变更的紧急要货行（含过滤条件）
     - `urgentExtendChanges`：查询延期申请中的行
  5. 返回`PickupDateChangeVO`，包含两个列表

#### 按钮2：提交变更（列表页）

- **触发条件**：选中行且已填写新提货时间
- **处理逻辑**：
  1. 调用`POST /v1/{organizationId}/pickup-date-change-lists/push-change-date`，传入`List<EpmUrgentOrderLinePushDTO>`
  2. 后端执行`PickupDateChangeListServiceImpl.pushChangeDate`方法
  3. 批量查询`EPM_URGENT_ORDER_LINE`验证数据存在
  4. 逐行校验预占数量，≤0的行标记"不处理"
  5. 调用`doPickupDate`方法：查询推送数据→获取系统参数→逐行调用ERP接口
  6. ERP成功后更新本地数据（行+库存+历史记录）
  7. 返回各行处理结果

### 保存校验

> 本功能为即时操作型，无独立保存动作，仅提交变更校验。

### 提交校验

- 校验1：紧急要货行数据必须存在 —— 确保变更操作有有效数据
  - **详细逻辑**：根据传入的`urgentOrderLineId`列表批量查询`EPM_URGENT_ORDER_LINE`，如果查询结果为空，抛出异常
  - **系统体现**：`PickupDateChangeListServiceImpl.pushChangeDate`第59-61行，抛出`CommonException("未找到对应的紧急要货行数据")`
  - **排查SQL**：
    ```sql
    SELECT * FROM EPM_URGENT_ORDER_LINE
    WHERE URGENT_ORDER_LINE_ID IN (:urgentOrderLineIds);
    ```

- 校验2：要货行提货时间数据必须存在 —— 确保CRM订单信息可查
  - **详细逻辑**：`queryPushData`查询要货行对应的CRM订单信息（关联`linkcrm.crm_sale_order_item_v`），如果查询结果为空，抛出异常
  - **系统体现**：`PickupDateChangeListServiceImpl.doPickupDate`第84-86行，抛出`CommonException("未找到对应的要货行提货时间数据")`
  - **排查SQL**：
    ```sql
    SELECT el.urgent_order_line_id, el.ext_sa_out_bill_line_id, co.orderid
    FROM EPM_URGENT_ORDER_LINE el
    LEFT JOIN linkcrm.crm_sale_order_item_v co ON el.ext_sa_out_bill_line_id = co.id
    WHERE el.urgent_order_line_id IN (:urgentOrderLineIds);
    ```

- 校验3：预占数量必须大于0 —— 仅预占中的行需要变更
  - **详细逻辑**：`preReservedQty ≤ 0`的行标记为"不处理"，提示"数量已全部保留成功，无需进行提货时间变更，请知悉"，不调用ERP接口
  - **系统体现**：`PickupDateChangeListServiceImpl.pushChangeDate`第64-69行，非阻断性提示，不影响其他行处理
  - **排查SQL**：
    ```sql
    SELECT URGENT_ORDER_LINE_ID, PRE_RESERVED_QTY
    FROM EPM_URGENT_ORDER_LINE
    WHERE URGENT_ORDER_LINE_ID IN (:ids)
    AND PRE_RESERVED_QTY <= 0;
    ```

#### 报错1：紧急要货行数据必须存在
- **触发条件**：提交提货时间变更时，传入的urgentOrderLineId列表批量查询EPM_URGENT_ORDER_LINE结果为空
- **逻辑分析**：提交校验中按urgentOrderLineId列表查询紧急要货行，若结果为空则抛出阻断性报错。需检查行ID有效性
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.URGENT_ORDER_HEAD_ID, euol.ITEM_CODE,
         euol.PRE_RESERVED_QTY, euol.INTF_RESULT, euol.IS_OVERDUE
  FROM EPM_URGENT_ORDER_LINE euol
  WHERE euol.URGENT_ORDER_LINE_ID IN (:urgentOrderLineIdList)
  -- 若返回空，说明传入的行ID不存在
  ```

#### 报错2：要货行提货时间数据必须存在
- **触发条件**：提交提货时间变更时，关联linkcrm.crm_sale_order_item_v查询CRM订单信息为空
- **逻辑分析**：queryPushData方法中按ext_sa_out_bill_line_id关联CRM订单视图，若查询为空则抛出阻断性报错。需检查CRM订单数据
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.EXT_SA_OUT_BILL_LINE_ID,
         csoi.LINE_ID AS CRM行存在性, csoi.PICK_UP_DATE, csoi.VALID_DATE
  FROM EPM_URGENT_ORDER_LINE euol
  LEFT JOIN LINKCRM.CRM_SALE_ORDER_ITEM_V csoi
    ON euol.EXT_SA_OUT_BILL_LINE_ID = csoi.LINE_ID
  WHERE euol.URGENT_ORDER_LINE_ID IN (:urgentOrderLineIdList)
    AND csoi.LINE_ID IS NULL
  -- 查出CRM订单信息不存在的行
  ```

#### 报错3：预占数量必须大于0
- **触发条件**：提交提货时间变更时，行预占数量(PRE_RESERVED_QTY)≤0
- **逻辑分析**：提交校验中检查PRE_RESERVED_QTY>0，≤0的行标记"不处理"，不阻断流程。仅预占中的行需要变更
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.ITEM_CODE, euol.PRE_RESERVED_QTY, euol.INTF_RESULT
  FROM EPM_URGENT_ORDER_LINE euol
  WHERE euol.URGENT_ORDER_LINE_ID IN (:urgentOrderLineIdList)
    AND (euol.PRE_RESERVED_QTY IS NULL OR euol.PRE_RESERVED_QTY <= 0)
  -- 查出预占数量≤0的行(标记为不处理)
  ```

#### 报错4：ERP接口返回失败
- **触发条件**：提交提货时间变更后，ERP接口返回失败(processStatus=E)
- **逻辑分析**：调用ERP接口变更提货时间，若返回失败则设置processStatus=E和processMessage。常见原因：新提货时间不合法、ERP端库存已释放、网络异常。单行失败不影响其他行处理
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.ITEM_CODE, euol.INTF_RESULT, euol.PROCESS_MESSAGE,
         euol.PICK_UP_DATE, euol.VALID_DATE
  FROM EPM_URGENT_ORDER_LINE euol
  WHERE euol.URGENT_ORDER_LINE_ID IN (:urgentOrderLineIdList)
    AND euol.INTF_RESULT = 'E'
  -- 查出ERP处理失败的行及错误信息
  ```

#### 报错5：延期申请中的行不可直接变更
- **触发条件**：查询紧急要货行时，行正在延期申请流程中(STAT<>5)或延期接口失败(INTF_RESULT='E'且IS_CANCEL<>2)
- **逻辑分析**：查询时urgentExtendChanges查询有延期申请且状态非完成或延期接口失败的行，单独展示在"延期申请中行"列表，提醒用户不可直接变更。需先完成或处理延期申请
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.ITEM_CODE, euol.STAT, euol.INTF_RESULT, euol.IS_CANCEL
  FROM EPM_URGENT_ORDER_LINE euol
  WHERE euol.URGENT_ORDER_LINE_ID IN (:urgentOrderLineIdList)
    AND (euol.STAT <> 5 OR (euol.INTF_RESULT = 'E' AND euol.IS_CANCEL <> 2))
  -- 查出延期申请中的行
  ```

**Q1：为什么某些行提示"数量已全部保留成功，无需进行提货时间变更"？**
A：该行的预占数量（`PRE_RESERVED_QTY`）≤ 0，表示数量已全部保留成功，无需再变更提货时间。系统自动标记为"不处理"，不影响其他行。

**Q2：提货时间变更失败可能的原因？**
A：ERP接口返回失败，常见原因包括：新提货时间不合法、ERP端库存已释放、网络异常等。可查看返回的`processMessage`获取详细错误信息。单行失败不影响其他行处理。

**Q3：提货时间变更后哪些数据会被更新？**
A：三处数据更新：(1) `EPM_URGENT_ORDER_LINE`的`PICK_UP_DATE`和`VALID_DATE`；(2) `EPM_URGENT_ORDER_LINE_STOCK`中未释放记录的`VALID_DATE`；(3) 新增`PICKUP_DATE_CHANGE_LIST`变更历史记录。

**Q4：为什么查询不到某些紧急要货行？**
A：查询有多个过滤条件：接口必须成功（`INTF_RESULT = 'S'`）、预占数量必须大于0、库存有效期必须大于当天、未超期（`IS_OVERDUE <> 2`）、无待审批延期申请。任一条件不满足的行不会展示。

**Q5：延期申请中的行为什么单独展示？**
A：这些行正在延期申请流程中（`STAT <> 5`）或延期接口失败（`INTF_RESULT = 'E'`），不能直接变更提货时间，需先完成或处理延期申请。
