# 工程管理-项目合同-自营工程合同

> 本页面为低代码页面(hlod)，无独立前端源码，基于后端API梳理。后端与经销商工程合同共用EpmProjectContractController（API: `/v1/{organizationId}/epm-project-contracts`）和ContractController（API: `/v1/{organizationId}/contracts/`），通过contractType=1区分自营合同。validContractMode方法执行自营特有校验。

## 业务流程

```
用户进入自营工程合同列表页面
  → 填写查询条件（合同编码、合同名称、客户、项目等）
  → 调用合同列表接口（GET /contracts/contract-list，contractType=1）
  → 查看合同详情（GET /contracts/get-contract-detail）
  → 新增合同：选择报备项目弹窗（GET /contracts/get-project-data）
    → 自营合同选择战略项目的单体项目时，调用do-strategic-projects带出数据
    → 选择交易公司/开票单位（GET /contracts/trading-company-customer，autotrophyFlag=999，tradingScope=28）
    → 选择产品/引用政策产品（POST /contracts/get-discount-policy）
    → 获取折扣率（POST /contracts/std-discount）
    → 保存合同（POST /epm-project-contracts/save-data）
    → 保存并提交工作流（POST /epm-project-contracts/save-data-submit）
  → 合同提交审批流程（POST /epm-project-contracts/do-Contract-Check）
  → 审批通过后自动更新项目阶段（doContractCheck → doMotionUpdate）
  → 审批拒绝/驳回（wfComplete → wfChangeUpdate）
```

## 重点逻辑

### 重点逻辑1：与经销商工程合同共用后端代码

- **业务意义**：自营合同和经销商合同共用EPM_PROJECT_CONTRACT表和后端ServiceImpl，通过contractType区分，减少重复代码
- **具体逻辑描述**：
  - 1、自营合同contractType=1(直销)，经销商合同contractType=2(经销)
  - 2、列表查询固定传参contractType=1，仅展示自营合同
  - 3、交易公司LOV传入autotrophyFlag=999和tradingScope=28筛选自营范围交易公司
  - 4、saveOrUpdate方法中，contractType=1时根据客户分类(customerClass)自动设置操作模式(contractMode)

### 重点逻辑2：操作模式校验（自营特有）

- **业务意义**：自营合同必须配置操作模式，且操作模式必须与客户分类匹配
- **具体逻辑描述**：
  - 1、validContractMode方法仅对contractType=1且非家装(isHome!=2)的合同执行校验
  - 2、查询客户组织(CustomerOrg)获取customerClass，为空则报错"自营工程:经销商客户类型不能为空，请先维护"
  - 3、contractMode为空则报错"自营工程:操作模式不能为空，请先维护"
  - 4、customerClass=1(内部用户)时，contractMode必须为1(自营工程)，否则报错
  - 5、customerClass=2(外部用户)时，contractMode必须为2(经销商服务)，否则报错

### 重点逻辑3：签收方式（自营特有）

- **业务意义**：自营合同需配置签收方式，决定签收流程和ERP推送行为
- **具体逻辑描述**：
  - 1、签收方式1=签收（仅签收流程），签收方式2=签收+验收（双重流程）
  - 2、当signWay=2时，财务签收审核后不推送ERP
  - 3、validContractMode方法校验signWay不能为空，报错"签收方式不能为空"

### 重点逻辑4：审批流程按区域区分

- **业务意义**：不同区域的自营工程合同使用不同的审批流程，实现差异化审核
- **具体逻辑描述**：
  - 1、东区使用SUB_CONTRACT_ZYSGCHT_EAST
  - 2、西区使用SUB_CONTRACT_ZYSGCHT_WEST
  - 3、南区使用SUB_CONTRACT_ZYSGCHT_SOUTH
  - 4、北区使用SUB_CONTRACT_ZYSGCHT_NORTH
  - 5、审批标识使用getSelfAuditFlag(区别于经销商的getAuditFlag)
  - 6、非定制且住贸常规项目时设置customZmFlag变量(getselfCustomZmFlag)

### 重点逻辑5：战略项目关联

- **业务意义**：自营合同选择战略项目的单体项目时，自动带出战略项目相关数据
- **具体逻辑描述**：
  - 1、自营合同选择战略项目的单体项目时，调用do-strategic-projects接口带出数据
  - 2、parameterCompletion方法从项目(EpmProject)强制写回战略报备信息到合同
  - 3、战略协议(isFrame=2)无需维护折扣单

### 重点逻辑6：纯定制合同处理

- **业务意义**：纯定制合同不要求维护产品清单，简化操作流程
- **具体逻辑描述**：
  - 1、isCustom=2时为纯定制合同，不要求维护产品清单信息
  - 2、保存时清除折扣相关信息：删除EPM_CONTRACT_ITEM、EPM_DISCOUNT_APPLY_LINE、EPM_DISCOUNT_APPLY_PLAN、EPM_DISCOUNT_APPLY
  - 3、非纯定制时，产品清单数据保存到EPM_CONTRACT_ITEM表，折扣信息保存到EPM_DISCOUNT_APPLY表

### 保存校验

- 校验1：合同名称不能为空 —— 确保合同有名称标识
  - **详细逻辑**：checkSaveData方法校验contractName非空
  - **系统体现**：保存时后端校验，抛出"合同名称不能为空"
  - **排查SQL**：`SELECT CONTRACT_NAME FROM EPM_PROJECT_CONTRACT WHERE CONTRACT_ID = #{contractId}`

- 校验2：合同名称长度不超过80 —— 防止名称过长
  - **详细逻辑**：contractName.length() > 80时报错
  - **系统体现**：保存时后端校验，抛出"合同名称过程过长，请控制长度"

- 校验3：必填内容校验 —— 确保关键信息完整
  - **详细逻辑**：contractName、tradingCompanyName、billingUnitName均不能为空
  - **系统体现**：保存时后端校验，抛出"有必填内容未填写，请填写后再保存"

- 校验4：订单产品线不能为空 —— 非定制合同必须维护产品线
  - **详细逻辑**：isCustom!=2时，epmDiscountApplyDTO.orderPdtLine不能为空或0
  - **系统体现**：保存时后端校验，抛出"订单产品线不能为空，请维护订单产品线！"

- 校验5：经销商客户类型不能为空 —— 自营合同特有校验
  - **详细逻辑**：validContractMode方法查询CustomerOrg，customerClass为空则报错
  - **系统体现**：保存时后端校验，抛出"自营工程:经销商客户类型不能为空，请先维护"
  - **排查SQL**：`SELECT CUSTOMER_CLASS FROM CUSTOMER_ORG WHERE CUSTOMER_ID = #{customerId}`

- 校验6：操作模式不能为空 —— 自营合同特有校验
  - **详细逻辑**：contractMode为空则报错
  - **系统体现**：保存时后端校验，抛出"自营工程:操作模式不能为空，请先维护"

- 校验7：操作模式与客户分类匹配 —— 自营合同核心校验
  - **详细逻辑**：customerClass=1(内部用户)时contractMode必须为1；customerClass=2(外部用户)时contractMode必须为2
  - **系统体现**：保存时后端校验，抛出"经销商客户分类为【内部用户】，对应的合同操作模式只能为【自营工程】"或"经销商客户分类为【外部用户】，对应的合同操作模式只能为【经销商服务】"

### 提交校验

- 校验1：合同未审核 —— 防止重复提交
  - **详细逻辑**：doCheckMotionChange方法校验hzApproveStatus不等于APPROVED
  - **系统体现**：提交时后端校验，抛出"该单据已经审核"
  - **排查SQL**：`SELECT HZ_APPROVE_STATUS FROM EPM_PROJECT_CONTRACT WHERE CONTRACT_ID = #{contractId}`

- 校验2：产品信息已维护 —— 非定制合同必须有产品清单
  - **详细逻辑**：isCustom!=2时，查询EPM_CONTRACT_ITEM count<1则报错
  - **系统体现**：doCheckMotionChange方法校验，抛出"请先维护产品信息，流程失败!"
  - **排查SQL**：`SELECT COUNT(*) FROM EPM_CONTRACT_ITEM WHERE CONTRACT_ID = #{contractId}`

- 校验3：折扣类型已维护 —— 非定制合同必须有折扣类型
  - **详细逻辑**：isCustom!=2时，查询EPM_DISCOUNT_APPLY为null则报错
  - **系统体现**：doCheckMotionChange方法校验，抛出"请先维护折扣类型，流程失败!"
  - **排查SQL**：`SELECT * FROM EPM_DISCOUNT_APPLY WHERE CONTRACT_ID = #{contractId}`

- 校验4：合同数据完整性 —— 提交前综合校验
  - **详细逻辑**：validationService.validateAll校验合同所有数据
  - **系统体现**：saveDataSubmit方法中调用，校验不通过则不启动流程

### 状态机

#### 合同审批状态（HZ_APPROVE_STATUS）

```text
┌──────────┐  提交   ┌──────────┐  审批通过  ┌──────────┐
│   NEW    │ ──────→ │   RUN    │ ────────→ │ APPROVED │
│ (新建)   │         │ (审批中) │           │(已生效)  │
└──────────┘         └────┬─────┘           └──────────┘
                          │
                    审批拒绝/驳回
                          │
              ┌───────────┴──────────┐
              │                      │
        ┌─────▼─────┐          ┌─────▼─────┐
        │ REJECTED  │          │  REBUT   │
        │(审批拒绝) │          │ (已驳回)  │
        └───────────┘          └───────────┘
```

#### 合同有效状态（VALID）

| 状态值 | 说明 |
|--------|------|
| 1 | 未生效 |
| 2 | 已生效 |
| 3 | 已失效 |
| 7 | 失效申请中 |

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|-------------|
| NEW | 新建 | 保存、保存并提交、编辑、删除 |
| RUN | 审批中 | 等待审批结果 |
| APPROVED | 已审批 | 失效、签收 |
| REJECTED | 已驳回 | 保存、保存并提交、编辑 |
| WITHDRAW | 已撤回 | 保存、保存并提交、编辑 |

#### 报错1：合同名称不能为空
- **触发条件**：保存合同时，合同头CONTRACT_NAME字段为空
- **逻辑分析**：在checkSaveData方法中校验，对合同头DTO的contractName属性执行非空判断，若为null或空字符串则抛出阻断性报错。该字段为合同基础标识字段，所有合同类型均需校验
- **排查SQL**：
  ```sql
  SELECT epc.CONTRACT_ID, epc.CONTRACT_CODE, epc.CONTRACT_NAME, epc.CONTRACT_TYPE
  FROM EPM_PROJECT_CONTRACT epc
  WHERE epc.CONTRACT_NAME IS NULL
     OR TRIM(epc.CONTRACT_NAME) = ''
  ```

#### 报错2：合同名称过程过长，请控制长度
- **触发条件**：保存合同时，CONTRACT_NAME字段长度超过80个字符
- **逻辑分析**：在checkSaveData方法中校验contractName长度，数据库列CONTRACT_NAME定义为VARCHAR(80)，若传入字符串长度>80则报错。需缩短合同名称至80字符以内
- **排查SQL**：
  ```sql
  SELECT epc.CONTRACT_ID, epc.CONTRACT_CODE, epc.CONTRACT_NAME, LENGTH(epc.CONTRACT_NAME) AS 名称长度
  FROM EPM_PROJECT_CONTRACT epc
  WHERE LENGTH(epc.CONTRACT_NAME) > 80
  ```

#### 报错3：有必填内容未填写，请填写后再保存
- **触发条件**：保存合同时，contractName、tradingCompanyName、billingUnitName任一为空
- **逻辑分析**：在checkSaveData方法中批量校验必填字段，合同名称(CONTRACT_NAME)、交易公司(TRADING_COMPANY_NAME)、开票单位(BILLING_UNIT_NAME)为自营合同必填项，任一为空即报错。该报错为聚合校验，会提示所有缺失的必填项
- **排查SQL**：
  ```sql
  SELECT epc.CONTRACT_ID, epc.CONTRACT_CODE,
         epc.CONTRACT_NAME, epc.TRADING_COMPANY_NAME, epc.BILLING_UNIT_NAME
  FROM EPM_PROJECT_CONTRACT epc
  WHERE epc.CONTRACT_TYPE = 1
    AND (epc.CONTRACT_NAME IS NULL OR epc.TRADING_COMPANY_NAME IS NULL OR epc.BILLING_UNIT_NAME IS NULL)
  ```

#### 报错4：订单产品线不能为空，请维护订单产品线！
- **触发条件**：保存非纯定制合同(IS_CUSTOM!=2)时，ORDER_PDT_LINE字段为空
- **逻辑分析**：在checkSaveData方法中校验，当合同非纯定制(isCustom!=2)时，订单产品线orderPdtLine不能为空。纯定制合同跳过此校验。产品线用于后续要货订单创建和ERP推送


- **工程自营签收**：合同生效后(VALID=2)，可基于该合同发起签收流程，签收方式由SIGN_WAY决定

## 常见问题FAQ

**Q1: 自营工程合同与经销商工程合同的后端接口是否相同？**
A: 是的，两者共用ContractController和EpmProjectContractController，通过contractType区分(自营=1，经销=2)。自营合同额外执行validContractMode校验操作模式与客户分类的匹配关系。

**Q2: 操作模式如何自动设置？**
A: saveOrUpdate方法中，contractType=1时查询CustomerOrg获取customerClass：customerClass=1(内部用户)自动设置contractMode=1(自营工程)，customerClass=2(外部用户)自动设置contractMode=2(经销商服务)。validContractMode方法校验一致性。

**Q3: 签收方式=2(签收+验收)时ERP未推送？**
A: signWay=2时，财务签收审核后不推送ERP，这是设计行为。处理：确认签收方式配置是否正确，如需推送ERP则签收方式应设为1。

**Q4: 自营合同的审批流程是否统一？**
A: 不是，不同区域的自营工程合同使用不同的审批流程：东区SUB_CONTRACT_ZYSGCHT_EAST，西区SUB_CONTRACT_ZYSGCHT_WEST，南区SUB_CONTRACT_ZYSGCHT_SOUTH，北区SUB_CONTRACT_ZYSGCHT_NORTH。审批标识使用getSelfAuditFlag(区别于经销商的getAuditFlag)。

**Q5: 自营合同有哪些特有必填字段？**
A: validContractMode方法校验的特有必填字段：报备项目编码(projectId)、签收方式(signWay)、合同总额(contractAmt)、签订时间(signedDate)、签订地点(signedLocation)、交易公司(tradingCompanyName)、开票单位(billingUnitId)、操作模式(contractMode)。

**Q6: 自营合同选择战略项目单体项目时有什么特殊处理？**
A: 调用do-strategic-projects接口自动带出战略项目的相关数据，包括项目基础信息、折扣信息等。parameterCompletion方法还会从项目强制写回战略报备信息到合同。

**Q7: 合同审批通过但有效状态未变为"已生效"？**
A: 审批回调wfComplete未正确执行。排查SQL：`SELECT CONTRACT_CODE, VALID, HZ_APPROVE_STATUS, HZ_INSTANCE_ID FROM EPM_PROJECT_CONTRACT WHERE CONTRACT_ID = #{contractId}`。处理：检查HZ_INSTANCE_ID对应的流程实例状态，手动修正VALID=2。
