# 工程管理-项目商机-报备生失效申请

> 本页面为低代码页面(hlod)，无独立前端源码，基于后端API与Entity梳理。报备生失效申请支持失效申请(type=1)和恢复生效申请(type=2)两种类型，共用同一张表，通过type字段区分。

## 业务流程

### 生失效如何流转

创建申请单 → 选择项目 → 填写申请说明 → 保存生成单号 → 提交审批 → 审批通过更新项目状态并推送CRM/ES。

```
用户进入报备生失效申请页面
  → 新建申请单，选择申请类型（type=1失效 / type=2恢复生效）
  → 选择需要失效/生效的项目报备（projectId）
  → 查询上一次失效数据（GET /query-last-disable，type=1）
  → 填写申请说明（失效reason / 恢复生效enableReason）
  → 保存（saveData）生成申请单号：
    → type=1使用编码规则AE.PROJECT_DISABLE_CODE
    → type=2使用编码规则AE.PROJECT_DISABLE_ENABLE_CODE
  → 提交审批，触发工作流（PROJECT_DISABLE_ENABLE_MAIN）
  → 审批通过后执行 wfComplete：
    → type=1失效：EPM_PROJECT.PROJECT_VALID=3，推送CRM validStatus=0，删除ES数据
    → type=2生效：EPM_PROJECT.PROJECT_VALID=2，推送CRM validStatus=1，推送ES数据
```

### 全链路流程图

```
开始 → ★新建申请★ → 选择类型(失效/恢复生效) → 选择项目 → 填写说明 → 保存生成单号
     → 提交工作流 · ⚖审批通过？ → 更新项目状态/推送CRM/同步ES → 结束（拒绝则修改重提）

上游支撑：项目档案(EPM_PROJECT)、项目报备(EPM_REPORT)、经销商档案(CUSTOMER)、编码规则引擎、工作流引擎、CRM系统、ES搜索引擎
下游影响：项目档案有效状态、CRM报备状态、ES搜索索引、项目商机查询
```

### 两种申请类型

- **失效申请(type=1)**：项目不再继续推进时，申请将项目有效状态置为失效(3)，需填写失效原因(reason)，使用编码规则AE.PROJECT_DISABLE_CODE
- **恢复生效申请(type=2)**：失效项目重新需要运作时，申请恢复生效(2)，需填写恢复生效说明(enableReason)，使用编码规则AE.PROJECT_DISABLE_ENABLE_CODE

## 重点逻辑

### 重点逻辑1：失效与恢复生效通过TYPE字段区分

- **业务意义**：失效与恢复生效共用同一张表和同一个服务，通过TYPE字段区分，减少冗余代码
- **具体逻辑描述**：
  - TYPE=1表示报备失效申请，TYPE=2表示报备恢复生效申请
  - 两种类型使用不同的编码规则生成单号：失效使用AE.PROJECT_DISABLE_CODE，恢复生效使用AE.PROJECT_DISABLE_ENABLE_CODE
  - 审批通过后，TYPE=1将PROJECT_VALID更新为3(失效)，TYPE=2更新为2(生效)

### 重点逻辑2：审批通过后多系统联动

- **业务意义**：报备有效状态变更需同步到CRM和ES，确保各系统数据一致
- **具体逻辑描述**：
  - 审批通过后首先更新项目有效状态(PROJECT_VALID)，记录审批人和审批时间
  - 非家装单体报备(monomerType!=2)时，推送报备有效状态到CRM(arrowEbsSdk.indivireportAdd)
  - 单体报备(reportType=1)时，失效删除ES索引(delEsDocByUser)，生效推送ES索引(reportToEs)
  - CRM推送失败仅记录日志(LOGGER.error)，不阻断主流程；ES操作失败同样仅记录日志

### 重点逻辑3：家装单体报备失效不推送CRM

- **业务意义**：家装单体报备失效(monomerType=2)不需要推送到CRM，与工程单体报备区分处理
- **具体逻辑描述**：
  - 当MONOMER_TYPE=2时，跳过CRM推送逻辑
  - 家装单体报备仍会执行项目有效状态更新和ES数据同步(如果reportType=1)

### 重点逻辑4：双编码规则

- **业务意义**：失效和恢复生效使用不同编码规则，便于区分单据类型
- **具体逻辑描述**：
  - saveData中根据type选择编码规则
  - type=1失效：codeRuleBuilder.generateCode(PROJECT_DISABLE_CODE)
  - type=2恢复生效：codeRuleBuilder.generateCode(PROJECT_DISABLE_ENABLE_CODE)

### 重点逻辑5：上一次失效查询

- **业务意义**：避免重复申请，查询项目上一次失效记录供前端参考
- **具体逻辑描述**：
  - queryLastDisable查询EPM_PROJECT_DISABLE中PROJECT_ID匹配且TYPE=1的记录
  - 按LAST_UPDATE_DATE倒序取第一条返回
  - 为空时返回空VO

### saveData保存逻辑

```
入参：List<EpmProjectDisable>
1. 按projDisableId是否为空分为insertList和updateList
2. 遍历insertList生成单号：
   → projDisableCode为空时：
     → type=1失效：codeRuleBuilder.generateCode(PROJECT_DISABLE_CODE)
     → type=2恢复生效：codeRuleBuilder.generateCode(PROJECT_DISABLE_ENABLE_CODE)
3. batchInsertSelective(insertList)
4. batchUpdateByPrimaryKeySelective(updateList)
```

### queryLastDisable逻辑

```
入参：EpmProjectDisableDTO (projectId)
1. 查询EPM_PROJECT_DISABLE中PROJECT_ID=projectId且TYPE=1的记录
2. 按LAST_UPDATE_DATE倒序
3. 为空返回空VO，非空取第一条转为VO返回
```

### wfComplete审批通过回调逻辑

```
入参：WfApproveDTO dto
1. 判断approveResult == APPROVED，不是则return true
2. 查询申请单 epmProjectDisable = selectByPrimaryKey(objId)
3. 查询项目 epmProject = selectByPrimaryKey(projectId)
4. 根据type更新项目有效状态：
   → type=1失效：epmProject.setProjectValid(3)
   → type=2生效：epmProject.setProjectValid(2)
5. updateOptional(epmProject, PROJECT_VALID)
6. 记录审批人auditor=当前用户名，审批时间audittime=now
7. 查询项目报备 EPM_REPORT where PROJECT_ID = projectId
8. 报备为空 → 抛出 CommonException("项目报备数据不存在")
9. monomerType != 2时推送CRM：
   → 查询客户获取shortName
   → 构建推送数据(acctCode/acctName/acctAbbr/orgCode/reportNo/projectName/validStatus)
   → validStatus: type=1→"0"(失效), type=2→"1"(生效)
   → arrowEbsSdk.indivireportAdd(resources)
   → 异常try-catch仅记录日志
10. reportType=1单体报备时操作ES：
    → type=1失效：epmReportService.delEsDocByUser(report) 删除ES文档
    → type=2生效：epmReportService.reportToEs(reportId) 推送ES文档
    → 异常try-catch仅记录日志
11. return true
```

### 保存校验

- 校验1：工程ID非空 —— 申请单必须关联有效的工程项目
  - **详细逻辑**：PROJECT_ID字段标注@NotNull，框架自动校验
  - **系统体现**：Entity注解校验
  - **排查SQL**：`SELECT * FROM EPM_PROJECT_DISABLE WHERE PROJECT_ID IS NULL;`

- 校验2：单体类型非空 —— 必须区分工程单体和家装单体
  - **详细逻辑**：MONOMER_TYPE字段标注@NotNull，框架自动校验
  - **系统体现**：Entity注解校验
  - **排查SQL**：`SELECT * FROM EPM_PROJECT_DISABLE WHERE MONOMER_TYPE IS NULL;`

- 校验3：组织ID非空 —— 单据必须归属正确的组织
  - **详细逻辑**：ORGANIZATION_ID字段标注@NotNull，框架自动校验
  - **系统体现**：Entity注解校验
  - **排查SQL**：`SELECT * FROM EPM_PROJECT_DISABLE WHERE ORGANIZATION_ID IS NULL;`

### 提交校验

- 校验1：项目报备数据必须存在 —— 审批通过后需查询报备信息用于推送CRM和操作ES
  - **详细逻辑**：wfComplete中根据PROJECT_ID查询EPM_REPORT，为空抛出"项目报备数据不存在"
  - **系统体现**：审批通过回调时校验
  - **排查SQL**：`SELECT EPD.PROJECT_ID, EPD.PROJ_DISABLE_CODE FROM EPM_PROJECT_DISABLE EPD LEFT JOIN EPM_REPORT ER ON EPD.PROJECT_ID = ER.PROJECT_ID WHERE ER.REPORT_ID IS NULL;`

### 状态机

```text
┌──────────┐  提交   ┌──────────┐  审批通过  ┌──────────┐
│  新建    │ ──────→ │ 审批中    │ ────────→ │ 审批通过  │
│ (NEW)   │         │ (RUN)   │           │(APPROVED) │
└──────────┘         └────┬─────┘           └──────────┘
      ↑                   │
      │              审批拒绝/退回
      │                   │
      └───────────────────┘
                  │
              (REJECTED)
```

**审批通过后动作**：
- type=1失效：EPM_PROJECT.PROJECT_VALID=3，推送CRM validStatus=0，删除ES数据
- type=2生效：EPM_PROJECT.PROJECT_VALID=2，推送CRM validStatus=1，推送ES数据

## 常见问题FAQ

### Q1: 报备失效申请前为什么要查询上一次失效数据？

避免重复申请，通过queryLastDisable查询该项目上一次失效记录(type=1)，若已有进行中的失效申请则不允许再次发起。

**排查SQL:**
```sql
SELECT * FROM EPM_PROJECT_DISABLE
WHERE PROJECT_ID = #{projectId} AND TYPE = 1
ORDER BY LAST_UPDATE_DATE DESC;
```

### Q2: 失效和恢复生效的区别？

失效(type=1)将项目状态置为3，推送CRM validStatus=0，删除ES数据；恢复生效(type=2)将项目状态置为2，推送CRM validStatus=1，推送ES数据。两者使用不同编码规则。

### Q3: 家装单体报备失效有何特殊处理？

家装单体报备(monomerType=2)不推送CRM，仅更新项目状态和ES数据，因为家装业务线CRM同步逻辑独立。

**排查SQL:**
```sql
SELECT EPD.PROJ_DISABLE_CODE, EPD.MONOMER_TYPE, EPD.TYPE
FROM EPM_PROJECT_DISABLE EPD
WHERE EPD.MONOMER_TYPE = 2 AND EPD.TYPE = 1;
```

### Q4: 审批通过后项目有效状态未变更？

原因是审批结果不是APPROVED，wfComplete中判断approveResult不等于APPROVED时直接返回true，不执行状态更新。

**排查SQL:**
```sql
SELECT EPD.PROJ_DISABLE_CODE, EPD.HZ_APPROVE_STATUS, EP.PROJECT_VALID
FROM EPM_PROJECT_DISABLE EPD
JOIN EPM_PROJECT EP ON EPD.PROJECT_ID = EP.PROJECT_ID
WHERE EPD.PROJ_DISABLE_ID = #{申请单ID};
```

### Q5: 恢复生效申请单号格式与失效申请单号不同？

两种类型使用不同编码规则：失效使用AE.PROJECT_DISABLE_CODE，恢复生效使用AE.PROJECT_DISABLE_ENABLE_CODE。

**排查SQL:**
```sql
SELECT PROJ_DISABLE_CODE, TYPE FROM EPM_PROJECT_DISABLE
WHERE PROJECT_ID = #{projectId}
ORDER BY CREATETIME DESC;
```

### Q6: 审批通过后ES数据未同步？

仅单体报备(reportType=1)才会操作ES数据，战略报备等其他类型不操作ES。

**排查SQL:**
```sql
SELECT EPD.PROJ_DISABLE_CODE, ER.REPORT_TYPE
FROM EPM_PROJECT_DISABLE EPD
JOIN EPM_REPORT ER ON EPD.PROJECT_ID = ER.PROJECT_ID
WHERE EPD.PROJ_DISABLE_ID = #{申请单ID};
```
