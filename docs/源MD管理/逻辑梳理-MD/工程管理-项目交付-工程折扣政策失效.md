### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| 工程折扣政策 | 数据依赖 | 失效必须关联一个已生效的折扣政策 | 政策头valid=2（已生效） |
| 折扣政策项 | 数据依赖 | 失效针对政策下的具体产品项 | 政策项validStat=0（未失效）且未被其他失效申请关联 |
| 编码规则配置 | 配置依赖 | 工程使用编码规则AE.GC_DISCOUNT_POLICY_DISABLED自动生成失效单编码 | 编码规则已配置且生效 |
| 工作流引擎 | 配置依赖 | 流程编码DISCOUNT_POLICY_DISABLED，启动OA审批流程 | 工作流已部署且可用 |
| CRM系统 | 数据依赖 | 专项折扣失效后推送CRM，保持两侧一致 | suitableType=special时推送 |
| OA审批系统 | 配置依赖 | OA多级审核，审批通过后回调更新失效状态 | OA流程配置完成 |

### 下游影响

- 影响1：更新政策项失效状态
  - 审批通过后更新政策项的disabledId和validStat=3，标记为已失效

- 影响2：政策头可能整体失效
  - 全部政策行失效时，政策头valid更新为3（已失效）

- 影响3：影响折扣单创建
  - 失效的政策项不再适用于新的折扣单创建

- 影响4：推送CRM侧政策失效
  - 专项折扣推送CRM，前端价格及时停更

## 重点逻辑

### 重点逻辑1：工程/家装/样品三菜单共用后端代码

- **业务意义**：三个菜单共用同一套后端Controller和ServiceImpl，减少重复代码，通过参数区分业务类型

- **具体逻辑描述**

  - 第1点：列表查询时，前端固定传suitableType参数——工程传normal、家装传special(isMakt=0)、样品传special(isMakt=2)

  - 第2点：编码规则根据关联政策的suitableType和isMakt自动选择——工程用AE.GC_DISCOUNT_POLICY_DISABLED、家装用AE.JZ_DISCOUNT_POLICY_DISABLED、样品用AE.YP_DISCOUNT_POLICY_DISABLED

  - 第3点：审批通过后，通用折扣(suitableType=normal)不推送CRM，专项折扣(suitableType=special)推送CRM

### 重点逻辑2：审批通过后执行失效

- **业务意义**：工作流审批通过是政策失效的生效条件，避免随意停折，确保受控回收

- **具体逻辑描述**

  - 第1点：审批通过后，调用updateVaildByDisabledId将本次失效申请关联的所有政策行validStat更新为3

  - 第2点：查询该政策下所有政策行，过滤掉validStat≠3且不属于本次失效申请的行，如果剩余行数为0则将政策头valid更新为3(全部失效)

  - 第3点：专项折扣推送CRM，逐行调用crmSdkService.policyDisabled接口，传入endFlag=Y、endUser、endTime和policyItemId(CRM行ID)

### 重点逻辑3：保存时政策行与失效申请关联

- **业务意义**：通过关联字段建立失效申请与政策行的对应关系，用于审批通过后定位需要失效的行

- **具体逻辑描述**

  - 第1点：新建时，先insert失效申请头，获取主键ID后，将选中的政策行的discountPolicyDisabledId更新为该ID

  - 第2点：编辑时，先清空该失效申请下所有政策行的discountPolicyDisabledId(clearDisabledId)，再重新关联新选中的行(updateDisabledId)

  - 第3点：删除时，先清空关联(clearDisabledId)，再删除失效申请头

### 重点逻辑4：前端submit参数覆盖疑似BUG

- **业务意义**：前端提交时硬编码覆盖了错误的业务参数，可能导致后端编码规则选择错误

- **具体逻辑描述**

  - 第1点：工程折扣政策失效应传isMakt:0和suitableType:'normal'，但headDS.ts中submit时写死为isMakt:2和suitableType:'special'

  - 第2点：该BUG可能导致后端编码规则选择错误（选择样品编码规则而非工程编码规则），以及列表查询suitableType过滤异常

  - 第3点：LOV查询参数(isMakt:0, suitableType:'normal')和列表查询参数(suitableType:'normal')是正确的，仅submit覆盖有误

```sql
SELECT d.*, p.DISCOUNT_POLICY_CODE, p.DISCOUNT_POLICY_NAME, p.POLICY_TYPE,
       p.SALE_AREA_NAME, p.PROVINCE_NAME, p.CUSTOMER_CLASS,
       p.EFFECTIVE_DATE_START, p.EFFECTIVE_DATE_END

LEFT JOIN EPM_DISCOUNT_POLICY p ON d.DISCOUNT_POLICY_ID = p.DISCOUNT_POLICY_ID
WHERE p.SUITABLE_TYPE = 'normal'
  AND p.IS_MAKT = 0
```

#### 按钮1：保存（详情页）

- **触发条件**：用户在详情页填写完毕点击"保存"按钮，编辑模式下可操作
- **执行逻辑**：
  - 第1点：设置organizationId为当前用户DEPT
  - 第2点：校验失效产品项列表非空
  - 第3点：若discountPolicyDisabledId为空（新建），生成失效单编码（编码规则AE.GC_DISCOUNT_POLICY_DISABLED），设置hzApproveStatus=NEW，插入EPM_DISCOUNT_POLICY_DISABLED记录，更新选中政策项的disabledId
  - 第4点：若discountPolicyDisabledId不为空（编辑），更新EPM_DISCOUNT_POLICY_DISABLED记录，清除旧政策项的disabledId(clearDisabledId)，更新新选中政策项的disabledId(updateDisabledId)
  - 第5点：保存附件
- **接口调用**：POST `/v1/{organizationId}/epm-discount-policy-disabled`

#### 按钮2：保存并提交（详情页）

- **触发条件**：用户在详情页点击"保存并提交"按钮，仅NEW/REJECTED/WITHDRAW/null状态可提交
- **执行逻辑**：
  - 第1点：保存失效单数据
  - 第2点：启动工作流（流程编码DISCOUNT_POLICY_DISABLED）
  - 第3点：更新hzApproveStatus=RUN
- **接口调用**：POST `/v1/{organizationId}/epm-discount-policy-disabled/save-and-submit`

#### 按钮3：删除（列表页）

- **触发条件**：用户在列表页选中一行或多行点击"删除"按钮，仅NEW状态可删除
- **执行逻辑**：
  - 第1点：先清空政策行关联(clearDisabledId)
  - 第2点：按discountPolicyDisabledId列表批量删除失效单头
- **接口调用**：DELETE `/v1/{organizationId}/epm-discount-policy-disabled`
- **排查SQL**：

```sql
SELECT DISCOUNT_POLICY_DISABLED_ID, DISCOUNT_POLICY_DISABLED_CODE, HZ_APPROVE_STATUS
FROM EPM_DISCOUNT_POLICY_DISABLED
WHERE DISCOUNT_POLICY_DISABLED_ID IN (:ids)
```

### 保存校验

- 校验1：失效政策行不允许为空 —— 确保用户选择了至少一个要失效的产品行

  - 详细逻辑

    - 第1点：检查discountPolicyItemDTOList不为空且存在非delete状态行

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM
    WHERE DISCOUNT_POLICY_DISABLED_ID = :discountPolicyDisabledId
    ```

- 校验2：当前折扣政策不允许失效 —— 确保关联的政策编码在系统中存在且状态允许失效

  - 详细逻辑

    - 第1点：检查折扣政策编码在EPM_DISCOUNT_POLICY中存在
    - 第2点：检查政策状态允许失效

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT * FROM EPM_DISCOUNT_POLICY
    WHERE DISCOUNT_POLICY_CODE = :discountPolicyCode
    ```

- 校验3：无法获上线文信息 —— 确保能获取到当前登录用户上下文

  - 详细逻辑

    - 第1点：检查用户上下文是否存在，用于编码生成时获取编码规则

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    -- 检查用户上下文，无SQL，为系统级检查
    ```

- 校验4：政策封顶总数量行必须大于单个经销商封顶数量 —— 确保封顶数量逻辑正确

  - 详细逻辑

    - 第1点：前端行DataSet中totalCapNumber和customerCapsNumber同时大于0时，totalCapNumber必须大于customerCapsNumber

  - 系统体现：toast提醒

  - 排查SQL：

    ```sql
    SELECT TOTAL_CAP_NUMBER, CUSTOMER_CAPS_NUMBER
    FROM EPM_DISCOUNT_POLICY_ITEM
    WHERE DISCOUNT_POLICY_ITEM_ID = :discountPolicyItemId
    ```

### 提交校验

- 校验1：仅特定状态允许提交 —— 防止重复提交或非法状态提交

  - 详细逻辑

    - 第1点：仅NEW/REJECTED/WITHDRAW/null状态显示"保存并提交"按钮
    - 第2点：前端控制按钮显隐，非这些状态下按钮不可见

  - 系统体现：按钮隐藏

  - 排查SQL：

    ```sql
    SELECT HZ_APPROVE_STATUS FROM EPM_DISCOUNT_POLICY_DISABLED
    WHERE DISCOUNT_POLICY_DISABLED_ID = :discountPolicyDisabledId
    ```

- 校验2：CRM推送成功 —— 专项折扣审批通过后推送CRM必须成功

  - 详细逻辑

    - 第1点：审批通过后，专项折扣(suitableType=special)逐行调用crmSdkService.policyDisabled接口
    - 第2点：接口返回null则报错"政策明细推送crm出错,请稍后再试"
    - 第3点：接口返回success=false则报错"政策明细推送crm出错：{lineId}:{message}"

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT ITEM.CRM_LINE_ID, ITEM.DISCOUNT_POLICY_ITEM_ID
    FROM EPM_DISCOUNT_POLICY_ITEM ITEM
    JOIN EPM_DISCOUNT_POLICY P ON ITEM.DISCOUNT_POLICY_ID = P.DISCOUNT_POLICY_ID
    WHERE ITEM.DISCOUNT_POLICY_DISABLED_ID = :discountPolicyDisabledId
      AND P.SUITABLE_TYPE = 'special'
    ```

### 状态机

#### 状态机流转图

```text
NEW(新建) ──保存并提交──→ RUN(审批中) ──审批通过──→ APPROVED(已审批)
  ↑                         │
  │                         ├──审批拒绝──→ REJECTED(已拒绝) ──保存并提交──→ RUN
  │                         ├──审批驳回──→ REBUT(已驳回)
  │                         └──终止──────→ INTERRUPT(已终止)
  │
  └──删除──→ (删除)

NEW ──撤回──→ WITHDRAW(已撤回) ──保存并提交──→ RUN
```

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|------------|
| NEW | 新建 | 编辑、保存、保存并提交、删除 |
| RUN | 审批中 | 无(等待审批结果) |
| APPROVED | 审批通过 | 无(流程结束) |
| REJECTED | 审批拒绝 | 编辑、保存、保存并提交 |
| REBUT | 已驳回 | 编辑、保存、保存并提交 |
| WITHDRAW | 已撤回 | 编辑、保存、保存并提交 |
| INTERRUPT | 已终止 | 无(流程结束) |

#### 报错1：失效政策行不允许为空
- **触发条件**：保存折扣政策失效单时，discountPolicyItemDTOList为空或所有行均为delete状态
- **逻辑分析**：保存校验中检查失效政策行列表非空且至少有一行非delete状态，因失效单必须指定要失效的政策明细行。该报错为阻断性报错
- **排查SQL**：
  ```sql
  SELECT edpd.DISABLE_ID, edpd.DISABLE_CODE, edpd.HZ_APPROVE_STATUS,
         (SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM edpi
          WHERE edpi.DISCOUNT_POLICY_DISABLED_ID = edpd.DISABLE_ID
            AND edpi.VALID_STAT = 0) AS 待失效行数
  FROM EPM_DISCOUNT_POLICY_DISABLE edpd
  WHERE edpd.DISABLE_ID = :disabledId
  -- 若待失效行数为0，则触发该报错
  ```

#### 报错2：当前折扣政策不允许失效 请检查
- **触发条件**：保存折扣政策失效单生成编码时，关联的政策编码(DISCOUNT_POLICY_CODE)在EPM_DISCOUNT_POLICY中不存在
- **逻辑分析**：编码生成方法中按DISCOUNT_POLICY_CODE查询EPM_DISCOUNT_POLICY，若返回null则抛出阻断性报错。可能原因：政策已被删除、政策编码传递错误
- **排查SQL**：
  ```sql
  SELECT edpd.DISABLE_ID, edpd.DISABLE_CODE, edpd.DISCOUNT_POLICY_CODE, edpd.DISCOUNT_POLICY_ID,
         edp.DISCOUNT_POLICY_ID AS 政策存在性, edp.VALID, edp.HZ_APPROVE_STATUS
  FROM EPM_DISCOUNT_POLICY_DISABLE edpd
  LEFT JOIN EPM_DISCOUNT_POLICY edp ON edpd.DISCOUNT_POLICY_CODE = edp.DISCOUNT_POLICY_CODE
  WHERE edpd.DISABLE_ID = :disabledId
  -- 若政策存在性为空，说明关联的政策编码不存在
  ```

#### 报错3：政策失效id不能为空
- **触发条件**：删除失效单或工作流回调时，disabledId参数为空或工作流回调objId为空
- **逻辑分析**：delete方法和doProcessOA方法中校验disabledId/objId非空，因操作需按主键定位失效单记录。该报错为阻断性报错
- **排查SQL**：
  ```sql
  SELECT edpd.DISABLE_ID, edpd.DISABLE_CODE, edpd.HZ_APPROVE_STATUS, edpd.CALLBACK_SOURCE
  FROM EPM_DISCOUNT_POLICY_DISABLE edpd
  WHERE edpd.DISABLE_ID = :disabledId
  -- 校验传入的失效ID是否存在
  ```

### 常见问题

- 问题1：工程折扣政策失效提交后编码规则使用了样品编码规则？
  - 原因：前端headDS.ts中submit时硬编码覆盖isMakt:2和suitableType:'special'(应为isMakt:0和suitableType:'normal')，导致后端generateCode方法走到样品分支
  - 解决思路：修改headDS.ts中submit覆盖参数为isMakt:0, suitableType:'normal'

- 问题2：审批通过后政策头未变为已失效？
  - 原因：政策下还有未失效的产品行(validStat≠3且不属于本次失效申请)。排查SQL：`SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM WHERE DISCOUNT_POLICY_ID = :policyId AND VALID_STAT != 3 AND DISCOUNT_POLICY_DISABLED_ID != :disabledId`
  - 解决思路：确认是否还有其他未失效的产品行，需对所有行分别发起失效申请

- 问题3：政策产品选择弹窗无数据？
  - 原因：该政策下所有产品行已被失效(validStat=3)或已被其他失效申请关联(discountPolicyDisabledId不为空)。排查SQL：`SELECT COUNT(*) FROM EPM_DISCOUNT_POLICY_ITEM WHERE DISCOUNT_POLICY_ID = :policyId AND VALID_STAT = 0 AND DISCOUNT_POLICY_DISABLED_ID IS NULL`
  - 解决思路：检查政策行状态，确认是否已全部失效

- 问题4：折扣政策失效后有什么影响？
  - 原因：审批通过后，选中的政策项的disabledId被更新，validStat更新为3，标记为已失效。失效的政策项不再适用于新的折扣单创建。若全部政策行失效，政策头valid也更新为3
  - 解决思路：这是预期行为，如需恢复需重新创建折扣政策

- 问题5：OA审批回调如何处理？
  - 原因：通过callbackSource字段标记回调来源（OA_PASS=OA审批通过，OA_REJECT=OA审批拒绝），系统根据回调结果更新审批状态
  - 解决思路：检查CALLBACK_SOURCE字段值确认回调来源

- 问题6：编辑失效单时产品项如何处理？
  - 原因：编辑时先清除旧选中政策项的disabledId(clearDisabledId)，再更新新选中政策项的disabledId(updateDisabledId)
  - 解决思路：这是预期行为，确保只有当前失效单关联的政策项被标记为失效
