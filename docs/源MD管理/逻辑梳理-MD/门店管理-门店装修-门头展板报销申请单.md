# 门店管理-门店装修-门头展板报销申请单

## 业务流程

### 全链路流程图

```
店面建设补贴政策(有效) → 新建门头报销申请 → 选择经销商/交易公司/法人/政策 → 添加门店装修明细 → 保存(NEW) → 提交审批 → 工作流审批(区域经理→销售会计) → 审批通过(APPROVED) → 可发起门头展板兑现
```

### 业务流程图

```
门头展板报销申请列表页(hlod低代码页面)
    │
    ├── 新增 ──→ 详情页(React组件 /custDhReimburseHead/add)

    │                ├── 选择交易公司(LOV: MBO.DISTRIBUTOR_COMPANY_VO) → 按经销商过滤

    │                ├── 选择店面建设补贴政策(LOV: AE.POLICY_STANDARD_VALID_HEAD) → 联动带出报销类型/预算年度

    │                │

```

### 状态机

```text
NEW(新建) ──提交──→ RUN(审批中) ──┬──审批通过──→ APPROVED(已审批) ──→ 可发起门头展板兑现
                                   ├──审批驳回──→ REBUT(已驳回) ──修改后重新提交──→ RUN
                                   └──审批退回──→ WITHDRAW(已撤回)
```

- 可编辑状态：NEW、WITHDRAW、INTERRUPT、REBUT
- 可删除状态：NEW、REBUT
- 审批通过后可发起门头展板兑现(菜单80)

## 重点逻辑

### 重点逻辑1：基于店面建设补贴政策报销

- **业务意义**：门头展板报销必须关联有效的店面建设补贴政策，按政策标准计算报销金额，确保报销有据可依
- **具体逻辑描述**：
  - 选择政策LOV(AE.POLICY_STANDARD_VALID_HEAD)，按当前用户组织ID(entid)过滤
  - 后端checkParams校验：政策不能为空、政策必须有效(valid=2)、政策在有效期内(startDate≤当前日期≤endDate)
  - 政策联动带出报销类型(bxType=budgetType)和预算年度(year)
  - 行表通过政策行(policyLineId)关联政策明细，获取标准金额、数量范围等

### 重点逻辑2：额度内外分开报销

- **业务意义**：根据报销类型(额度内/额度外)区分金额，不同类型走不同审批和预算控制
- **具体逻辑描述**：
  - 报销类型bxType：1-额度内、2-额度外
  - computeBxLine根据bxType清空不符合的金额：bxType=1时额度外金额置0，bxType=2时额度内金额置0
  - 行表含额度内申请金额(inApplyAmt)、额度外申请金额(outApplyAmt)、业务批准金额(inBizAmt/outBizAmt)、财务批准金额(inFinAmt/outFinAmt)
  - 新增时业务批准金额=申请金额、财务批准金额=申请金额(computeBxLine自动赋值)

### 重点逻辑3：行数据校验与计算(computeBxLine)

- **业务意义**：每行门店装修明细需校验数量范围和附件完整性，确保报销明细合规
- **具体逻辑描述**：
  - 申请数量必须>0，且在政策数量范围内(minNum≤applyNum≤maxNum)，否则报"报销申请数量必须在政策数量范围内"
  - 装修前照片(beforeDocId)必传，否则报"请上传装修前文件"
  - 装修后照片(afterDocId)必传，否则报"请上传装修后文件"
  - 行金额校验：非超额报销时(excessFlag!=Y)，申请/业务批准金额不能大于标准金额(inStandardAmt/outStandardAmt)
  - 前端validator校验：申请数量范围、额度内/外申请金额不超标准金额

### 重点逻辑4：提交时计算实际报销金额(computeAndUpdateBxAmt)

- **业务意义**：提交审批时根据是否限额计算实际报销金额，校验额度外预算充足
- **具体逻辑描述**：
  - 限额模式(custLimitFlag=Y)：调用computeLimitBxAmt
    - 获取经销商限额(getCustLimit)
    - 计算已报销金额(getOutBxUsedAmt，同一经销商+政策的RUN/RETURN/APPROVED状态报销单)
    - 额度外超限金额 = min(经销商限额 - 已报销金额 - 财务批准总额(额度外), 0)
    - 额度外实际报销金额 = 财务批准总额(额度外) + 超限金额
    - 超限处理策略(extraBudgetExcessStrategy)：1-超出不计(额度内实际报销=财务批准)、2-转额度内(额度内实际报销=财务批准-超限金额)
  - 非限额模式(custLimitFlag!=Y)：调用computeNotLimitBxAmt，实际报销金额=财务批准金额
  - 额度外预算校验(validBxAmt)：useExtraBudgetFlag=Y时，额度外实际报销金额≤剩余额度外可用预算(viewOverBudgetAmt)，否则报"X年的额度外预算不足"

### 重点逻辑5：工作流多节点审批

- **业务意义**：门头报销申请经区域经理和销售会计两级审批，各节点可修改不同字段
- **具体逻辑描述**：
  - 工作流编码：SUB_STORE_HEAD_PROCESS_DOOR(门头报销申请流程)
  - 提交时wfProcSubmit：先计算报销金额(onUserSubmit)，再启动工作流实例，设置HZ_INSTANCE_ID和HZ_APPROVE_STATUS=RUN
  - 区域经理审批(bizNodeUpdate)：修改业务批准金额(inBizAmt/outBizAmt)，校验非超额时不超政策标准，财务批准金额同步更新
  - 销售会计审批(finNodeUpdate)：修改财务批准金额(inFinAmt/outFinAmt)，根据bxType清空不符合的金额
  - 审批通过(onWfComplete)：设置HZ_APPROVE_STATUS=APPROVED
  - eventExecute处理：SEND_MBO(发送至MBO系统)、OUT_BX_AMT(更新流程变量reSignFlag和outBxAmt)

### 重点逻辑6：单独门店申请校验

- **业务意义**：部分政策要求每次报销只能申请一个门店，防止批量报销混用
- **具体逻辑描述**：
  - 当政策singleStoreApplyFlag=Y时，checkParams校验行表中门店ID(terminalId)去重后数量=1
  - 否则报"单独门店申请，只能报销一个门店"

### 重点逻辑7：编码生成

- **业务意义**：门头报销申请单号按规则自动生成，确保唯一性和可追溯性
- **具体逻辑描述**：
  - 编码规则：AE.DH_REIMBURSE_HEAD_NO
  - 生成方式：prefixCode + suffixCode，prefixCode为事业部编码(divisionCode)，若为空则用"ARR"
  - suffixCode通过CodeRuleBuilder.generateCode生成流水号
  - 生成时机：doInsert时调用genReimburseCode方法

### 重点逻辑8：重签协议标识(reSignFlag)

- **业务意义**：判断是否需要重新签署MBO合同协议，影响工作流分支
- **具体逻辑描述**：
  - reSignFlag字段：Y-需重签、N-无需重签，默认N
  - eventExecute中OUT_BX_AMT事件时调用reSignFlag方法判断
  - 若reSignFlag=Y直接返回Y；否则查询MBO合同附件数量(getAttachmentFileCount)，附件为0时返回Y
  - 更新工作流变量reSignFlag和outBxAmt，影响后续审批节点

### 保存校验

- 校验1：经销商必填 —— 确保报销单关联有效经销商
  - 详细逻辑：前端DataSet required=true校验，后端checkParams校验customerId为空报"经销商法人不能为空"
  - 系统体现：前端C7N必填提示，后端CommonException
  - 排查SQL：`SELECT * FROM CUSTOMER WHERE CUSTOMER_ID = #{customerId}`

- 校验2：交易公司必填 —— 确保报销单关联有效交易公司
  - 详细逻辑：前端DataSet required=true校验，后端getCustLegal查询法人信息失败报"获取法人信息失败"
  - 系统体现：前端C7N必填提示，后端CommonException

- 校验3：法人客户必填 —— 确保报销单关联有效法人
  - 详细逻辑：前端DataSet required=true校验，后端checkParams校验customerLegalId为空报"经销商法人不能为空"
  - 系统体现：前端C7N必填提示，后端CommonException

- 校验4：补贴政策必填且有效 —— 确保报销基于有效政策
  - 详细逻辑：后端checkParams校验policyStandardHead为空报"报销政策不能为空"，valid!=2报"报销政策已失效"，不在有效期内报"报销政策已过期"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT * FROM POLICY_STANDARD_HEAD WHERE POLICY_STANDARD_ID = #{policyStandardId} AND VALID = 2 AND START_DATE <= SYSDATE AND END_DATE >= SYSDATE`

- 校验5：报销类型必填 —— 确保选择额度内或额度外
  - 详细逻辑：后端checkParams校验bxType为空报"请选择报销类型"
  - 系统体现：后端CommonException

- 校验6：行表不能为空 —— 确保有门店装修明细
  - 详细逻辑：后端checkParams校验lines为空报"报销明细不能为空"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT COUNT(*) FROM CUST_DH_REIMBURSE_LINE WHERE HEAD_ID = #{headId}`

- 校验7：单独门店申请校验 —— 政策要求时只能一个门店
  - 详细逻辑：后端checkParams当singleStoreApplyFlag=Y时校验行表门店ID去重数=1，否则报"单独门店申请，只能报销一个门店"
  - 系统体现：后端CommonException

- 校验8：申请数量范围校验 —— 确保数量在政策范围内
  - 详细逻辑：前端validator校验applyNum < minNum或> maxNum报"装修项目数量限制范围为X-Y"；后端computeBxLine校验applyNum=0报"申请数量必须大于0"，不在范围报"报销申请数量必须在政策数量范围内"
  - 系统体现：前端字段validator提示，后端CommonException

- 校验9：装修前/后照片必传 —— 确保装修证据完整
  - 详细逻辑：前端beforeDocName/afterDocName required=true；后端computeBxLine校验beforeDocId为空报"请上传装修前文件"，afterDocId为空报"请上传装修后文件"
  - 系统体现：前端C7N必填提示，后端CommonException

- 校验10：金额不超标准(非超额报销) —— 确保报销金额不超政策标准
  - 详细逻辑：前端validator校验非超额时(excessFlag!=Y)申请/业务批准金额不超标准金额，报"输入的金额不能大于对应的额度(内/外)标准金额"；后端bizNodeUpdate校验非超额时业务批准金额不超标准，报"非超额报销，额度内/外金额不允许大于政策标准"
  - 系统体现：前端字段validator提示，后端CommonException

### 提交校验

- 校验1：额度外预算充足 —— 防止超额报销
  - 详细逻辑：提交时validBxAmt，当useExtraBudgetFlag=Y且额度外实际报销金额>0时，查询剩余额度外可用预算(viewOverBudgetAmt)，实际报销金额>剩余预算报"X年的额度外预算不足，有疑问请联系财务"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT * FROM FIN_FEE_CHECK_BX_HEADER WHERE BUD_YEAR = #{year} AND FEE_TYPE_ID = 66014602 AND DIVISION_ID = #{divisionId}`

- 校验2：经销商限额校验(限额模式) —— 防止超过经销商限额
  - 详细逻辑：提交时computeLimitBxAmt，当custLimitFlag=Y时计算超限金额=min(经销商限额-已报销金额-财务批准总额, 0)，根据超限处理策略处理
  - 系统体现：后端CommonException

- 校验3：超限处理策略校验 —— 确保超限处理配置正确
  - 详细逻辑：computeLimitBxAmt当extraBudgetExcessStrategy非1非2时报"当前额度外超限处理不存在，请联系相关人员处理"
  - 系统体现：后端CommonException

### 下游影响

- **门头展板兑现(CUST_DH_CASHOUT_HEAD)**：报销单审批通过(APPROVED)后可发起门头展板兑现(菜单80)，兑现单通过REIMBURSE_HEAD_ID关联报销单
- **MBO系统**：审批过程中eventExecute处理SEND_MBO事件时，通过mboFeignClient.advDecAdd推送至MBO系统，billFlag=6，reimbursementType=门头报销
- **额度外预算占用**：报销单提交后占用额度外预算(outBxAmt)，影响后续报销单的预算校验
- **经销商限额占用**：限额模式下报销单占用经销商限额(outBxUsedAmt)，影响同经销商后续报销
- **附件(OBJ_ATTACH_REL)**：报销单关联附件(attachConfId=20250516)，包括装修前/后照片、MBO合同等
- **工作流变量**：eventExecute更新工作流变量reSignFlag和outBxAmt，影响审批分支路由

#### 报错1：报销政策不能为空
- **触发条件**：点击"保存"按钮，checkParams校验policyStandardHead为null（未选择补贴政策）
- **逻辑分析**：门头展板报销必须关联有效的店面建设补贴政策，按政策标准计算报销金额。若用户未通过LOV(AE.POLICY_STANDARD_VALID_HEAD)选择政策、policyStandardId传值丢失、或前端未触发联动查询，policyStandardHead为null抛异常。需在新增页面选择有效的补贴政策。
- **排查SQL**：
  ```sql
  SELECT h.id           AS 政策ID,
         h.policy_name  AS 政策名称,
         h.valid        AS 有效状态,
         h.start_date   AS 开始日期,
         h.end_date     AS 结束日期
  FROM   policy_standard_head h
  WHERE  h.entid = #{当前用户组织ID}
  AND    h.valid = 2
  AND    h.start_date <= SYSDATE
  AND    h.end_date >= SYSDATE
  ORDER  BY h.start_date DESC;
  ```

#### 报错2：报销政策已失效，请重新选择有效报销政策
- **触发条件**：点击"保存"按钮，checkParams校验policyStandardHead.getValid()≠2
- **逻辑分析**：政策valid=2表示有效，其他值表示失效/草稿/作废。若用户选择了已失效的政策（如政策被管理员置为无效后用户仍使用前端缓存LOV）、或政策valid字段配置异常，校验不通过抛异常。需重新选择有效(valid=2)政策。
- **排查SQL**：
  ```sql
  SELECT h.id           AS 政策ID,
         h.policy_name  AS 政策名称,
         h.valid        AS 有效状态,
         CASE h.valid WHEN 2 THEN '有效' ELSE '失效' END AS 状态说明
  FROM   policy_standard_head h
  WHERE  h.id = #{传入的policyStandardId};
  ```

#### 报错3：经销商法人不能为空
- **触发条件**：点击"保存"按钮，checkParams校验customerId或customerLegalId为空
- **逻辑分析**：报销单需关联经销商和交易公司法人组合，用于后续推送MBO和资金池。若用户未选择经销商、未选择交易公司/法人、或联动查询getCustLegal未返回customerLegalId，校验不通过抛异常。需依次选择经销商→交易公司→法人客户。
- **排查SQL**：
  ```sql
  SELECT r.id                 AS 报销单ID,
         r.reimburse_code     AS 报销单号,
         r.customer_id        AS 经销商ID,
         r.customer_legal_id  AS 法人中间表ID,
         r.trading_company_code AS 交易公司编码
  FROM   cust_dh_reimburse_head r
  WHERE  r.hz_approve_status = 'NEW'
  AND    (r.customer_id IS NULL OR r.customer_legal_id IS NULL)
  ORDER  BY r.creation_date DESC;
  ```

#### 报错4：报销政策已过期，请重新选择有效报销政策
- **触发条件**：点击"保存"按钮，checkParams校验policyStandardHead.startDate>当前日期或endDate<当前日期
- **逻辑分析**：政策有有效期限制，仅在[startDate, endDate]区间内有效。若用户选择了已过期或未生效的政策（如政策endDate<当前日期已结束、或startDate>当前日期尚未生效），校验不通过抛异常。需选择当前日期在有效期内的政策。
- **排查SQL**：
  ```sql
  SELECT h.id           AS 政策ID,
         h.policy_name  AS 政策名称,
         h.start_date   AS 开始日期,
         h.end_date     AS 结束日期,
         SYSDATE        AS 当前日期
  FROM   policy_standard_head h
  WHERE  h.valid = 2
  AND    (h.start_date > SYSDATE OR h.end_date < SYSDATE)
  ORDER  BY h.end_date DESC;
  ```

#### 报错6：报销明细不能为空
- **触发条件**：点击"保存"按钮，checkParams/computeBxLine校验lines集合为空
- **逻辑分析**：报销单需至少一行门店装修明细，含门店、补贴项目、数量、金额、装修前后照片等。若用户未添加明细行、前端行数据源未正确绑定、或行数据被误清空，lines为空抛异常。需添加至少一行明细。
- **排查SQL**：
  ```sql
  SELECT r.id              AS 报销单ID,
         r.reimburse_code  AS 报销单号,
         (SELECT COUNT(1)
          FROM   cust_dh_reimburse_line l
          WHERE  l.head_id = r.id) AS 行表记录数
  FROM   cust_dh_reimburse_head r
  WHERE  r.hz_approve_status = 'NEW'
  AND    NOT EXISTS (SELECT 1 FROM cust_dh_reimburse_line l WHERE l.head_id = r.id)
  ORDER  BY r.creation_date DESC;
  ```

#### 报错7：单独门店申请，只能报销一个门店
- **触发条件**：点击"保存"按钮，checkParams校验政策singleStoreApplyFlag=Y时，行表中terminalId去重后数量≠1
- **逻辑分析**：部分政策要求每次报销只能申请一个门店，防止批量报销混用标准。若政策singleStoreApplyFlag=Y但用户在多行明细中选择了不同门店，校验不通过抛异常。需只保留一个门店的明细行。
- **排查SQL**：
  ```sql
  SELECT r.id              AS 报销单ID,
         r.reimburse_code  AS 报销单号,
         r.policy_standard_id AS 政策ID,
         COUNT(DISTINCT l.terminal_id) AS 门店去重数
  FROM   cust_dh_reimburse_head r
  JOIN   cust_dh_reimburse_line l ON l.head_id = r.id
  WHERE  r.hz_approve_status = 'NEW'
  GROUP  BY r.id, r.reimburse_code, r.policy_standard_id
  HAVING COUNT(DISTINCT l.terminal_id) > 1
  ORDER  BY r.creation_date DESC;
  ```


#### 报错9：报销申请数量必须在政策数量范围内
- **触发条件**：点击"保存"按钮，computeBxLine校验某行applyNum<minNum或applyNum>maxNum
- **逻辑分析**：政策明细行规定了数量上下限(minNum, maxNum)，确保报销数量在政策允许范围内。若用户填写的数量超出[minNum, maxNum]区间（如政策限1~5但填了10），校验不通过抛异常。需修改数量至政策范围内。
- **排查SQL**：
  ```sql
  SELECT l.id            AS 行ID,
         l.head_id       AS 报销单ID,

  JOIN   policy_standard_line p ON p.id = l.policy_line_id
  WHERE  l.apply_num < p.min_num OR l.apply_num > p.max_num
  ORDER  BY l.id DESC;
  ```

## 常见问题FAQ

**Q1：补贴政策LOV无数据？**
A：检查POLICY_STANDARD_HEAD表中是否存在VALID=2且START_DATE≤当前日期≤END_DATE的记录。排查SQL：`SELECT * FROM POLICY_STANDARD_HEAD WHERE VALID = 2 AND START_DATE <= SYSDATE AND END_DATE >= SYSDATE AND ENTID = #{当前用户组织ID}`

**Q2：额度外预算不足？**
A：检查当前年份额度外总预算是否充足。排查SQL：`SELECT * FROM FIN_FEE_CHECK_BX_HEADER WHERE BUD_YEAR = #{year} AND FEE_TYPE_ID = 66014602 AND DIVISION_ID = #{divisionId}`。同时检查同经销商+政策已报销金额：`SELECT SUM(OUT_BX_AMT) FROM CUST_DH_REIMBURSE_HEAD WHERE POLICY_STANDARD_ID = #{policyStandardId} AND CUSTOMER_ID = #{customerId} AND HZ_APPROVE_STATUS IN ('RUN','RETURN','APPROVED') AND ID != #{currentId}`

**Q3：经销商限额如何计算？**
A：限额模式下(custLimitFlag=Y)，通过getCustLimit查询经销商限额表。已报销金额=getOutBxUsedAmt(同一经销商+政策的RUN/RETURN/APPROVED状态报销单OUT_BX_AMT之和)。超限金额=min(限额-已报销-财务批准, 0)。

**Q4：区域经理审批时金额无法修改？**
A：检查政策excessFlag是否为Y(超额报销)。非超额报销时(excessFlag!=Y)，业务批准金额不能超过政策标准金额(inStandardAmt/outStandardAmt)。若标准金额为0则不允许修改。

**Q5：审批通过后如何发起兑现？**
A：报销单HZ_APPROVE_STATUS=APPROVED后，在门头展板兑现(菜单80)新建页面通过LOV(AE.CUSTDHCASHOUTHEADLIST.VIEW)选择该报销单发起兑现。兑现单通过REIMBURSE_HEAD_ID关联报销单。

**Q6：需重签协议标识如何判断？**
A：reSignFlag方法：若字段已为Y则直接返回Y；否则查询MBO合同附件数量(getAttachmentFileCount)，若附件为0则返回Y(需重签)，否则返回N。该标识影响工作流审批分支。
