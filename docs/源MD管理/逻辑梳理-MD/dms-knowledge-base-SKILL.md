# DMS知识库

根据菜单路径，梳理业务逻辑，按照标准结构模板产出规范格式的MD文档。

---

## The Job

1. 接收用户提供的菜单路径或菜单名称
2. 在代码库中搜索对应的前端和后端源码
3. 分析业务逻辑、校验规则、状态流转、数据库表结构
4. 按照标准模板格式生成MD文件
5. 保存到 `D:\VIP冰\项目\新门户\完整源码-外层\逻辑数量-最终\` 目录下
6. 输出MD文件内容并附上文件路径链接

---

## 标准结构扩展规则

在梳理菜单逻辑的过程中，如果发现代码中包含某些逻辑**不在当前标准结构模板中**（即无法归入现有章节），必须：

1. **暂停生成MD文件**
2. **向用户说明**：发现代码中存在 `{具体逻辑描述}` 不在当前标准结构中
3. **询问用户**：是否需要将该逻辑补充到标准结构模板中？如果需要，建议补充到哪个章节下？
4. **等待用户确认后**，先更新本SKILL.md的标准模板和编写规范，再继续生成MD文件

**不得自行决定**将新逻辑硬塞到不匹配的章节中，也**不得跳过**该逻辑不写。

## Language Rules

- **强制**：始终使用简体中文输出
- 数据库表名和字段名使用 UPPER_SNAKE_CASE 命名规范（如 EPM_VERIFER_INVOICE_DETAILS.VERIFER_INVOICE_DETAILS_ID）
- MD文件按菜单路径命名，使用中文加连字符格式，如：`工程管理-项目交付-工程折扣政策申请.md`

## Step 1: 接收菜单路径

用户会明确给出菜单路径，格式为：**【一级菜单-二级菜单-三级菜单】**

示例：
- `【工程管理-合同与折扣-项目合同失效】`
- `【家装管理-家装交付-家装折扣政策申请】`
- `【门店管理-样品及长库龄管理-样品及长库龄折扣政策失效】`

**关键原则：以用户指定的菜单路径为唯一切入点，直接定位该菜单对应的界面入口，从该入口出发梳理整个菜单的业务逻辑。禁止自行根据菜单名称主观理解业务逻辑，必须通过代码追踪验证。**

### 1.1 菜单路径解析

从菜单路径中提取关键信息：

| 路径层级 | 作用 | 示例 |
|---------|------|------|
| 一级菜单 | 确定业务域（工程/家装/门店） | 工程管理 |
| 二级菜单 | 确定业务子域 | 合同与折扣 |
| 三级菜单 | 确定具体功能模块 | 项目合同失效 |

### 1.2 菜单入口定位策略

**必须按以下优先级定位菜单入口：**

**第一优先级：前端路由/菜单配置文件**
- 搜索前端路由配置（router、menu配置），用三级菜单名称精确匹配路由path
- 从路由path确定前端页面组件路径
- 搜索目录：`packages/arrow-ae/src/` 下的路由配置文件

**第二优先级：前端页面目录**
- 根据菜单路径关键词，在 `packages/arrow-ae/src/pages/` 下搜索匹配的页面组件
- 搜索关键词：三级菜单名称的拼音、英文翻译、驼峰命名
- 示例：`项目合同失效` → 搜索 `ContractDisabled` / `contractDisabled` / `contract-disabled`

**第三优先级：后端Controller路径**
- 如果前端为低代码页面（hlod），无独立前端源码
- 在后端Controller中搜索与菜单名称匹配的API路径
- 搜索目录：`ae-business/src/main/java/com/arrow/dms/ae/biz/` 下的 `*Controller.java`

**第四优先级：后端Service/Entity名称**
- 根据菜单名称推断后端实体名，搜索对应的ServiceImpl和Entity
- 示例：`项目合同失效` → 搜索 `EpmContractDisabled` / `ContractDisabled`

### 1.3 入口定位后的代码追踪链

定位到菜单入口后，按以下链路追踪完整代码：

```
前端路由 → 前端页面组件 → API调用 → 后端Controller → ServiceImpl → Entity/Repository/Mapper
```

对于低代码页面：
```
后端Controller → ServiceImpl → Entity/Repository/Mapper
```

## Step 2: 源码搜索与分析

> **CRITICAL — 反思教训（2026-08-29）：**
>
> 界面模块的字段配置（详情页头表单、行表格列、弹窗入参、显隐条件、编辑权限等）**只能从前端DataSet配置或后端Entity中获取**，不能仅靠"网站内容对比"补充。之前批量处理时跳过了代码搜索步骤，仅做网站内容对比，导致大量文件缺少界面模块3/4、选择弹窗SQL、保存校验SQL等只能从代码中获取的内容。
>
> **正确流程：每个菜单必须先搜索前端代码+后端代码，从代码中梳理完整字段配置，按skill规范生成MD，然后再与知识库网站对比补充网站独有的内容。禁止跳过代码搜索直接做网站对比。**

### 2.1 前端源码分析

根据 Step 1 定位到的前端页面组件，读取并分析：
- 页面结构：表单字段、表格列、按钮
- API调用：请求路径、参数、响应结构
- 业务逻辑：前端校验、计算逻辑、条件显隐
- 工作流集成：提交、审批回调

**必须读取的文件（按重要性排序）：**
1. **DataSet配置文件**（headDS.ts / lineDS.ts / ListDS.ts）：字段定义、组件类型、显隐条件、编辑权限、lovPara、defaultValue、bind绑定关系 —— **这是界面模块表格的数据来源**
2. **页面组件文件**（index.tsx）：字段渲染顺序、条件渲染逻辑、按钮显隐条件、Tab结构
3. **行表格组件**（LineInfo.tsx等）：行列定义、列显隐条件、编辑权限、计算逻辑
4. **常量文件**（constants.ts）：权限前缀、审批对象类型ID、国际化前缀

注意：
- 部分菜单使用低代码页面（hlod），无独立前端源码
- 低代码页面**必须**基于后端Entity字段梳理界面模块，需在文档中明确说明
- **即使是低代码页面，也必须搜索后端Entity获取完整字段列表，不能省略界面模块3/4**

### 2.2 后端源码分析

根据前端API调用或菜单名称，定位并读取后端源码：

需要读取的文件类型（按重要性排序）：
1. **ServiceImpl**：核心业务逻辑（最重要，必须完整读取）—— 保存校验、提交校验、状态流转、推送逻辑
2. **Entity**：数据库表结构、字段定义（必须完整读取）—— **低代码页面的界面模块字段来源**
3. **Controller**：API接口定义、路径映射（必须读取）
4. **Repository/Mapper**：数据访问逻辑（按需读取，关注自定义SQL）—— 弹窗查询SQL来源
5. **DTO/VO**：数据传输对象（按需读取，补充字段信息）

### 2.3 共用代码识别

注意识别多个菜单共用同一后端代码的情况：
- 通过参数区分（如 isMakt、suitableType、reportType、actionType 等）
- 在文档中明确标注共用关系和差异点
- 即使共用代码，也必须以当前菜单路径为视角梳理，明确当前菜单使用的参数值

## Step 3: MD文件生成

### 3.1 文件命名规则

**按菜单的一级、二级、菜单名称命名，层级用`-`连接：**
- 示例：`家装管理-家装往来-家装真实性核销.md`
- 示例：`工程管理-合同与折扣-项目合同失效.md`

规则：
- 文件名 = 一级菜单-二级菜单-菜单名称，不做任何翻译或缩写
- 层级分隔符统一用中文短横线`-`
- 文件名与菜单在系统中的实际层级路径完全一致

### 3.2 文件存放路径

```
D:\VIP冰\项目\新门户\完整源码-外层\逻辑数量-最终\{文件名}.md
```

即存放在 `D:\VIP冰\项目\新门户\完整源码-外层\逻辑数量-最终\` 目录下。每个菜单输出一个独立的MD文件。

**模板执行规则：**
- 章节必须按以下编号顺序出现（1→7）

- 不得添加本模板中未列出的章节

## Step 4: 内容编写规范

### 4.1 业务流程

- **业务流程图**：根据上游依赖、下游依赖，用文本格式表达这个业务的完整业务流
- **上游依赖**：使用表格列出该菜单依赖的外部系统、服务、数据源、配置
  - 上游模块：模块名称
  - 依赖类型：数据依赖、配置依赖
  - 依赖说明：说明这个依赖对本模块的作用
  - 依赖成立条件：例如上游单据状态、数据状态
- **下游影响**：列出该菜单操作后影响的系统、表、数据，每项包含概述和具体描述

### 4.2 重点逻辑

- 每个重点逻辑包含：名称（标题右侧小标签概括）、业务意义、具体逻辑描述
- 逻辑描述要分点展示
- **不需要展示具体的表名、字段名，全部用通俗易懂的文字描述即可**
- 优先梳理：核心业务逻辑、共用代码差异点、特殊校验规则

### 4.3 详细逻辑 - 界面模块

- **字段名**：显示界面上实际展示的名称
- **数据库列名**：表名+字段名（UPPER_SNAKE_CASE）
- **组件**：如文本框、下拉选择框、单选框等
- **业务释义**：描述该字段的业务含义
- **显隐条件**：常显、隐藏、xxx时才显示
- **取值/赋值逻辑**：
  1. 说明默认值
  2. 来源：如来源xx值集、来源xx配置项、根据xx自动带出
  3. 涉及自动计算的，要说明计算公式（直接写在取值/赋值逻辑列中，如：自动计算=发票数量×转换率(保留3位小数)）
  4. 是否可编辑、何种条件下可编辑
  5. 可选值范围：例如值集内生效的项、例如时间范围；若无可选值范围限制，填写"-"
  6. 若涉及弹窗选择的，说明弹窗内可选数据范围的逻辑、以及对应的排查SQL

### 4.4 详细逻辑 - 选择弹窗

- 每个弹窗包含：入参（字段名、中文名、释义、示例）、数据范围、查询SQL

- 数据范围：说明弹窗内可选数据范围的逻辑
- **查询SQL（强制）**：每个弹窗必须提供对应的查询SQL，以引用块+代码块形式展示
