# 点将管理-特训营管理-活动点将执行

> 后端代码位于 mbo-business 微服务（源码未包含在当前源码目录下），前端 API 路径前缀 `mlt/activityApply/*`（与活动点将共用 API）。本菜单为活动点将的执行跟踪页面，审批通过后进入执行环节，固定参数 `pageType=activity`。

## 业务流程

### 业务流程图

```
活动点将审批通过
        |
        v
活动点将执行列表(本页面) ──autoQuery──→ 加载执行中数据(pageType=activity)
        |
        ├──→ 查看申请 ──→ 跳转经销商活动点将详情页(isExecute=true)
        ├──→ 查看确认书 ──→ queryPDF接口 ──→ window.open打开PDF
        ├──→ 特殊取消 ──→ 校验7天内且已生效 ──→ specialCancel接口
        ├──→ 结束执行 ──→ 弹窗填写实际时间+备注 ──→ endExecute接口
        ├──→ 同步OA ──→ pushOa接口
        ├──→ 同步FDD ──→ pushFdd接口
        └──→ 同步CRM ──→ sendCrmOrder接口
```

### 全链路流程图

```
开始 → 查看已生效活动点将 → ★执行跟踪★ → 执行完成·更新状态 → 回写执行记录·CRM状态 → 结束
```

### 下游影响

- **经销商活动点将详情页**：查看申请跳转，openTab 新标签页打开，传入 `isExecute=true`。
- **活动执行记录**：执行留痕，数据库共享 TRAIN_APPLY 表。
- **讲师排期(占用)**：讲师排期更新，数据库状态共享。
- **CRM订单状态**：订单状态同步，调用 sendCrmOrder 接口推送。
- **OA审批系统**：流程同步，调用 pushOa 接口推送。
- **法大大电子签约**：签约同步，调用 pushFdd 接口推送。

## 重点逻辑

### 重点逻辑1：只读跟踪

- **业务意义**：执行跟踪页面不修改点将申请原始内容，仅记录执行结果与状态推进，保证申请数据与执行结果分离。
- **具体逻辑描述**：
  - 本菜单仅提供查询、查看和执行结果回写功能。
  - 如需调整人员或时间，应回到活动点将管理发起变更或取消。
  - 列表查询固定传入 `pageType=activity`，`autoQuery=true` 自动加载。

### 重点逻辑2：数据来源

- **业务意义**：复用活动点将申请实体，筛选已审批通过且进入执行阶段的申请，避免重复建模。
- **具体逻辑描述**：
  - 复用 TRAIN_APPLY 表和 `mlt/activityApply/*` 接口。
  - 筛选条件 `APPLY_TYPE_ONE=activity` 且 `APPLY_APPROVAL_STATE=approved`。
  - 执行状态通过 `ORDER_LECTURE_STATE` 跟踪。

### 重点逻辑3：状态联动

- **业务意义**：执行状态与活动完成情况联动，确保状态机自动推进，减少人工干预。
- **具体逻辑描述**：
  - 执行状态与活动完成情况联动。
  - 所有子任务完成后自动更新执行状态为已完成。
  - 结束执行后点将状态推进为已执行，作为活动交付的最终留痕。

### 重点逻辑4：特殊取消校验

- **业务意义**：限制取消时机，避免临近开课取消造成资源浪费。
- **具体逻辑描述**：
  - 计算时间差值 `timeDiff = (planStartTime - nowTime) / (24*60*60*1000)`。
  - 校验条件 `1 <= timeDiff <= 7`（培训开始前1-7天内）。
  - 校验审批状态 `approvalState === 'fdd_sign'`（已法大大签约）。
  - 校验是否已发起取消：`cancelApprovalState` 不为空且不等于 `reject` 和 `oa_reject` 时提示"该单据已发起取消申请，不可重复发起！"。
  - 校验不通过提示"只有在培训开始前七天内且已生效的单据才可以发起取消申请！"。
  - 提交调用 `POST mlt/activityApply/specialCancel` 接口。

### 重点逻辑5：结束执行逻辑

- **业务意义**：记录实际交付时间与备注，作为活动交付的最终留痕。
- **具体逻辑描述**：
  - 结束执行通过 Modal 弹窗填写。
  - 实际开始时间 `realStartDate`：DatePicker，必填。
  - 实际结束时间 `realEndDate`：DatePicker，必填。
  - 结束执行人 `endExecuteUserName`：自动填充。
  - 结束备注 `endExecuteRemark`：TextArea，必填。
  - 调用 `POST mlt/activityApply/endExecute` 接口。

### 重点逻辑6：同步外部系统

- **业务意义**：将执行结果同步至外部系统，保证多方数据一致。
- **具体逻辑描述**：
  - **同步OA**：调用 `POST mlt/activityApply/pushOa/{applyCode}` 推送OA审批流程。
  - **同步FDD**：调用 `POST mlt/activityApply/pushFdd/{applyCode}` 推送法大大签约。
  - **同步CRM**：调用 `POST mlt/activityApply/sendCrmOrder/{applyCode}` 推送CRM订单。

- **触发方式**：点击工具栏"结束执行"按钮，需先选中一条数据。

### 保存校验

- 校验1：结束执行实际时间必填 —— 确保执行结果可留痕
  - **详细逻辑**：`realStartDate`、`realEndDate`、`endExecuteRemark` 必填，任一为空提示对应报错信息。
  - **系统体现**：前端 `endExecuteFormDS.validate()` 校验，后端二次校验。
  - **排查SQL**：
    ```sql
    SELECT ta.APPLY_CODE AS 申请编码, ta.REAL_START_DATE AS 实际开始时间,
           ta.REAL_END_DATE AS 实际结束时间, ta.END_EXECUTE_REMARK AS 结束备注
    FROM TRAIN_APPLY ta
    WHERE ta.ORDER_LECTURE_STATE = 'executed'
      AND (ta.REAL_START_DATE IS NULL OR ta.REAL_END_DATE IS NULL
           OR ta.END_EXECUTE_REMARK IS NULL);
    ```

### 提交校验

- 校验1：特殊取消时机校验 —— 防止临近开课取消造成资源浪费
  - **详细逻辑**：校验 `1 <= timeDiff <= 7` 且 `approvalState === 'fdd_sign'` 且未重复发起取消。
  - **系统体现**：前端时间差值计算与状态校验，后端二次校验。
  - **排查SQL**：
    ```sql
    SELECT ta.APPLY_CODE AS 申请编码, ta.APPROVAL_STATE AS 审核状态,
           ROUND(ta.ACTIVITY_START_DATE - SYSDATE) AS 距开始天数
    FROM TRAIN_APPLY ta
    WHERE ta.APPLY_TYPE_ONE = 'activity'
      AND ta.APPROVAL_STATE = 'fdd_sign'
      AND ta.ACTIVITY_START_DATE > SYSDATE
      AND ta.ACTIVITY_START_DATE <= SYSDATE + 7;
    ```

### 状态机

```
待执行 ──开始执行──→ 执行中 ──结束执行──→ 已执行
                        |
                        └──特殊取消──→ 已取消
```

| 当前状态 | 触发动作 | 目标状态 |
|---------|---------|---------|
| 待执行 | 开始执行(startExecute) | 执行中 |
| 执行中 | 结束执行(endExecute) | 已执行 |
| 执行中 | 特殊取消(specialCancel) | 已取消 |

#### 报错1：请选择一条数据
- **触发条件**：点击查看申请、查看确认书、特殊取消、结束执行、同步OA、同步FDD、同步CRM等行操作按钮时，未选择数据或选择了多行
- **逻辑分析**：前端在执行单选操作前校验选中行数量，若 selectedRows.length ≠ 1 则阻止操作并提示"请选择一条数据"。单选操作需要明确的目标申请，未选择时无法确定操作对象，多选时操作对象不唯一
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DISTRIBUTOR_NAME AS 申请人,
         ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE = 'approved'
  ORDER BY UPDATE_DATE DESC;
  ```

#### 报错2：只有在培训开始前七天内且已生效的单据才可以发起取消申请！
- **触发条件**：点击特殊取消按钮时，不满足"培训开始前1-7天内且已法大大签约"条件
- **逻辑分析**：前端执行多重校验：①计算时间差值 timeDiff = (ACTIVITY_START_DATE - nowTime) / (24*60*60*1000)，校验 1 <= timeDiff <= 7（培训开始前1-7天内）；②校验 APPROVAL_STATE = 'fdd_sign'（已法大大签约生效）。任一校验不通过则提示"只有在培训开始前七天内且已生效的单据才可以发起取消申请！"。此校验限制取消时机，避免临近开课取消造成资源浪费，同时要求单据已生效具备业务合法性
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         TO_CHAR(ACTIVITY_START_DATE,'YYYY-MM-DD') AS 活动开始时间,
         APPROVAL_STATE AS 审核状态,
         ROUND(ACTIVITY_START_DATE - SYSDATE) AS 距开始天数
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE = 'approved'
    AND (ACTIVITY_START_DATE <= SYSDATE
         OR ACTIVITY_START_DATE > SYSDATE + 7
         OR APPROVAL_STATE <> 'fdd_sign');
  ```

- **触发条件**：点击查看申请、特殊取消、结束执行、同步OA/FDD/CRM等按钮时，当前用户无对应 permissionList 权限码

- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名, R.ROLE_NAME AS 角色名, P.PERMISSION_CODE AS 权限码
  ```

### 常见问题

**Q1：执行跟踪页面能否修改数据？**
A：不能，本页面为只读跟踪页面，仅提供查询查看和执行结果回写功能。

**Q2：执行列表与活动点将管理列表有什么区别？**
A：活动点将管理列表展示所有状态的申请，执行列表仅展示已审批通过进入执行阶段的申请（`pageType=activity`）。

**Q3：特殊取消时机如何判断？**
A：培训开始前1-7天内且已法大大签约（`approvalState=fdd_sign`）的申请可发起特殊取消。

| 问题 | 排查方式 |
|------|---------|
| 列表无数据 | 检查 pageType=activity 参数，确认有执行中的活动点将 |
| 特殊取消按钮校验不通过 | 检查 ACTIVITY_START_DATE 与当前时间差值是否在1-7天，APPROVAL_STATE 是否为 fdd_sign |
| 结束执行失败 | 检查 realStartDate、realEndDate、endExecuteRemark 是否填写完整 |
| CRM同步失败 | 检查 sendCrmOrder 接口，确认经销商CRM映射存在 |
