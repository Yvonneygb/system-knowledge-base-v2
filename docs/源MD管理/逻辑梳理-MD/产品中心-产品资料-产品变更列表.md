# 产品中心-产品资料-产品变更列表

---

## 业务流程

### 业务流程图

```text
用户创建产品信息变更申请
        │
        ▼
  保存申请单（LNK_PROD_CHANGE_FORM + LNK_PROD_CHANGE_FORM_ITEM）
        │
        ├─── 变更类型：上下架（prodStatus）──→ 选择产品+上下架类型
        ├─── 变更类型：推广信息（popularizeMsg）──→ 选择产品+更新字段+更新内容
        ├─── 变更类型：关联产品（relateProd）──→ 选择产品+关联类型+关联产品+变更要求
        ├─── 变更类型：图册（prodPhoto）──→ 选择产品+图片类型+文件+变更要求
        └─── 变更类型：附件（prodFiles）──→ 选择产品+附件类型+文件+变更要求
        │
        ▼
  提交申请单 ──→ 校验（状态/在途单据/上下架产品/必填项）
        │
        ▼
  推送工作流引擎（WorkflowClient）
        │
        ├─── 审核通过 ──→ 执行变更：更新LNK_PROD/LNK_PROD_RELATE/OBJ_FILE_BUS_REL
        ├─── 审核拒绝 ──→ 状态回退，用户可修改后重新提交
        └─── 撤回 ──→ 状态回退至新建
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| LNK_PROD（产品主数据表） | 数据依赖 | 变更行中产品编码需存在于产品主数据表 | 产品已创建 |
| LNK_PROD_PROMOTE_GRADE_CONTROL（产品推广等级配置） | 数据依赖 | 上架校验时查询产品必填字段配置 | 上架/特殊新品上架提交时 |
| LNK_PRICE_APP_FORM（价目表申请单） | 数据依赖 | 上架校验关联老款产品是否有有效折扣政策 | 上架/特殊新品上架提交时 |
| EBS产品政策接口 | 数据依赖 | 查询关联老款产品可售月份 | 上架校验时 |
| 编码规则（PROD_CHANGE_FORM_CODE） | 配置依赖 | 新增申请单时自动生成申请单号 | 新增保存时 |
| 工作流引擎（WorkflowClient） | 服务依赖 | 提交时启动流程实例，审批回调更新状态 | 提交时 |
| 值集（LOV） | 配置依赖 | 申请类型、状态、变更类型等字段依赖值集翻译 | 值集数据已配置 |

### 下游影响

- 影响1：产品上下架状态
  - 审核通过后，更新LNK_PROD.PROD_STATUS字段（上架/下架/特殊新品上架）

- 影响2：产品推广信息
  - 审核通过后，更新LNK_PROD.SHOW_STANDARD（展陈标准）等推广信息字段

- 影响3：关联产品关系
  - 审核通过后，新增或删除LNK_PROD_RELATE关联产品记录

- 影响4：产品图册/附件
  - 审核通过后，新增或删除OBJ_FILE_BUS_REL文件关联记录

## 重点逻辑

### 重点逻辑1：申请单号自动生成 `编码规则`

- **业务意义**：新增申请单时自动生成唯一申请单号，无需用户手动输入

- **具体逻辑描述**

  - 第1点：新增保存时，通过编码规则PROD_CHANGE_FORM_CODE自动生成申请单号（formCode）

  - 第2点：申请单号生成后不可编辑，详情页该字段始终禁用

### 重点逻辑2：提交前多重校验 `提交校验`

- **业务意义**：确保变更申请数据完整、产品状态允许变更、无在途冲突单据

- **具体逻辑描述**

  - 第1点：校验申请单状态——仅"新建"和"审核拒绝"状态可提交，其他状态报错

  - 第2点：校验在途单据——变更涉及的产品编码若已在其他审批中的申请单内，报错提示具体产品、申请单号和申请人

  - 第3点：校验上下架产品——调用产品服务校验产品生命状态是否允许上架（Z1/Z8不允许上架，Z3/Z6/Z7/S6需确认上架）

  - 第4点：校验上架必填项——根据产品推广等级配置表，校验上架产品的基础信息、图册、附件等必填字段是否已填写

  - 第5点：校验变更行非空——变更行不能为空，否则报错"变更单行为空，不允许提交"

### 重点逻辑3：工作流审批回调处理 `审批回调`

- **业务意义**：审批通过后自动执行变更内容，将变更应用到产品主数据

- **具体逻辑描述**

  - 第1点：审批通过/结束时，按变更类型分组执行变更操作

  - 第2点：上下架变更——更新LNK_PROD.PROD_STATUS，特殊新品上架（UPPERSPECIALPROD）转为正常上架（UPPERSHELF）

  - 第3点：推广信息变更——更新LNK_PROD.SHOW_STANDARD（展陈标准）

  - 第4点：关联产品变更——先删除再新增LNK_PROD_RELATE记录

  - 第5点：图册/附件变更——先删除再新增OBJ_FILE_BUS_REL文件关联记录

  - 第6点：撤回时状态回退至"新建"，审核拒绝时状态更新为"审核拒绝"

### 重点逻辑4：五种变更类型 `业务分类`

- **业务意义**：产品信息变更按类型分为五大类，每类变更的数据结构和处理逻辑不同

- **具体逻辑描述**

  - 第1点：上下架（prodStatus）——变更产品上/下架状态，含正常上架、下架、特殊新品上架

  - 第2点：推广信息（popularizeMsg）——变更产品推广相关字段，如展陈标准

  - 第3点：关联产品（relateProd）——新增或删除产品间的关联关系

  - 第4点：图册（prodPhoto）——新增或删除产品图片

  - 第5点：附件（prodFiles）——新增或删除产品附件文件

### 提交校验

- 校验1：申请单状态校验 —— 仅新建和审核拒绝状态可提交

  - 详细逻辑

    - 第1点：查询申请单当前状态，若非NEW且非REJECTED则报错

  - 系统体现：阻断性报错"申请单状态为不为新建或审核拒绝，不可提交！"

  - 排查SQL：

    ```sql
    SELECT STATUS FROM LNK_PROD_CHANGE_FORM WHERE ID = :formId;
    ```

- 校验2：在途单据校验 —— 变更产品不可在其他审批中的申请单内

  - 详细逻辑

    - 第1点：查询当前申请单变更行涉及的产品编码，检查这些产品是否在其他状态为"审批中"的申请单中
    - 第2点：若存在在途单据，报错提示具体产品编码、申请单号和申请人

  - 系统体现：阻断性报错"变更单涉及产品【xxx】所在申请单【xxx】申请人【xxx】正在审批中。请审完在途单据再提交新的申请..."

  - 排查SQL：

    ```sql
    -- 查询在途单据
    SELECT DISTINCT I.PROD_CODE, F.FORM_CODE, F.CREATED_BY
    FROM LNK_PROD_CHANGE_FORM F
      JOIN LNK_PROD_CHANGE_FORM_ITEM I ON F.ID = I.HEAD_ID
    WHERE F.STATUS = 'RUN'
      AND F.ID <> :currentFormId
      AND I.PROD_CODE IN (
        SELECT PROD_CODE FROM LNK_PROD_CHANGE_FORM_ITEM WHERE HEAD_ID = :currentFormId
      );
    ```

- 校验3：上下架产品状态校验 —— 产品生命状态允许上架

  - 详细逻辑

    - 第1点：Z1、Z8状态产品不允许上架
    - 第2点：Z3、Z6、Z7、S6状态产品需确认上架（前端二次确认）
    - 第3点：Z5状态产品允许上架
    - 第4点：上架产品需校验关联老款产品是否有有效折扣政策

  - 系统体现：阻断性报错/确认弹窗

  - 排查SQL：

    ```sql
    -- 查询产品生命状态
    SELECT PROD_CODE, SM_STATE FROM LNK_PROD WHERE PROD_CODE IN (:prodCodeList);
    ```

- 校验4：上架必填项校验 —— 根据推广等级配置校验必填字段

  - 详细逻辑

    - 第1点：查询产品推广等级配置表，获取上架产品需必填的字段列表
    - 第2点：检查产品基础信息、图册、附件等必填字段是否已填写
    - 第3点：若变更单中已包含该字段的变更，则视为已填写

  - 系统体现：阻断性报错"产品<xxx>的xxx的值为空，不可上架"

  - 排查SQL：

    ```sql
    -- 查询产品推广等级配置
    SELECT * FROM LNK_PROD_PROMOTE_GRADE_CONTROL WHERE PROD_CODE IN (:prodCodeList);
    ```

- 校验5：变更行非空校验

  - 详细逻辑

    - 第1点：查询变更行数据，若为空则报错

  - 系统体现：阻断性报错"变更单行为空，不允许提交"

  - 排查SQL：

    ```sql
    SELECT COUNT(1) FROM LNK_PROD_CHANGE_FORM_ITEM WHERE HEAD_ID = :formId;
    ```

#### 状态机流转图

```text

  │   新建    │──────→│  审批中   │──────────→│ 审核通过  │
```

#### 报错1：申请单状态为不为新建或审核拒绝，不可提交！
- **触发条件**：详情页点击"提交"按钮时，后端校验申请单当前状态
- **逻辑分析**：后端提交接口先查询LNK_PROD_CHANGE_FORM.STATUS，仅允许NEW（新建）和REJECTED（审核拒绝）状态提交。其他状态（RUN审批中/APPROVED审核通过）提交会抛出CommonException。常见于并发场景：多人同时操作同一申请单，或前端状态未及时刷新。
- **排查SQL**：
  ```sql
  SELECT F.ID, F.FORM_CODE, F.STATUS, F.HZ_APPROVE_STATUS,
         F.LAST_UPDATED_BY, F.LAST_UPDATE_DATE
  FROM LNK_PROD_CHANGE_FORM F
  WHERE F.ID = :formId;
  ```

#### 报错2：变更单涉及产品【xxx】所在申请单【xxx】申请人【xxx】正在审批中
- **触发条件**：提交时校验在途单据，变更行产品已在其他审批中的申请单内
- **逻辑分析**：后端查询当前申请单所有变更行的产品编码集合，再查询其他STATUS='RUN'的申请单中是否包含相同产品。若存在则提示具体产品编码、申请单号和申请人，避免同一产品被多个变更单同时变更造成冲突。
- **排查SQL**：
  ```sql
  SELECT DISTINCT I.PROD_CODE AS 产品编码, F.FORM_CODE AS 申请单号,
         F.CREATED_BY AS 申请人, F.STATUS AS 状态
  FROM LNK_PROD_CHANGE_FORM F
    JOIN LNK_PROD_CHANGE_FORM_ITEM I ON F.ID = I.HEAD_ID
  WHERE F.STATUS = 'RUN'
    AND F.ID <> :currentFormId
    AND I.PROD_CODE IN (
      SELECT PROD_CODE FROM LNK_PROD_CHANGE_FORM_ITEM WHERE HEAD_ID = :currentFormId
    );
  ```

#### 报错3：变更单行为空，不允许提交
- **触发条件**：提交时校验变更行非空，申请单无任何变更行数据
- **逻辑分析**：后端根据HEAD_ID查询LNK_PROD_CHANGE_FORM_ITEM表，若COUNT为0则抛出异常。常见于用户新建申请单后未添加任何变更行就点击提交。
- **排查SQL**：
  ```sql
  SELECT F.FORM_CODE, F.STATUS,
  ```

### 常见问题

- 问题1：提交后申请类型自动变化
  - 原因：提交时后端根据变更行类型自动汇总FORM_TYPE字段，覆盖原有值
  - 解决思路：这是正常逻辑，申请类型由变更行内容决定

- 问题2：审核通过后产品状态未变更
  - 原因：可能工作流回调未成功执行，或变更行CHANGE_CONTENT值不正确
  - 解决思路：
    ```sql
    -- 检查变更行数据
    SELECT I.PROD_CODE, I.CHANGE_TYPE, I.CHANGE_CONTENT, F.STATUS
    FROM LNK_PROD_CHANGE_FORM F
      JOIN LNK_PROD_CHANGE_FORM_ITEM I ON F.ID = I.HEAD_ID
    WHERE F.ID = :formId AND F.STATUS = 'APPROVED';
    ```

- 问题3：特殊新品上架后变为普通上架
  - 原因：审批回调时，UPPERSPECIALPROD类型会自动转为UPPERSHELF写入产品表
  - 解决思路：这是正常逻辑，特殊新品上架审批通过后即转为正常上架状态
