### 流程说明

1. **查询阶段**：选择要货订单后，校验该订单下是否存在可发起插单的紧急要货行数据
2. **选择阶段**：用户选择"申请行"（调增方）和"调整行"（调减方），填写调整数量
3. **校验阶段**：按申请行分组校验总调整数量不超过预占数量，单行校验调整数量不超过调整行的保留数量
4. **推送ERP**：校验通过的数据调用ERP插单接口（`EpmUrgentAdjustInft`），ERP执行库存调整并返回结果
5. **本地更新**：ERP成功后更新保留/预占数量、插入库存保留记录和插单留档记录、对调整行发送库存占用申请
6. **即时操作**：无审批节点，执行即生效

## 重点逻辑

### 重点逻辑1：插单数据校验

- **业务意义**：确保插单数据合法，避免无效插单
- **具体逻辑描述**：
  1. 校验原始要货行是否存在可插单的产品行数据
  2. 若订单号不存在可插单的产品行数据，阻断性报错"该订单号不存在可发起紧急要货插单的产品行数据"
  3. 同时查询紧急要货行的延期状态（`selectUrgentExtendStatus`）

### 重点逻辑2：分组数量校验

- **业务意义**：确保同一申请行的总调整数量不超过其预占数量
- **具体逻辑描述**：
  1. 按`urgentOrderLineId`分组，计算每组所有`adjustAdjustQty`之和
  2. 若总和超过该行的`preReservedQty`（预占数量），则该组所有行标记错误
  3. 错误信息："该记录的数量目前已不符合调整需求，请检查。"

### 重点逻辑3：单行数量校验

- **业务意义**：确保单行调整数量不超过调整行的保留数量
- **具体逻辑描述**：
  1. 校验`adjustAdjustQty ≤ adjustReservedQty`（调整行的保留数量）
  2. 超过则标记错误，不推送ERP
  3. 通过的行加入推送列表

### 重点逻辑4：ERP推送执行插单

- **业务意义**：插单请求通过ERP接口执行实际的库存调整
- **具体逻辑描述**：
  1. 查询推送数据（`queryPushData`）获取CRM订单信息（头ID、行ID）
  2. 获取库存保留有效期系统参数（`VALIDITY_OF_STOCK_RETENTION`）
  3. 组装申请行和调整行数据，调用`EpmUrgentAdjustInft.urgentAdjustData`
  4. 调用`invoke`发送ERP请求（接口编码`URGENT_ADJUST_INFT`）
  5. 解析ERP返回：`L_RET_STATUS`、`L_RET_MESSAGE`、`EFFECTIVE_DATE_TO`

### 重点逻辑5：本地数据联动更新

- **业务意义**：ERP成功后需同步更新本地多处数据
- **具体逻辑描述**：
  1. 更新申请行：`RESERVED_QTY += adjustQty`，`PRE_RESERVED_QTY -= adjustQty`
  2. 更新调整行：`RESERVED_QTY += adjustQty`，`PRE_RESERVED_QTY -= adjustQty`
  3. 插入`EPM_URGENT_ORDER_LINE_STOCK`库存保留记录（申请行正数，调整行负数且`RELEASED_TYPE='插单'`）
  4. 插入`EPM_URGENT_ADJUST`留档记录（申请行`ADJUST_TYPE='+'`，调整行`ADJUST_TYPE='-'`，通过`REL_ADJUST_ID`互相关联）

### 重点逻辑6：补充库存占用

- **业务意义**：调整行被调走库存后，需向ERP重新申请库存占用以补充库存
- **具体逻辑描述**：
  1. 对调整行（被调减方）查询库存占用申请数据（`selectReserveApply`）
  2. 调用`ReserveApplyInft.reserveApplyData`发送库存占用申请
  3. 解析ERP返回，更新`EPM_URGENT_ADJUST`的`RESERVED_INTF_RESULT`和`RESERVED_INTF_INFO`

#### 按钮1：查询要货行数据（详情页）

- **触发条件**：选择要货单后
- **处理逻辑**：
  1. 调用`GET /v1/{organizationId}/epm-urgent-adjusts/get-sa-out-bill-data`
  2. 后端执行`EpmUrgentAdjustServiceImpl.getSaOutBillData`方法
  3. 从用户附加信息获取组织ID（`DEPT`字段，默认`DIVISION_101`）
  4. 分页查询可发起插单的紧急要货行数据

#### 按钮2：校验插单数据（详情页）

- **触发条件**：填写插单数据后
- **处理逻辑**：
  1. 调用`GET /v1/{organizationId}/epm-urgent-adjusts/verify-data`
  2. 后端执行`EpmUrgentAdjustServiceImpl.verifyData`方法
  3. 查询延期状态（`selectUrgentExtendStatus`）和可插单数据（`getSaOutBillData`）
  4. 若无可插单数据，抛出异常"该订单号不存在可发起紧急要货插单的产品行数据"

#### 按钮3：发送插单请求（详情页）

- **触发条件**：校验通过后
- **处理逻辑**：
  1. 调用`POST /v1/{organizationId}/epm-urgent-adjusts/push-adjust`，传入`List<EpmUrgentAdjustDTO>`
  2. 后端执行`EpmUrgentAdjustServiceImpl.pushAdjust`方法
  3. 批量查询申请行和调整行数据，刷新数量信息
  4. 分组校验和单行校验
  5. 校验通过的数据调用`doAdjust`推送ERP
  6. ERP成功后更新本地数据、插入留档记录、发送库存占用申请
  7. 返回成功列表和失败列表

### 提交校验

- 校验1：插单数据必须存在 —— 确保插单操作有有效数据
  - **详细逻辑**：校验原始要货行是否存在可插单的产品行数据，若不存在则阻断
  - **系统体现**：`EpmUrgentAdjustServiceImpl.verifyData`第186-188行，抛出`CommonException("该订单号不存在可发起紧急要货插单的产品行数据。")`
  - **排查SQL**：
    ```sql
    SELECT * FROM EPM_URGENT_ORDER_LINE el
    LEFT JOIN EPM_URGENT_ORDER eo ON eo.URGENT_ORDER_ID = el.URGENT_ORDER_ID
    WHERE eo.SA_OUT_BILL_HEAD_ID = :saOutBillHeadId
      AND el.INTF_RESULT = 'S';
    ```

- 校验2：同一申请行总调整数量不超过预占数量 —— 确保调增数量合理
  - **详细逻辑**：按`urgentOrderLineId`分组，若所有`adjustAdjustQty`之和超过`preReservedQty`则该组全部标记错误
  - **系统体现**：`EpmUrgentAdjustServiceImpl.pushAdjust`第139-151行，非阻断性标记，该组行不推送ERP
  - **排查SQL**：
    ```sql
    SELECT URGENT_ORDER_LINE_ID, PRE_RESERVED_QTY,
      SUM(:adjustAdjustQty) AS total_adjust
    FROM EPM_URGENT_ORDER_LINE
    WHERE URGENT_ORDER_LINE_ID = :urgentOrderLineId
    GROUP BY URGENT_ORDER_LINE_ID, PRE_RESERVED_QTY;
    ```

- 校验3：单行调整数量不超过调整行保留数量 —— 确保调减数量合理
  - **详细逻辑**：校验`adjustAdjustQty ≤ adjustReservedQty`，超过则标记错误
  - **系统体现**：`EpmUrgentAdjustServiceImpl.pushAdjust`第158-166行，非阻断性标记，该行不推送ERP
  - **排查SQL**：
    ```sql
    SELECT URGENT_ORDER_LINE_ID, RESERVED_QTY
    FROM EPM_URGENT_ORDER_LINE
    WHERE URGENT_ORDER_LINE_ID = :adjustUrgentOrderLineId;
    ```

### 下游影响

- **紧急要货行数量**：更新申请行和调整行的`RESERVED_QTY`和`PRE_RESERVED_QTY`
- **库存保留记录**：插入`EPM_URGENT_ORDER_LINE_STOCK`，申请行正数、调整行负数（`RELEASED_TYPE='插单'`）
- **插单留档记录**：插入`EPM_URGENT_ADJUST`，申请行（`ADJUST_TYPE='+'`）和调整行（`ADJUST_TYPE='-'`）成对记录
- **库存占用申请**：对调整行调用`ReserveApplyInft`发送库存占用申请，补充被调走的库存

#### 报错1：该订单号不存在可发起紧急要货插单的产品行数据
- **触发条件**：查询可插单产品行时，要货单下无符合条件的紧急要货行
- **逻辑分析**：查询方法中按SA_OUT_BILL_HEAD_ID关联EPM_URGENT_ORDER_LINE，筛选STAT=5(已审批通过)、INTF_RESULT='S'(接口成功)、未失效等条件，若为空则抛出阻断性报错
- **排查SQL**：
  ```sql
  SELECT euol.URGENT_ORDER_LINE_ID, euol.URGENT_ORDER_HEAD_ID, euol.ITEM_CODE,
         euol.STAT, euol.INTF_RESULT, euol.IS_CANCEL, euol.PRE_RESERVED_QTY
  FROM EPM_URGENT_ORDER_LINE euol
  WHERE euol.SA_OUT_BILL_HEAD_ID = :saOutBillHeadId
    AND euol.STAT = 5
    AND euol.INTF_RESULT = 'S'
    AND euol.IS_CANCEL <> 2
    AND euol.PRE_RESERVED_QTY > 0
  -- 若返回空，说明无可插单的产品行
  ```

#### 报错3：同一申请行总调整数量超过预占数量
- **触发条件**：提交插单时，同一申请行(ADJUST_TYPE='+')的所有调整数量之和超过该行的预占数量(PRE_RESERVED_QTY)
- **逻辑分析**：提交校验中按申请行汇总调整数量，若超过预占数量则抛出阻断性报错。说明操作期间数据已发生变化，需调整调增数量
- **排查SQL**：
  ```sql
  SELECT eua.URGENT_ADJUST_ID, eua.URGENT_ORDER_LINE_ID, eua.ADJUST_TYPE, eua.ADJUST_QTY,
         euol.PRE_RESERVED_QTY,
         SUM(eua.ADJUST_QTY) OVER(PARTITION BY eua.URGENT_ORDER_LINE_ID) AS 申请行总调整数量

  JOIN EPM_URGENT_ORDER_LINE euol ON eua.URGENT_ORDER_LINE_ID = euol.URGENT_ORDER_LINE_ID
  WHERE eua.URGENT_ADJUST_ID = :urgentAdjustId
    AND eua.ADJUST_TYPE = '+'
  -- 对比申请行总调整数量与预占数量
  ```

- **逻辑分析**：提交校验中按调整行检查ADJUST_QTY≤保留数量，若超过则抛出阻断性报错。需调整调减数量

#### 报错6：ERP返回EFFECTIVE_DATE_TO为空
- **触发条件**：插单推送ERP成功(L_RET_STATUS=S)后，ERP返回的X_RESERVE_OUT_TBL_ITEM中EFFECTIVE_DATE_TO字段为空
- **逻辑分析**：doAdjust方法中解析ERP返回的X_RESERVE_OUT_TBL_ITEM数组，对申请行和调整行分别取EFFECTIVE_DATE_TO作为库存保留有效期。若任一行的EFFECTIVE_DATE_TO为空字符串，则将status置为E，msg置为"EFFECTIVE_DATE_TO返回为空"。该报错为非阻断性，仅标记当前行失败，不影响其他行。常见原因：ERP侧库存未配置有效期、库存已被释放
- **排查SQL**：
  ```sql
  SELECT eua.URGENT_ADJUST_ID, eua.ADJUST_TYPE, eua.PROCCUSE_STATUS, eua.PROCESS_MESSAG,
         eua.APPLY_DATE, eua.ADJUST_DATE
  FROM EPM_URGENT_ADJUST eua
  WHERE eua.URGENT_ADJUST_ID = :urgentAdjustId
    AND eua.PROCCUSE_STATUS = 'E'
    AND eua.PROCESS_MESSAG LIKE '%EFFECTIVE_DATE_TO返回为空%'
  -- 查出ERP返回有效期为空的插单记录
  ```

#### 报错7：库存占用申请ERP返回数据校验失败
- **触发条件**：插单成功后对调整行发送库存占用申请(ReserveApplyInft)，ERP返回的X_RESERVE_OUT_TBL_ITEM数据校验失败
- **逻辑分析**：doReserveApply方法中调用ERP库存占用接口后，reserveFeedbackProcess方法逐行校验ERP返回数据，任一校验失败则收集错误信息并抛出RuntimeException。具体校验项包括：(1)CRM_LINE_ID为空→"未传递订单行ID"；(2)CRM_LINE_ID在紧急要货库存保留表中不存在→"未申请紧急要货"；(3)RESERVED_QUANTITY为空→"未传递[占用数量]"；(4)PRE_RESERVED_QUANTITY为空→"未传递[预占用数量]"；(5)RESERVED_TIME无法解析→"[占用时间]不是有效时间"；(6)EFFECTIVE_DATE_TO为空或无法解析→"未传递[有效期至]"。该报错为阻断性，会中断当前调整行的库存占用处理
- **排查SQL**：
  ```sql
  SELECT eua.URGENT_ADJUST_ID, eua.ADJUST_TYPE, eua.RESERVED_INTF_RESULT, eua.RESERVED_INTF_INFO,
         euol.EXT_SA_OUT_BILL_LINE_ID, euol.ITEM_CODE
  FROM EPM_URGENT_ADJUST eua
  JOIN EPM_URGENT_ORDER_LINE euol ON eua.URGENT_ORDER_LINE_ID = euol.URGENT_ORDER_LINE_ID
  WHERE eua.ADJUST_TYPE = '-'
    AND eua.RESERVED_INTF_RESULT = 'E'
  -- 查出库存占用申请失败的调整行及错误信息
  ```

**Q1：为什么提示"该订单号不存在可发起紧急要货插单的产品行数据"？**
A：该要货单下没有符合条件的紧急要货行（可能未审批通过、接口未成功、已失效等）。

**Q2：为什么提示"该记录的数量目前已不符合调整需求"？**
A：(1) 同一申请行的所有调整数量之和超过了该行的预占数量；(2) 单行调整数量超过了调整行的保留数量。说明在操作期间数据已发生变化。

**Q3：插单成功后调整行为什么还要发送库存占用申请？**
A：调整行被调走库存后，需要向ERP重新申请库存占用以补充库存，确保调整行的要货需求仍能满足。

**Q4：插单记录中ADJUST_TYPE的"+"和"-"分别代表什么？**
A："+"表示申请行（调增方，库存保留数量增加），"-"表示调整行（调减方，库存保留数量减少）。两者通过`REL_ADJUST_ID`互相关联。

**Q5：插单推送ERP失败？**
A：ERP接口不可用或网络问题。检查ERP接口`URGENT_ADJUST_INFT`状态，修复后重试。
