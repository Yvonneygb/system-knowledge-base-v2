# 门店管理-广告投放-广告报销发票兑现

## 业务流程

### 业务流程图

```text
广告费报销单        新建发票兑现        保存兑现单         提交审批          审批通过
(已审批通过)  →   选择兑现类型   →   填写兑现金额  →   校验金额    →   更新额度外预算
                 额度内/额度外       关联报销发票       推送工作流       回写交易公司
                                                       ↓
                                                  审批通过→同步ERP资金池
                                                          →推送MBO
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|------------|
| 广告费报销 | 数据依赖 | 提供已审批通过的报销单、可兑现总额、发票信息 | 报销单已审批通过 |
| 广告投放申请 | 数据依赖 | 额度内兑现时回写申请单的交易公司 | 申请单已审批通过 |
| 额度内资源额度 | 数据依赖 | 提供额度内可用金额 | 年度资源额度已配置 |
| 额度外预算 | 数据依赖 | 提供额度外可用金额、已占用金额 | 额度外预算已配置 |
| ERP系统 | 数据依赖 | 同步资金池调整数据 | ERP接口可用 |
| MBO系统 | 数据依赖 | 推送兑现数据到MBO | MBO接口可用 |
| 工作流引擎 | 配置依赖 | 发起审批流程ADJ_GGBXFPDX | 工作流已部署 |

### 下游影响

- 影响1：额度外预算更新
  - 额度外(cashoutType=2)审批通过后更新额度外预算已使用金额

- 影响2：ERP资金池调整
  - 审批通过后同步资金池调整数据到ERP

- 影响3：MBO推送
  - 审批通过后推送兑现数据到MBO系统

- 影响4：申请单交易公司回写
  - 额度内(cashoutType=1)审批通过后回写申请单和报销单的交易公司

- 影响5：验收单交易公司回写
  - 额度内审批通过后回写验收单的可用交易公司

## 重点逻辑

### 重点逻辑1：额度内与额度外兑现区分 {兑现类型}

- **业务意义**：兑现分为额度内和额度外，校验和预算处理逻辑不同

- **具体逻辑描述**

  - 第1点：cashoutType=1为额度内，校验本次核销金额不超过额度内可用金额

  - 第2点：cashoutType=2为额度外，校验本次兑现金额不超过额度外可用金额-已占用金额

  - 第3点：额度外审批通过后更新额度外预算已使用金额，按月份区分当年/次年

### 重点逻辑2：兑现金额校验 {核心校验}

- **业务意义**：确保兑现金额不超过剩余可兑现金额

- **具体逻辑描述**

  - 第1点：本次兑现金额<=可兑现总额-已兑现总额

  - 第2点：支付方式非3（非虚拟收款）时，发票金额必须>0

  - 第3点：提交时校验申请兑现金额不超过剩余未兑现总额

### 重点逻辑3：ERP资金池同步 {ERP集成}

- **业务意义**：审批通过后同步资金池调整到ERP

- **具体逻辑描述**

  - 第1点：组装资金池数据（源单据ID、交易公司、客户、金额等）

  - 第2点：额度内sourceType="广告费（额内）"，额度外sourceType="广告费（额外）"

  - 第3点：调用ERP接口cashPoolAdjust，返回ProcessStatus=S表示成功

### 重点逻辑4：额度外预算更新 {预算控制}

- **业务意义**：额度外兑现审批通过后更新预算已使用金额

- **具体逻辑描述**

  - 第1点：按当前月份更新对应的预算字段（当年this_outlimit_bud_used_月/次年next_outlimit_bud_used_月）

  - 第2点：使用金额=原已使用+本次申请金额×兑现比例，再除以税率

  - 第3点：最终兑现(isEnd=2)时将额度外预算剩余置为0

### 重点逻辑5：电子签章校验 {签章}

- **业务意义**：确保单据已完成电子签章才能继续流程

- **具体逻辑描述**

  - 第1点：校验签章状态(signatureState)是否为2（?（已签章）

  - 第2点：已签章但需重签(isResign=2)时返回false

### 保存校验

- 校验1：发票金额校验 —— 确保发票金额大于0

  - 详细逻辑

    - 第1点：支付方式非3（非虚拟收款）时，实际兑现金额(factInvoiceAmt)必须>0

    - 第2点：金额<=0时报错"发票金额异常，请检查！"

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT pay_type, fact_invoice_amt FROM fin_fee_cashout_header WHERE fee_cashout_id = {id};
    ```

- 校验2：剩余可兑现金额校验 —— 确保兑现金额不超剩余

  - 详细逻辑

    - 第1点：剩余可兑现金额=可兑现总额-已兑现总额

    - 第2点：本次兑现金额>剩余可兑现金额时报错

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT total_can_cashout_amt, used_cashout_amt, this_cashout_amt FROM fin_fee_cashout_header WHERE fee_cashout_id = {id};
    ```

- 校验3：额度内可用金额校验 —— 额度内核销金额不超可用

  - 详细逻辑

    - 第1点：兑现类型=额度内时，本次核销金额<=额度内可用金额

    - 第2点：超出时报错"本次核销金额不可超过额度内可用金额"

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT this_writeoff_amt, in_can_use_amt FROM fin_fee_cashout_header WHERE fee_cashout_id = {id} AND cashout_type = 1;
    ```

- 校验4：额度外可用金额校验 —— 额度外兑现金额不超可用

  - 详细逻辑

    - 第1点：兑现类型=额度外时，本次兑现金额<=额度外可用金额-已占用金额

    - 第2点：超出时报错"额度外金额已占用"

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT this_cashout_amt, out_can_use_amt FROM fin_fee_cashout_header WHERE fee_cashout_id = {id} AND cashout_type = 2;
    ```

### 提交校验

- 校验1：剩余未兑现总额校验 —— 确保申请金额不超剩余

  - 详细逻辑

    - 第1点：查询已使用兑现金额

    - 第2点：可兑现总额-已使用-本次兑现<0时报错

  - 系统体现：阻断性报错

  - 排查SQL：

    ```sql
    SELECT total_can_cashout_amt, this_cashout_amt FROM fin_fee_cashout_header WHERE fee_cashout_id = {id};
    ```

### 状态机

#### 状态机流转图

```text
NEW(新建) ──提交──→ RUN(审批中) ──审批通过──→ APPROVED(已审核)
                        │
                        │审批驳回
                        ↓
                   回到NEW
```

#### 状态机列表

| 状态机名称 | 状态释义 | 可执行的操作 |
|-----------|---------|------------|
| NEW | 新建，未提交 | 编辑、保存、提交、电子签章 |
| RUN | 审批中，工作流运行中 | 无（等待审批结果） |
| APPROVED | 已审核，审批通过 | 打印 |

#### 报错1：发票金额异常，请检查！
- **触发条件**：点击"提交"或"保存"按钮，支付方式非3（非虚拟收款）时，校验发票实际兑现金额factInvoiceAmt<=0
- **逻辑分析**：兑现单需有有效发票金额才能进行核销与预算更新。校验逻辑读取FIN_FEE_CASHOUT_HEADER.FACT_INVOICE_AMT，当PAY_TYPE≠3且FACT_INVOICE_AMT<=0时抛出阻断性异常。常见根因：用户未填写发票金额、发票金额被错误置0或负数、或前端未做必填校验直接提交空单。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         pay_type            AS 支付方式,
         fact_invoice_amt    AS 实际兑现金额,
         hz_approve_status   AS 审批状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    pay_type <> 3
  AND    (fact_invoice_amt IS NULL OR fact_invoice_amt <= 0)
  ORDER  BY create_time DESC;
  ```

#### 报错2：本次申请兑现金额不可超过该报销单据剩余的可兑现金额
- **触发条件**：点击"提交"按钮，校验本次兑现金额thisCashoutAmt>报销单剩余可兑现金额（TOTAL_CAN_CASHOUT_AMT-USED_CASHOUT_AMT）
- **逻辑分析**：兑现金额受报销单可兑现总额约束。校验逻辑从关联报销单FIN_FEE_BX_HEADER读取可兑现总额与已兑现总额，若本次兑现金额超过剩余可兑现（可兑现总额-已兑现总额）则抛异常。常见根因：用户输入金额超限、报销单已被其他兑现单占用部分额度、或前端未实时刷新剩余可兑现金额。
- **排查SQL**：
  ```sql
  SELECT c.fee_cashout_id      AS 兑现单ID,
         c.fee_cashout_no      AS 兑现单号,
         c.bx_no               AS 报销单号,
         c.this_cashout_amt    AS 本次兑现金额,
         c.total_can_cashout_amt AS 可兑现总额,
         c.used_cashout_amt    AS 已兑现总额,
         c.total_can_cashout_amt - c.used_cashout_amt AS 剩余可兑现
  FROM   fin_fee_cashout_header c
  WHERE  c.save_type = 2
  AND    c.this_cashout_amt > (c.total_can_cashout_amt - c.used_cashout_amt)
  ORDER  BY c.create_time DESC;
  ```

#### 报错3：本次核销金额不可超过额度内可用金额
- **触发条件**：点击"提交"按钮，兑现类型为额度内（CASHOUT_TYPE=1）时，校验本次核销金额thisWriteoffAmt>额度内可用金额inCanUseAmt
- **逻辑分析**：额度内兑现需核销资源额度，核销金额不能超过当前可用额度。校验逻辑读取FIN_FEE_CASHOUT_HEADER.THIS_WRITEOFF_AMT与IN_CAN_USE_AMT，当CASHOUT_TYPE=1且THIS_WRITEOFF_AMT>IN_CAN_USE_AMT时抛异常。常见根因：资源额度已被其他单据占用、额度未及时刷新、或用户输入核销金额超限。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         cashout_type        AS 兑现类型,
         this_writeoff_amt   AS 本次核销金额,
         in_can_use_amt      AS 额度内可用金额,
         hz_approve_status   AS 审批状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    cashout_type = 1
  AND    this_writeoff_amt > in_can_use_amt
  ORDER  BY create_time DESC;
  ```

#### 报错4：本次申请兑现金额不可超过额度外可用金额
- **触发条件**：点击"提交"按钮，兑现类型为额度外（CASHOUT_TYPE=2）时，校验本次兑现金额thisCashoutAmt>额度外可用金额outCanUseAmt
- **逻辑分析**：额度外兑现受额度外预算可用金额约束。校验逻辑读取FIN_FEE_CASHOUT_HEADER.THIS_CASHOUT_AMT与OUT_CAN_USE_AMT，当CASHOUT_TYPE=2且THIS_CASHOUT_AMT>OUT_CAN_USE_AMT时抛异常。常见根因：额度外预算已使用较多、可用金额未及时刷新、或用户输入兑现金额超限。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         cashout_type        AS 兑现类型,
         this_cashout_amt    AS 本次兑现金额,
         out_can_use_amt     AS 额度外可用金额,
         hz_approve_status   AS 审批状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    cashout_type = 2
  AND    this_cashout_amt > out_can_use_amt
  ORDER  BY create_time DESC;
  ```

#### 报错5：额度外金额已占用
- **触发条件**：点击"提交"按钮，兑现类型为额度外（CASHOUT_TYPE=2）时，校验本次兑现金额>额度外可用金额-已占用金额
- **逻辑分析**：额度外可用金额需扣除已被其他单据占用部分。校验逻辑查询MKT_OUTLIMIT_BUD_HEADER的已占用金额，若本次兑现金额超过剩余可用（可用金额-已占用金额）则抛异常。常见根因：并发提交导致额度外可用金额被其他兑现单占用、或前端未实时获取最新已占用金额。
- **排查SQL**：
  ```sql
  SELECT c.fee_cashout_id      AS 兑现单ID,
         c.fee_cashout_no      AS 兑现单号,
         c.this_cashout_amt    AS 本次兑现金额,
         c.out_can_use_amt     AS 额度外可用金额,
         b.this_outlimit_bud_used_amt AS 已占用金额,
         c.out_can_use_amt - b.this_outlimit_bud_used_amt AS 剩余可用
  FROM   fin_fee_cashout_header c
  LEFT   JOIN mkt_outlimit_bud_header b
         ON b.terminal_code = c.terminal_code
        AND b.bud_year = c.bud_year
  WHERE  c.save_type = 2
  AND    c.cashout_type = 2
  AND    c.this_cashout_amt > (c.out_can_use_amt - NVL(b.this_outlimit_bud_used_amt, 0))
  ORDER  BY c.create_time DESC;
  ```

#### 报错6：申请兑现金额已超剩余未兑现总额
- **触发条件**：点击"提交"按钮，提交时二次校验可兑现总额-已使用兑现金额-本次兑现金额<0
- **逻辑分析**：提交时再次校验防止并发兑现导致超额。校验逻辑重新查询关联报销单的已使用兑现金额，若可兑现总额-已使用-本次兑现<0则抛异常。常见根因：多用户并发对同一报销单提交兑现、或保存后到提交期间其他兑现单已占用额度，需刷新后重新提交。
- **排查SQL**：
  ```sql
  SELECT c.fee_cashout_id      AS 兑现单ID,
         c.fee_cashout_no      AS 兑现单号,
         c.bx_id               AS 报销单ID,
         c.total_can_cashout_amt AS 可兑现总额,
         c.used_cashout_amt    AS 已兑现总额,
         c.this_cashout_amt    AS 本次兑现金额,
         c.total_can_cashout_amt - c.used_cashout_amt - c.this_cashout_amt AS 提交后剩余
  FROM   fin_fee_cashout_header c
  WHERE  c.save_type = 2
  AND    c.hz_approve_status = 'NEW'
  AND    (c.total_can_cashout_amt - c.used_cashout_amt - c.this_cashout_amt) < 0
  ORDER  BY c.create_time DESC;
  ```

#### 报错7：流程中objid为0，流程失败！
- **触发条件**：点击"提交"按钮，发起工作流ADJ_GGBXFPDX时，传入的objid（单据主键FEE_CASHOUT_ID）为0或null
- **逻辑分析**：工作流引擎需用objid关联业务单据。若保存时未正确回写FEE_CASHOUT_ID（如自增序列未取回、事务未提交即发起流程），或前端未传id字段，会导致objid=0。工作流无法定位兑现单，流程发起失败。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         hz_instance_id      AS 工作流实例ID,
         hz_approve_status   AS 审批状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    (fee_cashout_id = 0 OR fee_cashout_id IS NULL)
  ORDER  BY create_time DESC;
  ```

#### 报错8：兑现类型异常！
- **触发条件**：ERP资金池同步时，读取兑现单CASHOUT_TYPE既非1（额度内）也非2（额度外）
- **逻辑分析**：ERP同步需根据兑现类型决定sourceType（额度内="广告费（额内）"，额度外="广告费（额外）"）。若CASHOUT_TYPE被错误写入其他值（如0、3、null），无法匹配sourceType分支，抛异常终止同步。常见根因：数据迁移错误、手动修改数据库、或新建时未正确初始化兑现类型。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         cashout_type        AS 兑现类型,
         hz_approve_status   AS 审批状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    cashout_type NOT IN (1, 2)
  ORDER  BY create_time DESC;
  ```

#### 报错9：该单据流程信息不存在
- **触发条件**：电子签章校验时，按兑现单ID查询工作流流程信息返回null
- **逻辑分析**：电子签章需关联工作流实例。若兑现单未发起工作流（HZ_INSTANCE_ID为空）、工作流实例已被清理、或兑现单已被删除，查询流程信息返回空，签章校验失败。常见根因：单据未提交即触发签章、工作流实例过期、或单据ID传值错误。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         hz_instance_id      AS 工作流实例ID,
         hz_approve_status   AS 审批状态,
         signature_state     AS 签章状态
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    (hz_instance_id IS NULL OR hz_approve_status = 'NEW')
  ORDER  BY create_time DESC;
  ```

#### 报错10：门店编码或预算年度不能为空
- **触发条件**：额度外兑现审批通过后更新额度外预算时，门店编码TERMINAL_CODE或预算年度BUD_YEAR为空
- **逻辑分析**：额度外预算更新需用门店编码和预算年度定位MKT_OUTLIMIT_BUD_HEADER记录。若报销单未带入门店编码、预算年度未填写，或字段在流转中丢失，后端校验为空即抛异常，无法更新预算已使用金额。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         terminal_code       AS 门店编码,
         bud_year            AS 预算年度,
         cashout_type        AS 兑现类型
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    cashout_type = 2
  AND    (terminal_code IS NULL OR bud_year IS NULL)
  ORDER  BY create_time DESC;
  ```

#### 报错11：可兑现总额不能为零或负数
- **触发条件**：额度外预算更新时，读取报销单可兑现总额TOTAL_CAN_CASHOUT_AMT<=0
- **逻辑分析**：额度外预算更新需用可兑现总额计算使用金额（使用金额=本次申请金额×兑现比例÷税率）。若可兑现总额为0或负数，计算结果异常，抛异常终止预算更新。常见根因：报销单可兑现总额被错误置0、数据迁移错误、或报销单本身金额异常。
- **排查SQL**：
  ```sql
  SELECT fee_cashout_id      AS 兑现单ID,
         fee_cashout_no      AS 兑现单号,
         total_can_cashout_amt AS 可兑现总额,
         used_cashout_amt    AS 已兑现总额,
         cashout_type        AS 兑现类型
  FROM   fin_fee_cashout_header
  WHERE  save_type = 2
  AND    cashout_type = 2
  AND    (total_can_cashout_amt IS NULL OR total_can_cashout_amt <= 0)
  ORDER  BY create_time DESC;
  ```

#### 报错12：税率配置格式错误
- **触发条件**：额度外预算更新时，读取系统配置SCPSYSCONF中Outlimit_Tax_Rate的值格式错误（非数字或为空）
- **逻辑分析**：额度外预算使用金额需除以税率（使用金额=本次申请金额×兑现比例÷税率）。税率从系统配置Outlimit_Tax_Rate读取，若配置缺失、值为非数字字符串、或为0（除零异常），抛异常终止预算更新。常见根因：运维未配置Outlimit_Tax_Rate、配置值被误改、或格式不规范。
- **排查SQL**：
  ```sql
  SELECT confname            AS 配置名称,
         confvalue           AS 配置值
  FROM   scpsysconf
  WHERE  confname = 'Outlimit_Tax_Rate';
  ```

#### 报错13：额度外预算数据不存在，请检查！
- **触发条件**：额度外兑现审批通过后更新预算时，按门店编码+预算年度查询MKT_OUTLIMIT_BUD_HEADER返回null
- **逻辑分析**：额度外预算更新需定位预算头表记录。若该门店该年度未配置额度外预算、预算已被删除、或门店编码与预算年度不匹配，查询返回空，无法更新已使用金额，抛异常。常见根因：预算未配置、门店未纳入预算范围、或预算年度错误。
- **排查SQL**：
  ```sql
  SELECT c.fee_cashout_id      AS 兑现单ID,
         c.fee_cashout_no      AS 兑现单号,
         c.terminal_code       AS 门店编码,
         c.bud_year            AS 预算年度,
         b.terminal_code       AS 预算门店编码
  FROM   fin_fee_cashout_header c
  LEFT   JOIN mkt_outlimit_bud_header b
         ON b.terminal_code = c.terminal_code
        AND b.bud_year = c.bud_year
  WHERE  c.save_type = 2
  AND    c.cashout_type = 2
  AND    b.terminal_code IS NULL
  ORDER  BY c.create_time DESC;
  ```
