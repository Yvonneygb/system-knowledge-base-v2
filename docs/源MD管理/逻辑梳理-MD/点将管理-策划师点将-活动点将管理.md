# 点将管理-策划师点将-活动点将管理

> 后端代码位于 mbo-business 微服务，RESTful API 路径前缀 `mlt/activityApply/*`。

## 业务流程

### 业务流程图

```
经销商发起点将申请
        |
        v
活动点将管理列表(本页面)
        |
        ├──pageType=manage──→ 按计划结算 / 查看申请 / 同步CRM / 特殊取消
        |                        |
        |                        ├──按计划结算──→ 弹窗(结算信息+申请详情) ──→ settleForPlan接口
        |                        └──特殊取消──→ 校验7天内且已生效 ──→ 提交specialCancel
        |
        ├──pageType=approval──→ 审批 ──→ 审批通过/驳回 ──→ activityApplyApproval接口
        |                        ├──→ 同步OA(pushOa)
        |                        └──→ 同步FDD(pushFdd)
        |
        └──pageType=cancelApproval──→ 审批 ──→ 审批通过/驳回 ──→ cancelApplyApproval接口
                                       └──→ 同步OA(pushOa)
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|-------------|
| 经销商活动点将 | 数据库共享 | 经销商发起活动点将申请 | APPLY_TYPE_ONE='activity' |
| HZERO权限服务 | 接口依赖 | 提供页面权限、按钮权限 | permissionList、useAuthPageOption |
| 活动主数据 | 数据关联 | 活动基础信息 | 申请时关联 |
| 策划师主档 | 数据关联 | 策划师资源信息 | 申请时关联 |
| 经销商主档 | 数据关联 | 经销商信息 | 申请时关联 |
| CRM系统 | REST API | CRM订单同步 | pushCrm接口可用 |
| 工作流引擎 | 工作流 | 审批流程 | activityApplyApproval 流程已部署 |

### 下游影响

- **活动点将执行**：审批通过后进入执行，状态流转驱动执行环节
- **CRM订单系统**：同步CRM推送订单，pushCrm接口回写CRM_ORDER_CODE
- **OA审批系统**：同步OA推送流程，pushOa接口
- **法大大电子签约**：同步FDD推送签约，pushFdd接口
- **流程摘要组件**：查看流程展示审批历史，ProcessDetail组件
- **参训记录**：点将生效后产生，数据库关联

## 重点逻辑

### 重点逻辑1：pageType页面类型切换

- **业务意义**：同一菜单页面通过pageType参数切换三种视图模式，复用列表与查询能力，差异化展示按钮和操作。
- **具体逻辑描述**：通过`useAuthPageOption`实现三种模式切换。manage（点将活动管理）显示按计划结算、同步CRM、特殊取消按钮；approval（活动点将审批）显示审批、同步OA、同步FDD按钮；cancelApproval（活动点将取消审批）显示审批、同步OA按钮。查询接口`pageType`参数默认为`manage`。

### 重点逻辑2：双审批流独立运行

- **业务意义**：活动点将申请提交与取消分别走独立审批流，互不影响，确保申请与取消审批权责清晰。
- **具体逻辑描述**：申请提交触发activityApplyApproval审批流（applyTypeTwo=apply）；取消申请触发activityCancelApplyOrgApproval审批流（applyTypeTwo=cancel_apply，组织级审批）。审批参数 applyTypeOne=activity，approvalResult=approved/reject。

### 重点逻辑3：按计划结算

- **业务意义**：对已生效的活动点将按计划进行结算，下发结算金额与目标数据，驱动费用结算与对账。
- **具体逻辑描述**：通过Modal弹窗实现，包含结算信息（PlanSettlementInfo）展示目标数据和完成数据，申请详情（ActivityApplyDetail）通过`onDetail`回调同步数据到结算信息。保存并下发时收集目标数据、完成数据、签订人、讲师牌价、结算金额、实际时间，调用`POST settleForPlan`接口（管理页面用settleForPlan，执行页面用startSettle）。

### 重点逻辑4：特殊取消校验

- **业务意义**：对已生效且活动开始时间临近的申请提供特殊取消通道，约束时间窗口与状态，避免随意取消影响活动执行。
- **具体逻辑描述**：校验规则与特训营点将管理一致。时间差值`timeDiff`需在1-7天内；审批状态需为`fdd_sign`（已法大大签约）；未发起过取消申请（或已驳回）。校验通过后提交调用`POST specialCancel`接口。

### 重点逻辑5：applyCode自动生成

- **业务意义**：保证活动点将申请编码全局唯一、可追溯，作为主键贯穿全链路。
- **具体逻辑描述**：提交申请时系统自动生成唯一编码applyCode，写入APPLY_CODE字段。

### 重点逻辑6：状态联动

- **业务意义**：点将状态是策划师档期占用与费用发生的唯一依据，任何调整都必须通过审批或取消审批完成，不得绕过流程改单。
- **具体逻辑描述**：活动点将申请状态与审批状态联动，审批通过后申请状态自动变更为已通过；取消审批通过后状态变更为已取消；取消则同步回退下游状态。

### 重点逻辑7：同步外部系统差异化

- **业务意义**：根据pageType差异化推送外部系统，避免误推送与重复推送。
- **具体逻辑描述**：同步CRM仅pageType=manage显示；同步OA在pageType≠manage时显示；同步FDD仅pageType=approval显示。

### 选择弹窗

#### 弹窗1：按计划结算弹窗（单选）

弹窗配置：title=`结算信息`，宽度1200，确认按钮=`保存并下发`，取消按钮=`关闭`。

入参：

| 参数名 | 来源 | 说明 |
|--------|------|------|
| applyCode | 列表选中行 | 申请编码 |
| pageType | 页面参数 | manage（按钮显隐条件，非接口入参） |

弹窗内容：包含"结算信息"（PlanSettlementInfo组件）和"申请详情"（ActivityApplyDetail组件）两个区块。ActivityApplyDetail通过`onDetail`回调将目标数据（saleTarget/collectionTarget/orderTarget）和完成数据（saleComplete/collectionComplete/orderComplete/completeRate）同步到PlanSettlementInfo。

结算信息-目标数据表单（targetSettleFormDS）：

| 字段名 | 数据库列名 | 组件 | 业务释义 | 显隐条件 | 取值/赋值逻辑 |
|--------|-----------|------|---------|---------|-------------|
| 销售 | SALE_TARGET | NumberField | 销售目标 | 始终显示 | 必填，默认0.01，step:0.01，min:0.01，单位万 |
| 回款 | COLLECTION_TARGET | NumberField | 回款目标 | 始终显示 | 必填，默认0.01，step:0.01，min:0.01，单位万 |
| 订单 | ORDER_TARGET | NumberField | 订单目标 | 始终显示 | 必填，默认1，step:1，min:1，单位单 |

结算信息-完成数据表单（completeSettleFormDS）：

| 字段名 | 数据库列名 | 组件 | 业务释义 | 显隐条件 | 取值/赋值逻辑 |
|--------|-----------|------|---------|---------|-------------|
| 销售 | SALE_COMPLETE | NumberField | 销售完成 | 始终显示 | 必填，默认0，min:0，step:0.01，单位万 |
| 回款 | COLLECTION_COMPLETE | NumberField | 回款完成 | 始终显示 | 必填，默认0，min:0，step:0.01，单位万 |
| 订单 | ORDER_COMPLETE | NumberField | 订单完成 | 始终显示 | 必填，默认0，min:0，step:1，单位单 |
| 完成率 | COMPLETE_RATE | NumberField | 完成率 | 始终显示 | 必填，只读，默认0，单位%。计算逻辑：((销售完成/销售目标)*100+(回款完成/回款目标)*100+(订单完成/订单目标)*100)/3 |

提交数据（settleForPlan接口）：applyCode、saleTarget、collectionTarget、orderTarget、saleComplete、collectionComplete、orderComplete、completeRate、realStartDate（取realStartDate，为空取preStartDate，格式YYYY-MM-DD）、realEndDate（取realEndDate，为空取preEndDate，格式YYYY-MM-DD）、lecturerPrice、settlementAmount、signerId、signerName、signerPhone。

校验：targetFormData非空、completeFormData非空、signerValid（申请详情表单generalFormDS签订人校验通过）。

查询SQL：

```sql
SELECT
  aa.APPLY_CODE    AS 申请编码,
  aa.ACTIVITY_NAME AS 活动名称,
  aa.LECTURER_PRICE AS 讲师牌价,
  aa.PRE_ORD_LECTURER_DAYS AS 拟点将天数,
  aa.SETTLEMENT_CONFIRM_STATE AS 结算确认状态
FROM TRAIN_APPLY aa
WHERE aa.APPLY_CODE = :applyCode
  AND aa.APPLY_TYPE_ONE = 'activity';
```

#### 弹窗2：特殊取消弹窗（单选）

弹窗配置：title=`活动点将取消申请`，宽度1000，确认按钮=`提交`，取消按钮=`关闭`。弹窗打开前置校验：timeDiff（计划开始时间与当前时间差值）在1-7天内且approvalState=`fdd_sign`，且cancelApprovalState为空或为`reject`/`oa_reject`，否则提示并阻止。

入参：

| 参数名 | 来源 | 说明 |
|--------|------|------|
| applyCode | 列表选中行 | 申请编码 |
| cancelReason | 手动输入 | 取消原因（必填） |

弹窗内容字段（cancelApplyFormDS）：

| 字段名 | 数据库列名 | 组件 | 业务释义 | 显隐条件 | 取值/赋值逻辑 |
|--------|-----------|------|---------|---------|-------------|
| 取消原因 | CANCEL_REASON | TextArea | 取消申请原因 | 始终显示 | 必填，手动输入，name=cancelReason |

弹窗内容还包含申请详情（ActivityApplyDetail组件），展示选中行申请明细。提交时调用specialCancel接口，data={cancelReason, applyCode}。

查询SQL：

```sql
SELECT
  aa.APPLY_CODE    AS 申请编码,
  TO_CHAR(aa.ACTIVITY_START_DATE, 'YYYY-MM-DD') AS 活动开始时间,
  aa.APPROVAL_STATE AS 审核状态,
  ROUND((aa.ACTIVITY_START_DATE - SYSDATE)) AS 距开始天数
FROM TRAIN_APPLY aa
WHERE aa.APPLY_CODE = :applyCode
  AND aa.APPLY_TYPE_ONE = 'activity';
```

#### 弹窗3：审批弹窗（单选）

弹窗配置：title=`活动点将申请审批`（cancelApproval模式为`活动点将取消申请审批`），宽度1000，确认按钮=`审批通过`，取消按钮=`关闭`，底部增加`驳回`按钮。审批人、审批时间在弹窗打开时自动赋值（审批人=当前用户realName，审批时间=当前时间）。

入参：

| 参数名 | 来源 | 说明 |
|--------|------|------|
| applyCode | 列表选中行 | 申请编码 |
| approvalResult | 手动选择 | approved/reject（通过按钮=approved，驳回按钮=reject） |
| approvalComments | 手动输入 | 审批意见（必填） |
| signerId | 手动选择 | 签订人ID（approval模式显示，通过时必填） |
| signerName | 手动选择 | 签订人姓名（取signer.name） |
| signerPhone | 手动选择 | 签订人手机号（取signer.mobile） |
| applyTypeOne | 固定值 | activity |
| applyTypeTwo | 页面参数 | apply（approval模式）/ cancel_apply（cancelApproval模式） |

弹窗内容字段（applyApprovalFormDS）：

| 字段名 | 数据库列名 | 组件 | 业务释义 | 显隐条件 | 取值/赋值逻辑 |
|--------|-----------|------|---------|---------|-------------|
| 审批人 | - | TextField | 当前审批人姓名 | 始终显示 | disabled，自动赋值当前用户realName，name=approvalUserName |
| 审批时间 | - | DatePicker | 当前审批时间 | 始终显示 | disabled，自动赋值new Date()，name=approvalDate |
| 签订人 | SIGNER_ID | Select | 合同签订人 | pageType=approval显示 | options=signerDS，textField=name，valueField=accountId，通过时必填，name=signer |
| 审批意见 | APPROVAL_COMMENTS | TextArea | 审批意见 | 始终显示 | 必填，手动输入，name=approvalComments |

弹窗内容还包含申请详情（ActivityApplyDetail组件，type=view，actionType=activityApproval）。提交时approval模式调用activityApplyApproval接口，cancelApproval模式调用activityCancelApplyOrgApproval接口。

查询SQL：

```sql
SELECT
  aa.APPLY_CODE    AS 申请编码,
  aa.APPROVAL_STATE AS 当前审核状态,
  aa.SIGNER_NAME   AS 签订人
FROM TRAIN_APPLY aa
WHERE aa.APPLY_CODE = :applyCode
  AND aa.APPLY_TYPE_ONE = 'activity';
```

### 保存/提交校验

- 校验1：按计划结算时targetFormData、completeFormData、signerValid非空 —— 确保结算数据完整，签订人已选择
- 校验2：特殊取消时取消原因必填 —— 留存取消依据，便于追溯
- 校验3：审批时审批意见必填 —— 审批意见为审批留痕必要信息
- 校验4：审批通过时签订人必填 —— 签订人作为后续合同签订主体

### 状态机

流转图：

```
draft(草稿) → submitted(已提交) → approved(审批通过) → valid(生效)
   → executing(执行中) → end(已完成)
rejected(审批驳回) → 可修改重提
valid → cancel_applied(取消申请中) → cancel_approved(已取消)
```

状态列表：

| 当前状态 | 触发动作 | 目标状态 |
|---------|---------|---------|
| draft | 保存并提交 | submitted |
| submitted | 审批通过 | approved |
| submitted | 审批驳回 | rejected |
| rejected | 修改后重新提交 | submitted |
| approved | 生效 | valid |
| valid | 开始执行 | executing |
| executing | 结束执行 | end |
| valid | 发起取消申请 | cancel_applied |
| cancel_applied | 取消审批通过 | cancel_approved |

#### 报错1：请选择一条数据
- **触发条件**：点击按计划结算、查看申请、同步CRM、特殊取消、审批、同步OA、同步FDD等行操作按钮时，未选择数据或选择了多行
- **逻辑分析**：前端在执行单选操作前校验选中行数量，若 selectedRows.length ≠ 1 则阻止操作并提示"请选择一条数据"。单选操作需要明确的目标申请，未选择时无法确定操作对象，多选时操作对象不唯一
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DISTRIBUTOR_NAME AS 申请人,
         ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错2：只有在培训开始前七天内且已生效的单据才可以发起取消申请！
- **触发条件**：点击特殊取消按钮时，不满足"活动开始前1-7天内且已法大大签约"条件
- **逻辑分析**：前端执行多重校验：①计算时间差值 timeDiff = (ACTIVITY_START_DATE - nowTime) / (24*60*60*1000)，校验 1 <= timeDiff <= 7（活动开始前1-7天内）；②校验 APPROVAL_STATE = 'fdd_sign'（已法大大签约生效）。任一校验不通过则提示"只有在培训开始前七天内且已生效的单据才可以发起取消申请！"。此校验限制取消时机，避免临近开课取消造成资源浪费，同时要求单据已生效具备业务合法性
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         TO_CHAR(ACTIVITY_START_DATE,'YYYY-MM-DD') AS 活动开始时间,
         APPROVAL_STATE AS 审核状态,
         ROUND(ACTIVITY_START_DATE - SYSDATE) AS 距开始天数
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE = 'approved'
    AND (ACTIVITY_START_DATE <= SYSDATE
         OR ACTIVITY_START_DATE > SYSDATE + 7
         OR APPROVAL_STATE <> 'fdd_sign');
  ```

#### 报错3：该单据已发起取消申请，不可重复发起！
- **触发条件**：点击特殊取消按钮时，该单据已存在进行中的取消申请
- **逻辑分析**：前端校验 CANCEL_APPROVAL_STATE 字段，若不为空且不等于 'reject' 和 'oa_reject'，说明已有进行中的取消申请（如待审批、审批中），提示"该单据已发起取消申请，不可重复发起！"。避免重复发起取消审批导致流程冲突
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         APPROVAL_STATE AS 审核状态,
         CANCEL_APPROVAL_STATE AS 取消审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE = 'fdd_sign'
    AND CANCEL_APPROVAL_STATE IS NOT NULL
    AND CANCEL_APPROVAL_STATE NOT IN ('reject', 'oa_reject');
  ```

#### 报错4：审批意见不能为空
- **触发条件**：审批提交时，approvalComments 字段为空
- **逻辑分析**：前端 applyApprovalFormDS.validate() 对 approvalComments 字段配置 required 校验，提交前校验审批意见是否填写，为空则阻止提交并提示"审批意见不能为空"。审批意见用于记录审批人决策依据，保证审批留痕完整可追溯
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         APPROVAL_STATE AS 审核状态,
         APPROVAL_COMMENTS AS 审批意见
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE IN ('approved', 'reject')
    AND (APPROVAL_COMMENTS IS NULL OR APPROVAL_COMMENTS = '');
  ```

#### 报错5：签订人不能为空
- **触发条件**：审批通过（approvalResult=approved）提交时，signerName/signerId 字段为空
- **逻辑分析**：前端在审批结果为 approved 时对 signerId 字段配置 required 校验，提交前校验签订人是否选择，为空则阻止提交并提示"签订人不能为空"。签订人用于后续法大大签约流程，审批通过后需明确签订人身份
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         APPROVAL_STATE AS 审核状态,
         SIGNER_ID AS 签订人ID,
         SIGNER_NAME AS 签订人姓名
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE = 'approved'
    AND (SIGNER_NAME IS NULL OR SIGNER_ID IS NULL);
  ```

#### 报错6：请求失败
- **触发条件**：调用 mlt/activityApply/* 系列接口时，后端返回 HTTP 状态码非 2xx
- **逻辑分析**：前端通过 axios 调用后端接口，若响应状态码非 2xx 或网络异常则触发错误回调，统一提示"请求失败"。常见根因包括：mbo-business 微服务未启动或异常、数据库连接失败、SQL 执行超时、后端业务异常未捕获、外部系统（OA/FDD/CRM）调用失败、工作流引擎异常、网络中断等。需检查 mbo-business 微服务运行状态、外部系统连通性、工作流配置、后端日志定位具体异常堆栈
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态,
  ```

- **逻辑分析**：前端 axios 请求未收到响应或响应超时，触发 catch 回调统一提示"请求失败"。常见根因：网络中断、mbo-business 服务假死、数据库慢查询、工作流引擎响应慢等。需检查网络连通性、后端服务负载、数据库性能

#### 报错8：权限不足
- **触发条件**：点击按计划结算、查看申请、同步CRM、特殊取消、审批、同步OA、同步FDD等按钮时，当前用户无对应 permissionList 权限码
- **逻辑分析**：前端 Button 组件通过 permissionList 配置权限码，HZERO 框架校验当前用户角色是否包含该权限码，未包含则按钮不可见或禁用。若强制调用接口，后端也会校验权限返回403。需联系管理员配置对应角色权限
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名, R.ROLE_NAME AS 角色名, P.PERMISSION_CODE AS 权限码
  FROM SYS_USER U
  LEFT JOIN SYS_USER_ROLE UR ON U.USER_ID = UR.USER_ID
  LEFT JOIN SYS_ROLE R ON UR.ROLE_ID = R.ROLE_ID
  LEFT JOIN SYS_ROLE_PERMISSION RP ON R.ROLE_ID = RP.ROLE_ID
  LEFT JOIN SYS_PERMISSION P ON RP.PERMISSION_ID = P.PERMISSION_ID
  WHERE P.PERMISSION_CODE LIKE '%activity_general_manage%' ORDER BY U.USER_NAME;
  ```

#### 报错9：数据不存在
- **触发条件**：查看申请、审批等操作时，接口返回数据为空或申请编码不存在
- **逻辑分析**：前端通过 applyCode 调用详情接口，后端查询 TRAIN_APPLY 表无对应记录或记录已逻辑删除，返回空数据。常见根因：申请编码错误、申请已被删除、跨租户查询、数据权限隔离等。需检查 APPLY_CODE 有效性及数据权限
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态, DELETE_FLAG AS 删除标记
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND (DELETE_FLAG = 'Y' OR APPLY_CODE IS NULL);
  ```

#### 报错10：状态不允许操作
- **触发条件**：点击审批、特殊取消等按钮时，申请状态不在允许操作的状态范围内
- **逻辑分析**：后端校验申请状态机，如审批要求 APPROVAL_STATE 为 to_be_approval、特殊取消要求审批通过且活动开始前7天内等。状态不匹配时后端返回业务异常，前端提示后端返回的 message。需检查申请当前状态及操作流程
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态, APPROVAL_STATE AS 审核状态,
         CANCEL_APPROVAL_STATE AS 取消审核状态, ERROR_INFO AS 异常问题
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND APPROVAL_STATE NOT IN ('to_be_approval','approved','reject','fdd_sign')
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错11：同步外部系统失败
- **触发条件**：点击同步CRM/同步OA/同步FDD按钮，对应推送接口返回失败
- **逻辑分析**：前端通过 PRequest 调用 pushCrm/pushOa/pushFdd 接口，接口返回 success=false 或非2xx状态码时触发错误回调。常见根因：CRM/OA/FDD 外部系统不可用、数据不符合外部接口要求、申请状态不允许同步、网络中断等。后端会将异常写入 ERROR_INFO 字段
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         CRM_ORDER_CODE AS CRM单号, CRM_ORDER_STATUS AS CRM订单状态,
         ERROR_INFO AS 异常问题,
         TO_CHAR(LAST_UPDATE_DATE,'YYYY-MM-DD HH24:MI:SS') AS 最后更新时间
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity'
    AND (ERROR_INFO IS NOT NULL OR CRM_ORDER_STATUS = 'FAIL')
    AND LAST_UPDATE_DATE >= SYSDATE - 7
  ORDER BY LAST_UPDATE_DATE DESC;
  ```

#### 报错12：值集数据不显示
- **触发条件**：查询条件或列表中审核状态、点将状态等下拉选项为空
- **逻辑分析**：前端通过 lookupCode 查询值集 MBO.APPLY_APPROVAL_STATE、MBO.ORDER_LECTURE_STATE 等，值集未配置或未启用则下拉选项为空。需在值集管理页面配置对应值集
- **排查SQL**：
  ```sql
  SELECT LOOKUP_CODE AS 值集编码, LOOKUP_VALUE_CODE AS 值编码,
         LOOKUP_VALUE_NAME AS 值名称, ENABLE_FLAG AS 启用标记
  FROM SYS_LOOKUP_VALUE
  WHERE LOOKUP_CODE IN ('MBO.APPLY_APPROVAL_STATE','MBO.ORDER_LECTURE_STATE','MBO.CANCEL_APPROVAL_STATE')
    AND ENABLE_FLAG = 'N' ORDER BY LOOKUP_CODE;
  ```

### 常见问题

**Q1：活动点将与特训营点将有什么区别？**
A：活动点将由策划师发起，审批流为activityApplyApproval；特训营点将由经销商/业务员发起，审批流为campApplyApproval。

**Q2：取消审批为什么是组织级审批？**
A：活动取消影响范围较大，需组织级管理层审批确认，因此取消审批流为activityCancelApplyOrgApproval。

**Q3：活动点将申请被拒绝后能否重新提交？**
A：可以，拒绝后可修改申请内容重新提交审批。

**Q4：按计划结算按钮不显示？**
A：确认pageType为manage，按计划结算仅在管理视图显示。

**Q5：同步FDD按钮不显示？**
A：确认pageType为approval，同步FDD仅在审批视图显示。
