# 点将管理-经销商点将-活动点将

> 后端代码位于 mbo-business 微服务，RESTful API 路径前缀 `mlt/activityApply/*`。

## 业务流程

### 业务流程图

```
经销商发起活动点将
        |
        v
活动点将列表(本页面)
        |
        ├──新建──→ 跳转详情页(/detail/null/add) ──→ 填写申请信息
        |                                            ├──保存──→ dealerSave接口 ──→ 草稿
        |                                            └──保存并提交──→ dealerSaveAndSubmit接口 ──→ 已提交
        |
        ├──编辑──→ 跳转详情页 ──→ 修改后保存/保存并提交
        |
        ├──删除──→ 校验草稿/驳回状态 ──→ delete接口
        |
        ├──取消申请──→ 校验提前7天且已签约 ──→ 弹窗填写取消原因 ──→ cancelApply接口
        |
        └──行操作──→ 查看详情/查看流程/编辑/删除
```

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|-------------|
| 经销商主档 | 数据关联 | 提供经销商信息 | 当前登录用户关联经销商 |
| 门店主档 | LOV选择 | 提供门店列表供选择 | 经销商下存在门店 |
| 讲师主档 | LOV选择 | 提供讲师列表供选择 | campApi.lecturerList接口可用，pageType=activity |
| 活动主数据 | 数据关联 | 活动基础信息 | 申请时关联 |
| HZERO权限服务 | 接口依赖 | 提供按钮权限校验 | permissionList权限编码 |
| 法大大电子签约 | 接口依赖 | 申请确认签合同 | useFDD钩子可用 |
| 工作流引擎 | 工作流 | 审批流程 | activityApplyApproval 流程已部署 |

### 下游影响

- **活动点将管理**：申请提交后进入管理审批，数据库共享
- **活动点将执行**：审批通过后进入执行，状态流转
- **活动点将详情页**：申请/编辑跳转，openTab新标签页
- **参与确认回执**：确认参与状态，数据回写
- **活动执行记录**：活动留痕，数据库共享
- **CRM订单系统**：同步CRM推送订单，pushCrm接口回写CRM_ORDER_CODE

## 重点逻辑

### 重点逻辑1：经销商发起视角

- **业务意义**：本菜单由经销商主动发起活动点将申请，经销商自主选择门店、讲师与活动信息。
- **具体逻辑描述**：通过`dealer`路径接口（dealerPage、dealerSave、dealerSaveAndSubmit）实现经销商发起，后端自动按当前登录经销商过滤数据并写入DEALER_CODE、DEALER_NAME，APPLY_TYPE_ONE='activity'，APPLY_TYPE_TWO='apply'。

### 重点逻辑2：数据范围隔离

- **业务意义**：经销商仅能查看和操作自己发起的活动点将记录，避免跨经销商数据泄露。
- **具体逻辑描述**：通过`dealer`路径接口自动按当前登录经销商过滤，前端无需传经销商参数。

### 重点逻辑3：applyCode自动生成

- **业务意义**：保证活动点将申请编码全局唯一、可追溯，作为主键贯穿全链路。
- **具体逻辑描述**：提交申请时系统自动生成唯一编码applyCode，写入APPLY_CODE字段。

### 重点逻辑4：取消申请校验

- **业务意义**：约束取消申请的时间窗口与状态，避免临近活动开始取消影响讲师排期与活动筹备。
- **具体逻辑描述**：时间校验 timeDiff >= 7（提前7天），基于activityStartDate；状态校验 approvalState === 'fdd_sign'（已法大大签约）；取消状态校验 cancelApprovalState 为空或 reject/oa_reject；点将状态校验 orderLectureState !== 'end'（未结束）。校验通过弹窗填写取消原因，调用`POST cancelApply`接口。

### 重点逻辑5：编辑再发起校验

- **业务意义**：仅草稿或各类驳回状态可编辑，避免已生效或审批中单据被误改。
- **具体逻辑描述**：行操作"编辑再发起"校验状态：orderLectureState === 'draft'（草稿）或 approvalState 为 reject/oa_reject/fdd_reject（各种驳回）。校验通过跳转编辑详情页，否则提示"当前状态数据无法编辑！"。

### 重点逻辑6：讲师排期冲突校验

- **业务意义**：避免同一讲师在同一时间段被重复点将，保障讲师档期合理性。
- **具体逻辑描述**：保存时校验所选讲师在拟定开始时间至拟定结束时间区间内不存在已生效点将记录，存在冲突则提示并阻止保存。

### 重点逻辑7：点将费计算

- **业务意义**：明确活动点将费用计算方式，为结算提供依据。
- **具体逻辑描述**：点将费用 = 被点将人点将牌价 × 具体折扣。最终点将价格由系统生成结算确认书由经销商确认。

### 选择弹窗

#### 弹窗1：申请点将弹窗（讲师选择，列表页头部"申请点将"按钮触发）

> 数据来源：`list.tsx` 的 `handleApply` + `stores/listConfig.tsx` 的 `applyListDSProps`/`applyListDScolumns`。接口 `campApi.lecturerList`，固定传参 `pageType='activity'`。

入参：

| 参数名 | 来源 | 说明 |
|--------|------|------|
| lecturerName | 查询栏输入 | 讲师姓名模糊查询 |
| lecturerLevel | 查询栏选择 | 讲师级别，值集MBO.ACTIVITY_LECTURER_LEVEL |
| pageType | 固定值 | 固定'activity'，标识活动点将 |

列表列：序号、讲师姓名（点击跳转讲师档案详情）、讲师级别、报价、讲师类型（值集MBO.LECTURER_TYPE）、负责区域、标签、操作（查看日程/选择）。

行操作：
- 查看日程：弹出讲师日历组件 `LecturerCalendar`，传入rowData和haveLecturerCode=true
- 选择：调用 `handleChoose`，`openTab` 跳转详情页 `/detail/null/add`，state携带讲师信息

查询SQL：

```sql
SELECT
  la.ID              AS 讲师档案ID,
  la.LECTURER_NAME   AS 讲师姓名,
  la.LECTURER_LEVEL  AS 讲师级别,
  la.PRICE           AS 报价,
  la.LECTURER_TYPE   AS 讲师类型,
  la.COVER_AREA      AS 负责区域,
  la.LECTURER_LABEL  AS 标签
FROM MBO_TRAIN_LECTURER_ARCHIVE la
WHERE la.PAGE_TYPE = 'activity'
  AND (:lecturerName IS NULL OR la.LECTURER_NAME LIKE '%' || :lecturerName || '%')
  AND (:lecturerLevel IS NULL OR la.LECTURER_LEVEL = :lecturerLevel)
ORDER BY la.CREATE_DATE DESC;
```

> 数据来源：`components/ActivityApplyDetail/index.tsx` 的 `handleShowStoreList` + `distributorGeneralCamp/components/ApplyInfo/config.tsx` 的 `storeDS`/`storeListDSColumns`。接口 `campApi.storePage`，单选，autoQuery=true。

```sql
SELECT
```

```sql
WHERE (:terminalCode IS NULL OR t.TERMINAL_CODE LIKE '%' || :terminalCode || '%')
```

### 状态机

流转图：

```
draft(新建) → submitted(已提交) → approved(审批通过) → valid(生效)
   → executing(执行中) → end(已完成)
rejected(审批驳回) → 可修改重提
valid → cancel_applied(取消申请中) → cancel_approved(已取消)
```

状态列表：

| 当前状态 | 触发动作 | 目标状态 |
|---------|---------|---------|
| draft | 保存并提交 | submitted |
| submitted | 审批通过 | approved |
| submitted | 审批驳回 | rejected |
| rejected | 修改后重新提交 | submitted |
| approved | 生效 | valid |
| valid | 开始执行 | executing |
| executing | 结束执行 | end |
| valid | 发起取消申请 | cancel_applied |
| cancel_applied | 取消审批通过 | cancel_approved |

#### 报错1：请选择一条数据
- **触发条件**：点击编辑、删除、取消申请、查看流程等行操作按钮时，未选择数据或选择了多行
- **逻辑分析**：前端在执行单选操作前校验选中行数量，若 selectedRows.length ≠ 1 则阻止操作并提示"请选择一条数据"。单选操作需要明确的目标申请，未选择时无法确定操作对象，多选时操作对象不唯一
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DISTRIBUTOR_NAME AS 申请人,
         ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错2：需提前7天且已生效的单据才可以发起申请取消！
- **触发条件**：点击取消申请按钮时，不满足"提前7天"条件
- **逻辑分析**：前端计算时间差值 timeDiff = (ACTIVITY_START_DATE - nowTime) / (24*60*60*1000)，校验 timeDiff >= 7（活动开始前至少7天）。校验不通过则提示"需提前7天且已生效的单据才可以发起申请取消！"。此校验确保有充足时间通知讲师和门店调整安排，避免临时取消造成资源浪费
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         TO_CHAR(ACTIVITY_START_DATE,'YYYY-MM-DD') AS 活动开始时间,
         APPROVAL_STATE AS 审核状态,
         ROUND(ACTIVITY_START_DATE - SYSDATE) AS 距开始天数
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND ACTIVITY_START_DATE < SYSDATE + 7;
  ```

#### 报错3：该状态单据无法发起取消申请！
- **触发条件**：点击取消申请按钮时，审批状态不为 fdd_sign 或点将状态为 end 或已有进行中的取消申请
- **逻辑分析**：前端执行多重校验：①校验 APPROVAL_STATE = 'fdd_sign'（已法大大签约）；②校验 ORDER_LECTURE_STATE ≠ 'end'（未结束）；③校验 CANCEL_APPROVAL_STATE 为空或为 reject/oa_reject（未取消或已驳回）。任一校验不通过则提示"该状态单据无法发起取消申请！"。确保仅已签约生效且未结束、未重复取消的单据可发起取消
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         APPROVAL_STATE AS 审核状态,
         ORDER_LECTURE_STATE AS 点将状态,
         CANCEL_APPROVAL_STATE AS 取消审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND (APPROVAL_STATE <> 'fdd_sign'
         OR ORDER_LECTURE_STATE = 'end'
         OR (CANCEL_APPROVAL_STATE IS NOT NULL
             AND CANCEL_APPROVAL_STATE NOT IN ('reject', 'oa_reject')));
  ```

#### 报错4：当前状态数据无法编辑！
- **触发条件**：点击编辑按钮时，状态非草稿且非各类驳回状态
- **逻辑分析**：前端校验 ORDER_LECTURE_STATE = 'draft'（草稿）或 APPROVAL_STATE 为 reject/oa_reject/fdd_reject（各种驳回），任一条件满足才允许编辑。已生效（valid）、审批中（approving）等状态的申请已被下游引用，编辑可能影响数据一致性，故限制编辑。校验不通过提示"当前状态数据无法编辑！"
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND ORDER_LECTURE_STATE <> 'draft'
    AND APPROVAL_STATE NOT IN ('reject', 'oa_reject', 'fdd_reject');
  ```

- **逻辑分析**：后端保存前校验讲师排期冲突，查询 TRAIN_APPLY 表中同一讲师（LECTURER_CODE 相同）且状态为 valid 或 executing 的点将记录，判断新申请的 [ACTIVITY_START_DATE, ACTIVITY_END_DATE] 与已有记录的时间段是否存在交集。若存在交集则提示"讲师排期冲突"并阻止保存。此校验避免同一讲师在同一时间段被重复点将，保障讲师档期合理性

  ```sql
  SELECT a.APPLY_CODE AS 申请1编码,

    AND a.LECTURER_CODE = b.LECTURER_CODE

    AND a.ORDER_LECTURE_STATE IN ('valid', 'executing')
    AND b.ORDER_LECTURE_STATE IN ('valid', 'executing')

    AND a.ACTIVITY_END_DATE >= b.ACTIVITY_START_DATE;
  ```

#### 报错13：权限不足
- **触发条件**：点击编辑、删除、取消申请等按钮时，当前用户无对应 permissionList 权限码
- **逻辑分析**：前端 Button 组件通过 permissionList 配置权限码，HZERO 框架校验当前用户角色是否包含该权限码，未包含则按钮不可见或禁用。若强制调用接口，后端也会校验权限返回403。需联系管理员配置对应角色权限
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名, R.ROLE_NAME AS 角色名, P.PERMISSION_CODE AS 权限码
  FROM SYS_USER U
  LEFT JOIN SYS_USER_ROLE UR ON U.USER_ID = UR.USER_ID
  LEFT JOIN SYS_ROLE R ON UR.ROLE_ID = R.ROLE_ID
  LEFT JOIN SYS_ROLE_PERMISSION RP ON R.ROLE_ID = RP.ROLE_ID
  LEFT JOIN SYS_PERMISSION P ON RP.PERMISSION_ID = P.PERMISSION_ID
  WHERE P.PERMISSION_CODE LIKE '%activity_general%' ORDER BY U.USER_NAME;
  ```


#### 报错15：状态不允许操作
- **触发条件**：点击取消申请、结束确认等按钮时，申请状态不在允许操作的状态范围内
- **逻辑分析**：后端校验申请状态机，如取消申请要求 approvalState 为 fdd_sign 且 orderLectureState 非 end、结束确认要求状态为执行中等。状态不匹配时后端返回业务异常，前端提示后端返回的 message。需检查申请当前状态及操作流程
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         ORDER_LECTURE_STATE AS 点将状态, APPROVAL_STATE AS 审核状态,
         CANCEL_APPROVAL_STATE AS 取消审核状态, ERROR_INFO AS 异常问题
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND ORDER_LECTURE_STATE NOT IN ('draft','valid','executing','finished')
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错16：值集数据不显示
- **触发条件**：查询条件或列表中点将状态、审核状态等下拉选项为空
- **逻辑分析**：前端通过 lookupCode 查询值集 MBO.ORDER_LECTURE_STATE、MBO.APPLY_APPROVAL_STATE 等，值集未配置或未启用则下拉选项为空。需在值集管理页面配置对应值集
- **排查SQL**：
  ```sql
  SELECT LOOKUP_CODE AS 值集编码, LOOKUP_VALUE_CODE AS 值编码,
         LOOKUP_VALUE_NAME AS 值名称, ENABLE_FLAG AS 启用标记
  FROM SYS_LOOKUP_VALUE
  WHERE LOOKUP_CODE IN ('MBO.ORDER_LECTURE_STATE','MBO.APPLY_APPROVAL_STATE')
    AND ENABLE_FLAG = 'N' ORDER BY LOOKUP_CODE;
  ```

#### 报错17：活动时间范围校验失败
- **触发条件**：保存或保存并提交时，ACTIVITY_START_DATE > ACTIVITY_END_DATE
- **逻辑分析**：前端校验活动时间范围合法性，若开始时间大于结束时间则阻止提交。需检查时间范围选择是否正确
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         TO_CHAR(ACTIVITY_START_DATE,'YYYY-MM-DD') AS 活动开始时间,
         TO_CHAR(ACTIVITY_END_DATE,'YYYY-MM-DD') AS 活动结束时间
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND ACTIVITY_START_DATE > ACTIVITY_END_DATE;
  ```

#### 报错18：拟点将天数必须大于0
- **触发条件**：保存或保存并提交时，PRE_ORD_LECTURER_DAYS 字段非正数
- **逻辑分析**：后端校验 PRE_ORD_LECTURER_DAYS > 0，拟点将天数用于费用计算与讲师排期，必须为正数。若为0或负数则返回业务异常。需检查拟点将天数输入是否正确
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码, ACTIVITY_NAME AS 活动名称,
         PRE_ORD_LECTURER_DAYS AS 拟点将天数
  FROM TRAIN_APPLY
  WHERE APPLY_TYPE_ONE = 'activity' AND APPLY_TYPE_TWO = 'apply'
    AND PRE_ORD_LECTURER_DAYS IS NOT NULL AND PRE_ORD_LECTURER_DAYS <= 0;
  ```

### 常见问题

**Q1：经销商看不到自己发起的活动点将记录？**
A：检查该经销商是否正确关联当前登录用户，确认DEALER_CODE与当前登录用户关联的经销商一致。

**Q2：详情页type参数有什么作用？**
A：`type`参数用于区分详情页的展示模式，不同模式可能展示不同的操作按钮和字段。

**Q3：活动点将状态未更新？**
A：状态由审批流程驱动，需联系审批人确认审批进度。

**Q4：申请点将弹窗无讲师数据？**
A：检查campApi.lecturerList接口，pageType=activity参数是否正确传递。

**Q5：取消点将校验不通过？**
A：检查activityStartDate时间差值、approvalState是否为fdd_sign、orderLectureState是否非end。
