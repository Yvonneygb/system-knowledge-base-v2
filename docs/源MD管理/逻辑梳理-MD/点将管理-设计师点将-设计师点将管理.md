# 点将管理-设计师点将-设计师点将管理

> 后端代码位于 mbo-business 微服务，API 路径前缀为 `mlt/designApply/*`。

## 业务流程

```
经销商发起设计点将申请
        |
        └── 审批流 ──→ 设计点将审批(运营) ──→ 设计点将审批(设计师) ──→ 设计师接单执行
                                    |                        |
                                    └── 驳回                 └── 驳回
        |
        ├── 取消申请 ──→ 设计点将取消审批(运营) ──→ 设计点将取消审批(设计师)
        |
        ├── 项目终止申请 ──→ 项目终止审批 ──→ 终止完成
        |
        └── 设计改派(运营管理) ──→ 更换设计师 ──→ 重新进入执行流程
```

通过 pageType 切换管理视图(manage)和审批视图(approval)，审批接口为 POST mlt/designApply/designApplyApproval。

### 上游依赖

| 上游模块 | 依赖类型 | 依赖说明 | 依赖成立条件 |
|---------|---------|---------|-------------|
| 经销商点将-设计点将 | 数据依赖 | 经销商发起设计点将申请，生成申请数据进入本页面管理 | 经销商已提交设计点将申请 |
| 讲师档案 | 数据依赖 | 设计师选择时引用讲师档案数据，查看讲师详情跳转讲师档案 | 设计师已在讲师档案中配置 |
| CRM订单 | 数据依赖 | CRM订单状态同步展示，关联CRM单号 | 已执行同步CRM操作 |

### 下游影响

- 审批通过后申请进入执行阶段，由设计点将执行页面管理后续流程
- 设计师选定后影响其饱和度数据，审批时查看饱和度
- 同步CRM后更新CRM订单状态
- 审批通过后可同步OA
- 审批通过后可推送FDD签署

## 重点逻辑

### 重点逻辑1：pageType切换管理/审批视图

- **业务意义**：同一页面支持管理和审批两种视图，通过 pageType 参数切换，减少页面数量
- **具体逻辑描述**：pageType=manage 为管理视图，pageType=approval 为审批视图，审批按钮仅在 pageType 不等于 manage 时显示

### 重点逻辑2：审批接口分流

- **业务意义**：不同审批场景调用不同审批接口，确保审批流程正确流转
- **具体逻辑描述**：根据 pageType 调用不同审批接口：approval 调用 designApplyApproval，cancelApproval 调用 cancelApplyApproval，designerApproval 调用 designApplyLecturerApproval，designerCancelApproval 调用 cancelApplyApproval

### 重点逻辑3：项目终止审批

- **业务意义**：终止申请需独立审批流程，确保终止决策有审批留痕
- **具体逻辑描述**：当 applyType=termination 且 terminationApprovalState=to_be_approval 时，走项目终止审批逻辑，调用 designApplyTerminalApproval 接口

### 重点逻辑4：设计改派

- **业务意义**：管理视图下可更换设计师，灵活调整服务资源
- **具体逻辑描述**：仅 manage 模式可用，通过弹窗选择新设计师后调用 designReassignment 接口

### 重点逻辑5：多级审批链路

- **业务意义**：设计点将涉及多级审批，按顺序依次触发，确保各环节确认
- **具体逻辑描述**：设计点将涉及4个内置审批流程：designApplyLecturerApproval(讲师审批)→designApplyTerminalApproval(门店审批)→designApplyApproval(常规审批)；取消审批走 designApplyCancelApproval

### 重点逻辑6：审批互斥

- **业务意义**：取消审批与常规审批互斥，避免审批流程冲突
- **具体逻辑描述**：已进入审批流程的申请需先完成或取消当前审批，才能发起新的审批

列表查询SQL（接口 POST /mlt/designApply/page）：

```sql
SELECT MLA.APPLY_CODE              AS "申请编码",
       MLA.APPLY_USER_NAME         AS "申请人",
       MLA.APPLY_TYPE              AS "申请类型",
       MLA.STORE_NAME              AS "门店名称",
       MLA.CREATE_DATE             AS "申请时间",
       MLA.LECTURER_NAME           AS "设计师",
       MLA.ORDER_LECTURE_STATE     AS "点将状态",
       MLA.DESIGN_STATE            AS "设计状态",
       MLA.APPROVAL_STATE          AS "申请审核状态",
       MLA.TERMINATION_APPROVAL_STATE AS "终止审批状态",
       MLA.SETTLEMENT_CONFIRM_STATE AS "结算确认状态",
       MLA.CRM_ORDER_CODE          AS "CRM单号",
       MLA.CRM_ORDER_STATUS        AS "CRM订单状态",
       MLA.ERROR_INFO              AS "异常问题",
       MLA.RELATION_APPLY_CODE     AS "关联单据"
FROM DESIGN_APPLY MLA
WHERE MLA.APPLY_TYPE_ONE = 'design'
  AND MLA.PAGE_TYPE = :pageType
  AND (:applyCode IS NULL OR MLA.APPLY_CODE LIKE '%' || :applyCode || '%')
  AND (:approvalState IS NULL OR MLA.APPROVAL_STATE = :approvalState)
  AND (:applyType IS NULL OR MLA.APPLY_TYPE = :applyType)
  AND (:startDate IS NULL OR MLA.CREATE_DATE >= TO_DATE(:startDate, 'YYYY-MM-DD'))
  AND (:endDate IS NULL OR MLA.CREATE_DATE < TO_DATE(:endDate, 'YYYY-MM-DD') + 1)
ORDER BY MLA.CREATE_DATE DESC;
```

#### 按钮1：查看申请（Header按钮）

校验选中一条数据后，openTab 跳转设计点将申请详情页 `/general/distributorGeneral/distributorGeneralDesign/detail/{applyCode}/view`，传递 state={ isSupplement: applyType==='supplement', isCrm: true }。

#### 按钮2：审批（Header按钮）

当 pageType 不等于 manage 时显示。校验选中一条数据后，设置 approvalUserName=当前用户realName、approvalDate=new Date()、approvalType=pageType。判断是否终止审批：pageType 为 approval/designerApproval 且（applyType=termination 时 terminationApprovalState=to_be_approval，否则 approvalState=to_be_approval）则 isTerminalApproval=true。弹出审批弹窗，支持审批通过/驳回，根据 pageType 分流调用不同审批接口。

#### 按钮3：设计改派（Header按钮）

当 pageType=manage 时显示。校验选中一条数据后，弹出设计改派弹窗，点击新设计师搜索图标弹出设计师选择列表，选择后回填。onOk 校验新设计师必填，提交 lecturerArchivesCode 调用 designReassignment 接口（/mlt/designApply/designReassignment），成功后刷新列表。

#### 按钮4：查看流程（行操作）

点击弹出流程摘要弹窗（宽度1000），内容为 ProcessDetail 组件（传 applyCode），展示申请审批流程明细，仅含关闭按钮。

#### 按钮5：审批通过（审批弹窗内）

弹窗 onOk 触发，调用 approvalRequest(isPass=true)。校验审批意见必填后，组装数据 { approvalComments, applyCode, applyTypeOne:'design', applyTypeTwo: isCancel?'cancel_apply':'apply', approvalResult:'approved' }，按分流规则调用审批接口，成功后刷新列表。

#### 按钮6：驳回（审批弹窗内）

弹窗 footer 自定义按钮触发，调用 approvalRequest(isPass=false)。组装数据 approvalResult='reject'，按分流规则调用审批接口，成功后关闭弹窗并刷新列表。

> 审批接口分流规则（approvalRequest）：
> - isTerminalApproval（终止审批）：pageType=approval → designApplyTerminalApproval（/mlt/designApply/designApplyTerminalApproval）；其他 → designApplyApproval（/mlt/designApply/designApplyLecturerApproval）
> - isCancel（cancelApproval/designerCancelApproval）→ cancelApplyApproval（/mlt/designApply/designApplyCancelApproval）
> - pageType=designerApproval → designApplyApproval（/mlt/designApply/designApplyLecturerApproval）
> - 其他（approval）→ applyApproval（/mlt/designApply/designApplyApproval）

### 保存/提交校验

- 校验1：审批意见必填 —— applyApprovalFormDS.validate 校验 approvalComments 非空，确保审批决策有理由留痕
- 校验2：审批时需选择一条数据 —— getSelectedRow 校验 tableDS.selected.length===1，确保操作对象明确
- 校验3：设计改派时新设计师必填 —— newDesignerFormDS.validate 校验 lecturerName 非空，确保改派目标有效

### 状态机

```
[待审批] --审批通过--> [已通过] --进入执行--> [执行中]
         --驳回--> [已驳回] --修改重提--> [待审批]

[已通过] --取消申请--> [取消审批中] --审批通过--> [已取消]
                                  --审批驳回--> [已通过]

[执行中] --终止申请--> [终止审批中] --审批通过--> [已终止]
                                  --审批驳回--> [执行中]
```

| 状态 | 状态说明 | 可执行操作 |
|------|---------|-----------|
| 待审批 | 申请已提交待审批 | 审批、查看申请 |
| 已通过 | 审批通过 | 查看申请、设计改派(manage模式) |
| 已驳回 | 审批驳回 | 查看申请、修改重提 |
| 取消审批中 | 取消申请审批中 | 审批、查看申请 |
| 已取消 | 申请已取消 | 查看申请 |
| 终止审批中 | 终止申请审批中 | 审批、查看申请 |
| 已终止 | 项目已终止 | 查看申请 |
| 执行中 | 服务执行中 | 查看申请 |

#### 报错1：请选择一条数据
- **触发条件**：点击查看申请、审批、设计改派等行操作按钮时，未选择数据或选择了多行
- **逻辑分析**：前端在执行单选操作前校验选中行数量，若 selectedRows.length ≠ 1 则阻止操作并提示"请选择一条数据"。单选操作需要明确的目标申请，未选择时无法确定操作对象，多选时操作对象不唯一
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         APPLY_USER_NAME AS 申请人,
         DESIGN_NAME AS 设计名称,
         LECTURER_NAME AS 设计师,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错2：请求失败
- **触发条件**：调用 mlt/designApply/* 系列接口时，后端返回 HTTP 状态码非 2xx
- **逻辑分析**：前端通过 axios 调用后端接口，若响应状态码非 2xx 或网络异常则触发错误回调，统一提示"请求失败"。常见根因包括：mbo-business 微服务未启动或异常、数据库连接失败、SQL 执行超时、后端业务异常未捕获、外部系统（OA/FDD/CRM）调用失败、工作流引擎异常、网络中断等。需检查 mbo-business 微服务运行状态、外部系统连通性、工作流配置、后端日志定位具体异常堆栈
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DESIGN_NAME AS 设计名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态,
         CRM_ORDER_STATUS AS CRM订单状态,
         ERROR_INFO AS 异常问题,
         TO_CHAR(LAST_UPDATE_DATE,'YYYY-MM-DD HH24:MI:SS') AS 最后更新时间
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND LAST_UPDATE_DATE >= SYSDATE - 1
  ORDER BY LAST_UPDATE_DATE DESC;
  ```

#### 报错3：审批意见不能为空
- **触发条件**：提交审批时，APPROVAL_COMMENTS 字段为空
- **逻辑分析**：前端审批弹窗对 approvalComments 字段配置 required 校验，提交前校验审批意见是否填写，为空则阻止提交并提示"审批意见不能为空"。审批意见用于记录审批人决策依据，保证审批留痕完整可追溯
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DESIGN_NAME AS 设计名称,
         APPROVAL_STATE AS 审核状态,
         APPROVAL_RESULT AS 审批结果,
         APPROVAL_COMMENTS AS 审批意见
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND APPROVAL_STATE IN ('approved', 'reject')
    AND (APPROVAL_COMMENTS IS NULL OR APPROVAL_COMMENTS = '');
  ```

#### 报错4：新设计师不能为空
- **触发条件**：提交设计改派时，LECTURER_NAME 字段为空
- **逻辑分析**：前端设计改派弹窗对 lecturerName 字段配置 required 校验，提交前校验新设计师是否选择，为空则阻止提交并提示"新设计师不能为空"。设计改派需明确新的设计师作为改派目标，否则无法完成改派
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DESIGN_NAME AS 设计名称,
         LECTURER_NAME AS 当前设计师,
         LECTURER_ARCHIVES_CODE AS 设计师档案编码,
         ORDER_LECTURE_STATE AS 点将状态
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND ORDER_LECTURE_STATE = 'valid'
    AND (LECTURER_NAME IS NULL OR LECTURER_ARCHIVES_CODE IS NULL);
  ```

#### 报错5：网络异常/接口超时
- **触发条件**：任意接口调用时，网络中断或接口响应超过 axios timeout 配置
- **逻辑分析**：前端 axios 请求未收到响应或响应超时，触发 catch 回调统一提示"请求失败"。常见根因：网络中断、mbo-business 服务假死、数据库慢查询、工作流引擎响应慢、接口处理时间超过 timeout 阈值等。需检查网络连通性、后端服务负载、数据库性能、工作流引擎状态
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态,
         TO_CHAR(LAST_UPDATE_DATE,'YYYY-MM-DD HH24:MI:SS') AS 最后更新时间
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND LAST_UPDATE_DATE >= SYSDATE - 1
  ORDER BY LAST_UPDATE_DATE DESC;
  ```

#### 报错6：权限不足
- **触发条件**：点击查看申请、设计改派、审批等按钮时，当前用户无对应 permissionList 权限码
- **逻辑分析**：前端 Button 组件通过 permissionList 配置权限码（如 hzero.general_manage.design.design_general_manage.ps.show_apply、reassign、approval 等），HZERO 框架校验当前用户角色是否包含该权限码，未包含则按钮不可见或禁用。若强制调用接口，后端也会校验权限返回403。需联系管理员配置对应角色权限
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名,
         R.ROLE_NAME AS 角色名,
         P.PERMISSION_CODE AS 权限码
  FROM SYS_USER U
  LEFT JOIN SYS_USER_ROLE UR ON U.USER_ID = UR.USER_ID
  LEFT JOIN SYS_ROLE R ON UR.ROLE_ID = R.ROLE_ID
  LEFT JOIN SYS_ROLE_PERMISSION RP ON R.ROLE_ID = RP.ROLE_ID
  LEFT JOIN SYS_PERMISSION P ON RP.PERMISSION_ID = P.PERMISSION_ID
  WHERE P.PERMISSION_CODE LIKE 'hzero.general_manage.design.design_general_manage.ps.%'
  ORDER BY U.USER_NAME;
  ```

#### 报错7：数据不存在
- **触发条件**：查看申请、审批、设计改派等操作时，接口返回数据为空或申请编码不存在
- **逻辑分析**：前端通过 applyCode 调用详情接口，后端查询 DESIGN_APPLY 表无对应记录或记录已逻辑删除，返回空数据。常见根因：申请编码错误、申请已被删除、跨租户查询、数据权限隔离等。需检查 APPLY_CODE 有效性及数据权限
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         APPLY_USER_NAME AS 申请人,
         ORDER_LECTURE_STATE AS 点将状态,
         DELETE_FLAG AS 删除标记
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND (DELETE_FLAG = 'Y' OR APPLY_CODE IS NULL);
  ```

#### 报错8：状态不允许操作
- **触发条件**：点击审批、设计改派等按钮时，申请状态不在允许操作的状态范围内
- **逻辑分析**：后端校验申请状态机，如审批要求 APPROVAL_STATE 为 to_be_approval、设计改派要求 ORDER_LECTURE_STATE 为 valid 且审批通过、取消审批要求已发起取消申请等。状态不匹配时后端返回业务异常，前端提示后端返回的 message。需检查申请当前状态及操作流程
- **排查SQL**：
  ```sql
  SELECT APPLY_CODE AS 申请编码,
         DESIGN_NAME AS 设计名称,
         ORDER_LECTURE_STATE AS 点将状态,
         APPROVAL_STATE AS 审核状态,
         TERMINATION_APPROVAL_STATE AS 终止审批状态,
         ERROR_INFO AS 异常问题
  FROM DESIGN_APPLY
  WHERE APPLY_TYPE_ONE = 'design'
    AND APPROVAL_STATE NOT IN ('to_be_approval','approved','reject')
  ORDER BY CREATE_DATE DESC;
  ```

#### 报错9：审批人不能为空
- **触发条件**：提交审批时，前端从 getCurrentUser().realName 取审批人姓名为空
- **逻辑分析**：前端审批弹窗 beforeOpen 阶段设置 approvalUserName 为 userInfo.realName，若用户未登录或登录态失效导致 realName 为空，则审批人字段为空。需检查用户登录态、token 是否过期、用户信息接口是否正常
- **排查SQL**：
  ```sql
  SELECT U.USER_NAME AS 用户名,
         U.REAL_NAME AS 真实姓名,
         U.LOGIN_FLAG AS 登录标记,
         U.STATUS_CODE AS 状态
  FROM SYS_USER U
  WHERE U.REAL_NAME IS NULL
     OR U.STATUS_CODE <> 'ACTIVE';
  ```

#### 报错10：设计师列表为空
- **触发条件**：设计改派点击设计师搜索图标，弹窗 applyTableDS 查询返回空列表
- **逻辑分析**：前端通过 applyTableDS 查询讲师档案列表，返回空则无法选择新设计师。常见根因：讲师档案未配置、讲师档案已失效、查询条件过严、数据权限隔离等。需检查讲师档案配置及查询条件
- **排查SQL**：
  ```sql
  SELECT LECTURER_ARCHIVES_CODE AS 档案编码,
         LECTURER_NAME AS 讲师姓名,
         LECTURER_LEVEL AS 讲师级别,
         STATUS_CODE AS 状态,
         DELETE_FLAG AS 删除标记
  FROM LECTURER_ARCHIVES
  WHERE STATUS_CODE <> 'ACTIVE'
     OR DELETE_FLAG = 'Y'
  ORDER BY CREATION_DATE DESC;
  ```

### 常见问题
