# 门店管理-门店装修-门头展板兑现

## 业务流程

### 全链路流程图

```
门头展板报销申请单(APPROVED) → 新建门头展板兑现 → 选择报销申请单(LOV) → 填写兑现比例 → 保存(NEW) → 提交审批 → 工作流审批(区域经理→设计师→销售会计→运营专员) → 审批通过(APPROVED) → 生成额度内兑现单(FIN_FEE_TERMINAL_CASHOUT) → 推送资金池(EBS)
```

### 状态机

```text
NEW(新建) ──提交──→ RUN(审批中) ──┬──审批通过──→ APPROVED(已审批)
                                   ├──审批驳回──→ REBUT(已驳回) ──修改后重新提交──→ RUN
                                   └──审批退回──→ WITHDRAW(已撤回)
```

- 可编辑状态：NEW、WITHDRAW、INTERRUPT、REBUT
- 可删除状态：NEW、REBUT
- 审批通过后不可编辑/删除

## 重点逻辑

### 重点逻辑1：基于报销申请单发起兑现

- **业务意义**：门头展板兑现不能独立创建，必须关联已审批通过(APPROVED)的门头展板报销申请单，确保兑现有据可依
- **具体逻辑描述**：
  - 新增页面通过LOV(AE.CUSTDHCASHOUTHEADLIST.VIEW)选择报销申请单，接口GET `/cust-dh-reimburse-heads/get-cashout-lov`
  - 选择后调用GET `/cust-dh-reimburse-heads/do-select`查询报销单详情，联动带出经销商、交易公司、法人客户、预算年度、报销类型、支付方式、额度内外金额等全部信息
  - 后端checkParams校验：报销单必须存在且hzApproveStatus=APPROVED，否则报"报销单号不存在或未完成审核"
  - 后端checkParams校验：同一报销单下不能存在未审批完成的兑现单(状态非APPROVED)，否则报"该报销单存在未审批结束的兑现单X，请勿重复创建"

### 重点逻辑2：额度内外分开兑现

- **业务意义**：门头展板报销金额分为额度内和额度外两部分，兑现时分别按不同规则计算申请兑现金额
- **具体逻辑描述**：
  - 额度内申请兑现金额 = 额度内业务批准金额 - 已兑现的申请兑现金额(sumInCashoutApplyAmt)，由fillFields方法计算
  - 额度外申请兑现金额 = min(申请兑现比例 × 额度外实际报销金额, 额度外实际报销金额 - 已提报的额度外实际报销金额)
  - 额度外兑现比例(outCashoutRatio)由用户输入，范围0-1，前端校验：申请兑现比例 ≤ 1 - 已提报的申请兑现比例
  - 前端通过addEventListener('update')监听outCashoutRatio变化，自动计算outCashoutApplyAmt = outBxAmt × outCashoutRatio
  - 兑现金额为0时不允许保存(额度内和额度外均为0时报"兑现金额为0，保存失败")

### 重点逻辑3：工作流多节点审批

- **业务意义**：门头展板兑现需经过区域经理、设计师、销售会计、运营专员多级审批，各节点可编辑不同字段
- **具体逻辑描述**：
  - 工作流编码：SUB_STORE_MTZBBXDX(门头展板报销兑现)
  - 提交时调用onUserSubmit，通过workflowClient.startInstanceByFlowKey启动工作流实例，设置HZ_INSTANCE_ID和HZ_APPROVE_STATUS=RUN
  - 审批节点保存时调用nodeEditSave，根据taskName分发到不同节点更新方法：
    - 区域经理审批(bizNodeUpdate)：更新验收方式bzsBizMethod、保证人bzsBizName、保证时间bzsBizTime(自动取当前时间)、提前兑现比例inEarlyCashoutRatio
    - 设计师审批(designerNodeUpdate)：更新验收方式bzsDesMethod、保证人bzsDesName、保证时间bzsDesTime
    - 销售会计审批(salesFinUpdate)：更新额度外兑现有效期outValidDate、备注remark，校验首次兑现才允许修改有效期
    - 运营专员审批(operatNodeUpdate)：仅更新附件
  - 前端通过window.addEventListener('message', handleEvent)监听工作流iframe的审批动作，匹配taskName为区域经理/设计师/销售会计/运营专员时执行saveValid校验

### 重点逻辑4：审批通过后处理(onWfComplete)

- **业务意义**：审批通过后设置兑现有效期、入账信息，并触发定时任务生成额度内兑现单
- **具体逻辑描述**：
  - 获取系统参数dh_cashout_valid_month(额度内有效月数)，设置额度内兑现有效期 = 当月1日 + (validMonth + 1)个月
  - 设置审核通过时间checkTime = 当前时间
  - 设置额度内剩余未兑现金额inThisSurCashoutAmt = 额度内申请兑现金额
  - 设置额度外剩余未兑现金额outThisSurCashoutAmt = 0
  - 若payType=3(经销商承担)且额度外申请兑现金额>0，设置入账日期finDate和入账金额finAmt = 额度外申请兑现金额
  - 更新HZ_APPROVE_STATUS = APPROVED
  - 定时任务syncCustDhCashoutGenerateV：查询已审批兑现单，计算广告费余额、核销金额、提前兑现金额，生成FIN_FEE_TERMINAL_CASHOUT额度内兑现单

### 重点逻辑5：首次提交额度外预算校验(firstSubmitVerify)

- **业务意义**：使用额度外预算时校验预算充足和经销商限额，防止超额兑现
- **具体逻辑描述**：
  - 仅当兑现单额度外申请金额>0且政策标准useExtraBudgetFlag=Y时执行
  - 校验1：已使用金额(其他兑现单的outCashoutApplyAmt之和) + 本次兑现金额 ≤ 当前年份总预算金额(viewOverBudgetAmt)，否则报"额度外预算不足，有疑问请联系财务"
  - 校验2(经销商限额控制custLimitFlag=Y)：经销商限额 - 已报销金额 + 当前报销单实际额度外报销金额 - 当前申请金额 ≥ 0，否则报"额度外申请金额需≤剩余可报销限额"
  - 校验3：同一报销单下，本次额度外申请金额 ≤ 报销单实际额度外报销金额 - 已提交或已审批的sum(各兑现单本次额度外申请金额)

### 重点逻辑6：验收人员保证书

- **业务意义**：设计师和区域经理需签署保证书，确认门头展板已真实验收，防止虚假兑现
- **具体逻辑描述**：
  - 前端GuaranteeTab组件渲染保证书HTML，包含设计师验收和区域经理验收两部分
  - 设计师验收：勾选验收方式(1-视频验收/2-现场验收)，填写保证人姓名，保证时间自动取当前时间
  - 区域经理验收：勾选验收方式(1-视频验收/2-现场验收)，填写保证人姓名，保证时间自动取当前时间
  - 验收方式通过CheckBox多选，值以逗号拼接存入bzsDesMethod/bzsBizMethod
  - 前端saveValid校验：区域经理审批时校验bzsBizMethod和bzsBizName必填且保证人=当前用户；设计师审批时校验bzsDesMethod和bzsDesName必填且保证人=当前用户

### 重点逻辑7：编码生成

- **业务意义**：门头展板兑换单号按规则自动生成，确保唯一性和可追溯性
- **具体逻辑描述**：
  - 编码规则：AE.DH_CASHOUT_HEAD_NO
  - 生成方式：prefixCode + suffixCode，prefixCode为事业部编码(divisionCode)，若为空则用"ARR"
  - suffixCode通过CodeRuleBuilder.generateCode生成流水号
  - 生成时机：doInsert时调用genCashoutNo方法

### 保存校验

- 校验1：报销申请单必填 —— 确保兑现单关联有效的报销申请单
  - 详细逻辑：前端DataSet required=true校验，后端getReimburseHead查询报销单，不存在或非APPROVED报"报销单号不存在或未完成审核"
  - 系统体现：前端C7N必填提示，后端CommonException
  - 排查SQL：`SELECT * FROM CUST_DH_REIMBURSE_HEAD WHERE ID = #{reimburseHeadId} AND HZ_APPROVE_STATUS = 'APPROVED'`

- 校验2：额度外兑现比例范围0-1 —— 防止输入非法比例值
  - 详细逻辑：前端validator校验value<0报"申请兑现比例不能小于0"，value > 1-sumOutCashoutRatio报"申请兑现比例需≤X"；后端checkParams校验outCashoutRatio < 0或> 1报"额度外兑现比例必须在0到1之间"
  - 系统体现：前端字段validator提示，后端CommonException
  - 排查SQL：`SELECT SUM(OUT_CASHOUT_RATIO) AS SUM_RATIO FROM CUST_DH_CASHOUT_HEAD WHERE REIMBURSE_HEAD_ID = #{reimburseHeadId} AND HZ_APPROVE_STATUS = 'APPROVED' AND ID != #{currentId}`

- 校验3：同一报销单不能有未审批完成的兑现单 —— 防止重复创建兑现单
  - 详细逻辑：后端checkParams查询同一REIMBURSE_HEAD_ID下HZ_APPROVE_STATUS非APPROVED的兑现单，存在则报"该报销单存在未审批结束的兑现单X，请勿重复创建"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT * FROM CUST_DH_CASHOUT_HEAD WHERE REIMBURSE_HEAD_ID = #{reimburseHeadId} AND HZ_APPROVE_STATUS != 'APPROVED' AND ID != #{currentId}`

- 校验4：行表不能为空 —— 确保有门店装修信息
  - 详细逻辑：后端checkParams校验lines为空报"行表不能为空"；前端校验terminalData为空报"请至少添加一条门店信息"
  - 系统体现：前端message.error，后端CommonException
  - 排查SQL：`SELECT COUNT(*) FROM CUST_DH_CASHOUT_LINE WHERE HEAD_ID = #{headId}`

- 校验5：兑现金额不能为0 —— 确保有实际兑现金额
  - 详细逻辑：后端checkParams校验额度内和额度外申请兑现金额均为0时报"兑现金额为0，保存失败"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT IN_CASHOUT_APPLY_AMT, OUT_CASHOUT_APPLY_AMT FROM CUST_DH_CASHOUT_HEAD WHERE ID = #{id}`

- 校验6：区域经理审批时验收方式与保证人必填 —— 确保验收真实性
  - 详细逻辑：前端saveValid校验taskName匹配"区域经理"时，bzsBizMethod为空或bzsBizName!=当前用户realName报"请填写【验收人员保证书】区域经理相关信息！"；后端bizNodeUpdate校验bzsBizMethod为空报"验收方式不能为空"，bzsBizName为空报"区域经理名字不能为空"
  - 系统体现：前端notification.error，后端CommonException

- 校验7：设计师审批时验收方式与保证人必填 —— 确保验收真实性
  - 详细逻辑：前端saveValid校验taskName=="设计师审批"时，bzsDesMethod为空或bzsDesName!=当前用户realName报"请填写【验收人员保证书】展示设计师相关信息！"；后端designerNodeUpdate校验bzsDesMethod为空报"验收方式不能为空"，bzsDesName为空报"区域经理名字不能为空"
  - 系统体现：前端notification.error，后端CommonException

- 校验8：销售会计审批时额度外兑现有效期必填 —— 确保额度外兑现有有效期约束
  - 详细逻辑：前端outValidDate在taskName=="销售会计审批"时required=true；后端salesFinUpdate校验outValidDate为空报"额度外兑现有效期不能为空"，非首次兑现修改报"报销单非首次兑现，不允许编辑额度外兑现有效期"
  - 系统体现：前端C7N必填提示，后端CommonException

- 校验9：附件校验 —— 确保必要附件已上传
  - 详细逻辑：前端saveValid调用childRefUpload.current.validateUpload()校验附件；提交时(temp=1)还需otherValidate('验收时间及定位水印照片')和otherValidate('报销申请审批表')；运营专员审批时需otherValidate('兑现申请审批表')
  - 系统体现：前端UploadTable组件校验

### 提交校验

- 校验1：额度外预算充足 —— 防止超额兑现
  - 详细逻辑：首次提交时firstSubmitVerify，当额度外申请金额>0且政策useExtraBudgetFlag=Y时，查询当前年份总预算(viewOverBudgetAmt)，校验已使用金额+本次兑现金额≤总预算，否则报"额度外预算不足，有疑问请联系财务"
  - 系统体现：后端CommonException
  - 排查SQL：`SELECT * FROM POLICY_STANDARD_HEAD WHERE POLICY_STANDARD_ID = #{policyStandardId} AND USE_EXTRA_BUDGET_FLAG = 'Y'`

- 校验2：经销商限额 —— 防止超过经销商限额
  - 详细逻辑：当政策custLimitFlag=Y时，校验经销商限额-已报销金额+当前报销单实际额度外报销金额-当前申请金额≥0，否则报"额度外申请金额需≤剩余可报销限额"
  - 系统体现：后端CommonException

- 校验3：同一报销单剩余可申请金额 —— 防止超过报销单可兑现余额
  - 详细逻辑：校验本次额度外申请金额≤报销单实际额度外报销金额-已提交或已审批的sum(各兑现单本次额度外申请金额)，否则报"申请金额需≤剩余未申请金额"
  - 系统体现：后端CommonException

### 下游影响

- **FIN_FEE_TERMINAL_CASHOUT(额度内兑现单)**：审批通过后定时任务syncCustDhCashoutGenerateV生成额度内兑现单，计算核销金额、提前兑现金额、广告费余额，按月生成兑现记录
- **资金池(EBS)**：通过synAdjustCashPoolToEbs推送兑现数据至EBS资金池，sourceType="广告费（额外）"，amount=额度外申请兑现金额

#### 报错1：报销单号不存在或未完成审核
- **触发条件**：点击"保存"按钮，checkParams校验时按reimburseHeadId查询CUST_DH_REIMBURSE_HEAD返回null，或返回记录的hzApproveStatus≠APPROVED
- **逻辑分析**：门头展板兑现必须基于已审批通过的门头报销申请单发起，确保兑现有据可依。若报销单在兑现前被删除、reimburseHeadId传值错误（如LOV缓存失效）、或报销单仍处于RUN/NEW/REBUT等中间状态，校验不通过抛异常阻断保存。需核查报销单是否存在且已APPROVED。
- **排查SQL**：
  ```sql
  SELECT r.id                 AS 报销单ID,
         r.reimburse_code     AS 报销单号,
         r.hz_approve_status  AS 审批状态,
         r.last_update_date   AS 最后更新时间
  FROM   cust_dh_reimburse_head r
  WHERE  r.id = #{传入的reimburseHeadId};
  ```

#### 报错2：该报销单存在未审批结束的兑现单X，请勿重复创建
- **触发条件**：点击"保存"按钮，checkParams校验时查询同一REIMBURSE_HEAD_ID下CUST_DH_CASHOUT_HEAD存在hzApproveStatus非APPROVED的记录
- **逻辑分析**：同一报销单下同一时间只允许存在一个未审批完成的兑现单，避免并发兑现造成额度重复占用。校验逻辑按reimburseHeadId查询CUST_DH_CASHOUT_HEAD，若存在状态在(NEW,RUN,REBUT,WITHDRAW)的记录即抛异常。常见根因：用户重复点击新增、前一笔兑现单未提交或被驳回未处理。
- **排查SQL**：
  ```sql
  SELECT c.id                 AS 兑现单ID,
         c.cashout_no         AS 兑现单号,
         c.reimburse_head_id  AS 报销单ID,
         c.hz_approve_status  AS 审批状态,
         c.creation_date      AS 创建时间
  FROM   cust_dh_cashout_head c
  WHERE  c.reimburse_head_id = #{传入的reimburseHeadId}
  AND    c.hz_approve_status <> 'APPROVED'
  ORDER  BY c.creation_date DESC;
  ```

#### 报错3：额度外兑现比例必须在0到1之间
- **触发条件**：点击"保存"按钮，checkParams校验outCashoutRatio < 0 或 outCashoutRatio > 1
- **逻辑分析**：额度外兑现比例用于计算额度外申请兑现金额（=额度外实际报销金额×比例），业务上比例应为0~1之间的百分数（如0.5表示兑现50%）。若用户输入负数、大于1的值、或前端NumberField精度控制失效，校验不通过。需修正兑现比例至合法区间。
- **排查SQL**：
  ```sql
  SELECT c.id                   AS 兑现单ID,
         c.cashout_no           AS 兑现单号,
         c.out_cashout_ratio    AS 额度外兑现比例,
         c.out_cashout_apply_amt AS 额度外申请兑现金额
  FROM   cust_dh_cashout_head c
  WHERE  (c.out_cashout_ratio < 0 OR c.out_cashout_ratio > 1)
  AND    c.hz_approve_status = 'NEW'
  ORDER  BY c.creation_date DESC;
  ```

#### 报错4：行表不能为空
- **触发条件**：点击"保存"按钮，checkParams校验从报销单行表CUST_DH_REIMBURSE_LINE带入的lines集合为空
- **逻辑分析**：兑现单需关联门店装修信息行表（含门店编码、面积、装修前后照片等），行表数据从报销单行表联动带入。若报销单行表为空（报销单未维护门店明细）、LOV选择报销单后未触发联动查询、或前端terminalTableDS数据源未正确绑定，lines为空抛异常。需核查报销单行表数据完整性。
- **排查SQL**：
  ```sql
  SELECT r.id              AS 报销单ID,
         r.reimburse_code  AS 报销单号,
         (SELECT COUNT(1)
          FROM   cust_dh_reimburse_line l
          WHERE  l.head_id = r.id) AS 行表记录数
  FROM   cust_dh_reimburse_head r
  WHERE  r.hz_approve_status = 'APPROVED'
  AND    NOT EXISTS (SELECT 1 FROM cust_dh_reimburse_line l WHERE l.head_id = r.id)
  ORDER  BY r.last_update_date DESC;
  ```

#### 报错5：兑现金额为0，保存失败
- **触发条件**：点击"保存"按钮，checkParams校验inCashoutApplyAmt=0且outCashoutApplyAmt=0
- **逻辑分析**：兑现单需有实际兑现金额才有业务意义。额度内申请兑现金额=额度内业务批准金额-已兑现金额，额度外申请兑现金额=兑现比例×额度外实际报销金额。若报销单额度内金额已全部兑现完且额度外比例为0（或额度外金额为0），两者均为0抛异常。常见根因：报销单已全额兑现、用户未填写兑现比例、或报销单金额异常为0。
- **排查SQL**：
  ```sql
  SELECT c.id                    AS 兑现单ID,
         c.cashout_no            AS 兑现单号,
         c.in_cashout_apply_amt  AS 额度内申请兑现金额,
         c.out_cashout_apply_amt AS 额度外申请兑现金额,
         c.in_biz_amt            AS 额度内业务批准金额,
         c.out_fin_amt           AS 额度外财务批准金额,
         c.out_cashout_ratio     AS 额度外兑现比例
  FROM   cust_dh_cashout_head c
  WHERE  c.hz_approve_status = 'NEW'
  AND    NVL(c.in_cashout_apply_amt, 0) = 0
  AND    NVL(c.out_cashout_apply_amt, 0) = 0
  ORDER  BY c.creation_date DESC;
  ```

#### 报错6：额度外预算不足，有疑问请联系财务
- **触发条件**：点击"提交"按钮，firstSubmitVerify校验兑现单额度外申请金额>0且政策useExtraBudgetFlag=Y时，已使用金额+本次兑现金额>当前年份总预算金额(viewOverBudgetAmt)
- **逻辑分析**：额度外兑现占用年度预算总额，需确保预算充足。校验逻辑汇总当前年份同事业部下其他兑现单的outCashoutApplyAmt之和（已使用金额），加上本次申请金额，若超过FIN_FEE_CHECK_BX_HEADER中该年份总预算金额即抛异常。常见根因：年度预算配置不足、历史兑现单占用过多、或本次申请金额过大。需联系财务确认预算或减少申请金额。
- **排查SQL**：
  ```sql
  SELECT b.bud_year              AS 预算年度,
         b.division_id           AS 事业部ID,
         b.total_amt             AS 年度总预算,
         NVL((SELECT SUM(c.out_cashout_apply_amt)
              FROM   cust_dh_cashout_head c
              WHERE  c.year = b.bud_year
              AND    c.division_id = b.division_id
              AND    c.hz_approve_status IN ('RUN','APPROVED','RETURN','INTERRUPT')), 0) AS 已使用金额
  FROM   fin_fee_check_bx_header b
  WHERE  b.fee_type_id = 66014602
  AND    b.bud_year = #{当前年份}
  ORDER  BY b.division_id;
  ```

#### 报错8：申请金额需≤剩余未申请金额
- **触发条件**：点击"提交"按钮，firstSubmitVerify校验同一报销单下，本次额度外申请金额>报销单实际额度外报销金额-已提交或已审批的sum(各兑现单本次额度外申请金额)
- **逻辑分析**：同一报销单下可分多次兑现，但累计额度外申请金额不得超过报销单实际额度外报销金额。校验逻辑计算：报销单实际额度外报销金额-已有兑现单(状态RUN/APPROVED/RETURN/INTERRUPT)的outCashoutApplyAmt之和，若本次申请金额超过该余额即抛异常。常见根因：已有兑现单占用大部分金额、本次申请金额过大、或报销单金额被错误调整。
- **排查SQL**：
  ```sql
  SELECT r.id                       AS 报销单ID,
         r.reimburse_code           AS 报销单号,
         r.out_fin_amt              AS 额度外实际报销金额,
         NVL((SELECT SUM(c.out_cashout_apply_amt)
              FROM   cust_dh_cashout_head c
              WHERE  c.reimburse_head_id = r.id
              AND    c.hz_approve_status IN ('RUN','APPROVED','RETURN','INTERRUPT')), 0) AS 已申请金额,
         r.out_fin_amt - NVL((SELECT SUM(c.out_cashout_apply_amt)
              FROM   cust_dh_cashout_head c
              WHERE  c.reimburse_head_id = r.id
              AND    c.hz_approve_status IN ('RUN','APPROVED','RETURN','INTERRUPT')), 0) AS 剩余未申请金额
  FROM   cust_dh_reimburse_head r
  WHERE  r.hz_approve_status = 'APPROVED'
  ORDER  BY r.last_update_date DESC;
  ```

- **触发条件**：设计师审批节点保存，前端saveValid校验taskName=="设计师审批"时，bzsDesMethod为空或bzsDesName≠当前用户realName
- **逻辑分析**：保证书要求设计师签署验收方式和保证人姓名，确认门头展板已真实验收。若设计师未勾选验收方式(bzsDesMethod为空)或保证人姓名与当前登录用户不一致(bzsDesName≠realName，防止代签)，前端notification.error提示。需在保证书Tab勾选验收方式并确认保证人为当前用户。
- **排查SQL**：
  ```sql
  SELECT c.id              AS 兑现单ID,
         c.cashout_no      AS 兑现单号,
         c.bzs_des_method  AS 设计师验收方式,
         c.bzs_des_name    AS 设计师保证人,
         c.hz_approve_status AS 审批状态
  FROM   cust_dh_cashout_head c
  WHERE  c.hz_approve_status = 'RUN'
  AND    (c.bzs_des_method IS NULL OR c.bzs_des_name IS NULL)
  ORDER  BY c.last_update_date DESC;
  ```

#### 报错26：请至少添加一条门店信息
- **触发条件**：点击"保存"或"提交"按钮，前端handleSave/handleSaveWithWorkflow校验terminalData为空或length=0
- **逻辑分析**：兑现单需关联门店装修信息行表，前端通过terminalTableDSRef管理行数据。若用户未添加门店行、行数据被误清空、或从报销单联动带入行表失败，terminalData为空前端message.error提示。需确保至少有一条门店装修信息。
- **排查SQL**：
  ```sql
  SELECT c.id              AS 兑现单ID,
         c.cashout_no      AS 兑现单号,
         (SELECT COUNT(1)
          FROM   cust_dh_cashout_line l
          WHERE  l.head_id = c.id) AS 行表记录数
  FROM   cust_dh_cashout_head c
  WHERE  c.hz_approve_status = 'NEW'
  AND    NOT EXISTS (SELECT 1 FROM cust_dh_cashout_line l WHERE l.head_id = c.id)
  ORDER  BY c.creation_date DESC;
  ```

#### 报错27：额度外财务批准金额大于0时，必须填写兑现有效期
- **触发条件**：保存时前端validateOutValidDate校验outFinAmt>0且outValidDate为空且firstOutValidDate为空(首次兑现)
- **逻辑分析**：额度外财务批准金额大于0时需设置兑现有效期约束兑现资金使用期限。若outFinAmt>0但未填写outValidDate且为首次兑现(firstOutValidDate为空)，前端message.error提示。需在额度外兑现有效期字段填写日期。
- **排查SQL**：
  ```sql
  SELECT c.id              AS 兑现单ID,
         c.cashout_no      AS 兑现单号,
         c.out_fin_amt     AS 额度外财务批准金额,
         c.out_valid_date  AS 额度外兑现有效期,
         c.first_out_valid_date AS 首单额度外有效期,
         c.hz_approve_status AS 审批状态
  FROM   cust_dh_cashout_head c
  WHERE  c.hz_approve_status = 'NEW'
  AND    NVL(c.out_fin_amt, 0) > 0
  AND    c.out_valid_date IS NULL
  AND    c.first_out_valid_date IS NULL
  ORDER  BY c.creation_date DESC;
  ```

## 常见问题FAQ

**Q1：报销申请单LOV无数据？**
A：检查CUST_DH_REIMBURSE_HEAD表中是否存在HZ_APPROVE_STATUS='APPROVED'的记录，且该报销单下不存在未审批完成的兑现单。排查SQL：`SELECT * FROM CUST_DH_REIMBURSE_HEAD WHERE HZ_APPROVE_STATUS = 'APPROVED' AND ENTID = #{当前用户组织ID}`

**Q2：兑现金额计算不正确？**
A：额度内申请兑现金额 = 额度内业务批准金额 - 已兑现的申请兑现金额(同一报销单下APPROVED状态的兑现单IN_CASHOUT_APPLY_AMT之和)。额度外申请兑现金额 = min(兑现比例 × 额度外实际报销金额, 额度外实际报销金额 - 已提报金额)。排查SQL：`SELECT SUM(IN_CASHOUT_APPLY_AMT), SUM(OUT_CASHOUT_APPLY_AMT), SUM(OUT_CASHOUT_RATIO) FROM CUST_DH_CASHOUT_HEAD WHERE REIMBURSE_HEAD_ID = #{reimburseHeadId} AND HZ_APPROVE_STATUS = 'APPROVED'`

**Q3：审批流程未启动？**
A：检查workflow/proc-submit接口调用参数是否完整(objId, subject='SUB_STORE_MTZBBXDX', flowCode)。确认工作流配置中SUB_STORE_MTZBBXDX流程已部署。排查SQL：`SELECT HZ_INSTANCE_ID, HZ_APPROVE_STATUS FROM CUST_DH_CASHOUT_HEAD WHERE ID = #{id}`

**Q4：额度外预算不足？**
A：检查当前年份额度外总预算是否充足。排查SQL：`SELECT * FROM FIN_FEE_CHECK_BX_HEADER WHERE BUD_YEAR = #{year} AND FEE_TYPE_ID = 66014602 AND DIVISION_ID = #{divisionId}`。同时检查已使用金额：`SELECT SUM(OUT_CASHOUT_APPLY_AMT) FROM CUST_DH_CASHOUT_HEAD WHERE REIMBURSE_HEAD_ID = #{reimburseHeadId} AND HZ_APPROVE_STATUS IN ('RUN','RETURN','APPROVED','INTERRUPT')`

**Q5：保证书无法填写？**
A：确认当前审批节点taskName为"区域经理审批"或"设计师审批"。保证书中的CheckBox和TextField仅在对应对审批节点可编辑。前端通过taskName匹配控制disabled属性。

**Q6：门店装修信息为空？**
A：门店装修信息从报销申请单行表联动带入，选择报销申请单时自动加载。若为空，检查报销单行表CUST_DH_REIMBURSE_LINE是否有数据。排查SQL：`SELECT * FROM CUST_DH_REIMBURSE_LINE WHERE HEAD_ID = #{reimburseHeadId}`
